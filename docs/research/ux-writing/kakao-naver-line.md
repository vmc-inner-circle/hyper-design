## 0. 먼저 알아 둘 것: 찾은 것과 못 찾은 것

| **카카오페이** | 없음 | **공식 UX 라이팅/보이스톤 글 못 찾음.** tech.kakaopay.com 사이트맵의 글 164개를 다 훑었지만 UX 라이팅 글 없음 |

**요청한 세부 질문 가운데 근거를 못 찾은 것**
- 탭과 섹션 헤더를 명사로 끝낼지 해요체로 끝낼지 위치별로 정한 규칙: 다섯 회사 어디에도 없음. 카카오 문서 가이드의 "제목 품사 규칙"이 가장 가까운 근거임(아래 K-1).
- 해요체와 합니다체 가운데 무엇을 고를지와 그 이유: 다섯 회사 모두 명시적 근거 없음. 다만 정황은 있음. 네이버파이낸셜은 개선안을 해요체로 씀(N-2). LINE은 한국어 예시에서 합니다체와 해요체를 섞어 씀(L-1~L-6). 카카오 개발자 문서는 합니다체로 정해져 있는데, 이건 문서용 규칙임(K-6).
- "~할 수 있어요" 남용 금지 규칙: 못 찾음. 오히려 네이버파이낸셜의 개선 예시와 LINE 예시에 "~할 수 있어요/있습니다"가 그대로 쓰임.
- 제목을 조건절, 조사, 대시(—)로 끝내지 말라는 규칙: 못 찾음.
- "님/고객님" 호칭 규칙: 직접적인 규칙은 못 찾음. LINE 예시에 "Brown이" → "Brown님이"로 고친 사례 하나뿐(L-4).
- 빈 화면(empty state) 문구 규칙: 한국어 예시는 못 찾음. LINE 영문 예시 1건만 있음(L-9).

## 1. LINE — LINE Voice (LINE Design System)

- 한국어 페이지 데이터: https://designsystem.line.me/page-data/about/line-voice-ko/page-data.json (화면 주소는 https://designsystem.line.me/about/line-voice-ko)
- 영어 페이지 데이터: https://designsystem.line.me/page-data/about/line-voice-en/page-data.json
- 예시 이미지: https://vos.line-scdn.net/strapi-cluster-instance-bucket-474/ 아래의 LINE_Voice_Re_KR_01~05, g_img_6 등. 이미지는 직접 열어 읽었고, 아래에 글자 그대로 옮겼다.
- 참고: 2026-10 현재 HTML 페이지(`/about/line-voice`)는 403을 반환한다. 위 page-data JSON은 정상(200)으로 받았다.

**서문(ko, 원문 그대로):** "LINE이 사용자와 소통하는 방식은 'CLOSING THE DISTANCE'라는 LINE의 미션과 맞닿아 있습니다. LINE은 사람, 정보, 서비스 간의 거리를 좁히고, 세상의 모든 것들을 연결하기 위해 다음과 같은 목소리를 사용합니다."
**서문(en, 원문 그대로):** "CLOSING THE DISTANCE means knowing whom to write for, writing to be understood, and writing for our audience, not ourselves."

### L-1. 오류는 원인과 해결 방법을 함께 알린다
- 원칙(원문): "명확하지 않은 텍스트는 읽기도, 이해하기도 어렵습니다. 사용자가 LINE의 목소리를 신뢰할 수 있도록, 다르게 해석될 여지가 없는 명료하고 단순한 표현만 사용해 주세요." / "문제 상황의 원인을 명확하게 알려주고, 해결 방안도 함께 제시합니다."
- 예시(이미지 LINE_Voice_Re_KR_01, 대화상자):
  - ✕ 제목 `비밀번호가 올바르지 않습니다.` / 본문 `계정을 사용할 수 없습니다.` / 버튼 `확인`
  - ✓ 제목 `비밀번호가 5회 불일치하여 계정이 잠겼습니다.` / 본문 `잠금을 해제하려면 고객센터에 문의해 주세요.` / 버튼 `확인`
- 이유(원문): "사용자가 LINE의 목소리를 신뢰할 수 있도록".
- 관찰: 좋은 예도 합니다체로 썼다. 무엇이 일어났는지는 제목에, 해결 방법은 본문에 "~하려면 ~해 주세요" 꼴로 나눠 썼다.

### L-2. 확인창 버튼에 "취소/확인"을 쓰지 않는다 (같은 말이 두 뜻으로 읽힘)
- 원칙(원문): "중의적으로 해석될 수 있는 표현 대신, 사용자의 빠른 선택을 도울 수 있는 명확한 표현을 사용합니다."
- 예시(이미지 LINE_Voice_Re_KR_02):
  - ✕ 제목 `영수증 등록을 취소하시겠습니까?` / 버튼 `취소` `확인`
  - ✓ 제목 `영수증 등록을 취소하시겠습니까?` / 본문 `작성한 내용이 모두 삭제됩니다.` / 버튼 `아니오` `네`
- 이유: 원문에는 "중의적으로 해석될 수 있는 표현 대신"이라고만 되어 있다. (추론) 질문이 "취소하시겠습니까?"인데 버튼도 "취소"라서, 그 버튼이 '취소를 그만두기'인지 '취소하기'인지 헷갈린다. 결과(작성한 내용 삭제)도 본문에 미리 알렸다.
- 함께 볼 영어 원칙(en, 원문): "Buttons are the user's voice — Anticipate the user's intent with intelligent button labels."
  - en 예시(LINE_Voice_Re_EN_01): ✕ `Download the LINE Black theme?` + `Go to Theme shop` / `Cancel` → ✓ 같은 질문 + `Download now` / `Later`
  - en 예시(LINE_Voice_Re_EN_03): ✕ 제목 `Verify age` / `You can't join the chat if you haven't verified your age.` / 버튼 `Confirm` → ✓ `You need to verify your age to join this chat. Verify now?` / 버튼 `Verify` `Close`

### L-3. 사람과 대화하듯이: 어려운 말과 외래어를 줄이고, 다음 행동을 알려 준다
- 원칙(원문): "실제 존재하는 'LINE'이라는 사람과 사용자가 서로 대화를 나누고 있다고 상상해 보세요. 사용자가 일상에서 자주 쓰는 쉬운 용어로 따뜻하고 친근하게 사용자와 소통해 주세요." / "오류 상황에서도 따뜻하고 위트 있는 목소리로 해결 방식을 안내합니다. 어려운 기술 용어나 불필요한 외래어 사용은 최소화합니다."
- 예시(이미지 LINE_Voice_Re_KR_03, 오류 화면):
  - ✕ `잘못된 미팅 사이트 URL입니다.` / `다시 한번 확인해주세요.` / `또는 URL을 카피하여 공유해보세요.`
  - ✓ 제목 `앗! 미팅 장소가 여기가 아닌것 같아요` / 본문 `미팅 링크를 다시 입력해 보세요` / `미팅을 새로 만들어 멤버들에게만 공유할 수도 있어요`
- 관찰: "URL→링크", "카피하여→(삭제)", "사이트→장소"로 외래어와 기술 용어를 바꿨다. 좋은 예에서는 합니다체가 해요체로 바뀌었고, 마침표도 없다. 띄어쓰기 "아닌것"은 원문 그대로 옮겼다.
- 영어 원칙(원문): "Our job is to translate the complex into the intuitive. This means always speaking the user's language." / "Most casual users don't think of themselves as "users." Go for more natural words."

### L-4. 알림 문구: 이름에 "님"을 붙이고, 다음에 할 일을 제안한다
- 원칙(원문): "사용자 사이의 소통, 새로운 연결을 친근한 목소리로 응원하고 격려해 주세요."
- 예시(이미지 LINE_Voice_Re_KR_04, 목록 항목):
  - ✕ `Brown이 LINE에 가입했습니다.`
  - ✓ `Brown님이 LINE에 가입했습니다.` / 보조 문구 `따뜻한 환영 메시지를 보내보세요.`
- 이유: 원문은 "친근한 목소리로 응원하고 격려"라고만 한다. (추론) 다른 사용자 이름에 "님"을 붙이는 것은 높임 처리이고, 보조 문구는 다음 행동을 이끈다. 이번 조사에서 호칭 "님"에 관한 근거는 이것 하나뿐이다.

### L-5. 실패는 사용자 탓이 아니다. 뭉뚱그린 "오류"를 쓰지 말고 구체적인 원인을 쓴다
- 원칙(원문): "과업의 실패는 사용자의 탓이 아닙니다. 사용자의 탐색과 선택을 위축시킬 수 있는 단정적인 통보나 비난은 삼가 주세요."
- 예시(이미지 LINE_Voice_Re_KR_05, 토스트):
  - ✕ `오류가 발생했습니다. 다운로드에 실패했습니다.`
  - ✓ `휴대폰 저장 공간이 부족하여 다운로드할 수 없습니다.`
- 관찰: "오류가 발생했습니다"처럼 시스템 쪽에서 말하는 상투구를 원인을 담은 한 문장으로 바꿨다. 좋은 예도 합니다체다.

### L-6. 완료 문구: "대상 추가 완료" 같은 명사 나열 대신 일어난 일을 문장으로 쓰고, 되돌리는 방법을 알린다
- 원칙(원문): "수행한 액션의 결과에 대해 사용자가 확신할 수 있도록 도와주세요. 사용자의 불안감을 이해하고, 다른 선택도 가능하다는 사실을 알려주세요."
- 예시(이미지 g_img_6_2x_980cc8bc87_87d128433e):
  - ✕ 제목 `대상 추가 완료` / 본문 `차단 대상은 설정 > LINE VOOM 차단 계정에서 볼 수 있습니다.` / 버튼 `확인`
  - ✓ 제목 `Brown님을 차단했습니다` / 본문 `설정 > LINE VOOM > LINE VOOM 차단 계정에서 언제든지 차단을 해제할 수 있습니다.` / 버튼 `확인`
- **번역투 판단에 가장 직접적인 근거다.** "대상 추가 완료"는 'Target added'를 그대로 옮긴 듯한 명사 나열 제목이다. 이를 주어(누구를)와 동사(차단했습니다)가 있는 문장 제목으로 고쳤다. 제목 끝에는 마침표가 없다.
- 이유(원문): "사용자가 확신할 수 있도록" / "다른 선택도 가능하다는 사실을 알려주세요".

### L-7. (영문) 능동문으로 쓴다
- 원칙(en 원문): "Use active sentences"
- 예시(en, g_img_6_2x_4157d7fd12): ✕ `Versions of LINE older than 7.16.0 will stop working after support ends.` → ✓ `Versions of LINE below 7.16.0 will no longer be usable once support ends.`
- 관찰: 이미지 속 예시는 능동/수동 대비가 뚜렷하지 않다. 한국어판에는 이 항목이 없다.

### L-8. (영문) 할 수 없는 것보다 할 수 있는 것을 강조한다
- 원칙(en 원문): "Emphasize what users can do instead of what they can't"
- 예시(LINE_Voice_Re_EN_03): ✕ `You can't join the chat if you haven't verified your age.` → ✓ `You need to verify your age to join this chat. Verify now?`
- 함께 볼 원칙(en 원문): "Use descriptive links instead of URLs paired with instructions"

### L-9. (영문) 짧게 쓰고 전문 용어로 길게 설명하지 않는다 (빈 화면, 오류 화면)
- 원칙(en 원문): "If nothing else, text must be understood. Trim away unimportant information to make the main ideas impossible to miss. Part of this means using consistent language and terminology, but when choosing between consistency and clarity, go for clarity." / "Avoid over-explaining with technical jargon — Use unambiguous language. Users shouldn't have to think, let alone guess about an action." / "Keep it short"
- 예시(en, g_img_1): ✕ `Unable to show this image because its server display period has expired.` → ✓ `Sorry, we couldn't find this image.`
- 예시(en, g_img_3, 빈 화면 성격): ✕ `Stories you uploaded previously will be stored here for your viewing.` → ✓ `Find your old stories here.`
- 예시(en, LINE_Voice_Re_EN_02): ✕ `Add friend` / `You must add this user as a friend to make voice calls with them. Add this user as a friend?` → ✓ `Add friend` / `To call this person, add them as a friend first. Add this person now?` (버튼은 둘 다 `Cancel` / `Add friend`)
- 이유(원문): "when choosing between consistency and clarity, go for clarity."

### L-10. LINE 로그인 버튼 레이블 (언어별 공식 문구)
- 출처: https://developers.line.biz/ja/docs/line-login/login-button/ (ko 경로는 내용이 비어 있어 ja 페이지의 언어표를 인용)
- 원문(ja): 「LINEログインボタンのテキストは、「LINEでログイン」にすることを推奨しています。」 / 独自テキストを使う場合 「改行を入れないこと。」「LINEでアプリにログインすることがユーザーにはっきりと伝わること。」
- 언어표(원문 그대로): en `Log in with LINE` / `Log in`, ja `LINEでログイン` / `ログイン`, **ko `LINE으로 로그인` / `로그인`**
- 관찰: 한국어 버튼은 "~하기"나 "~하세요"가 아니라 명사(동작 명사)로 끝난다. 영어 'Log in with LINE'을 "LINE으로 로그인하기"로 옮기지 않았다.

### LINE 문체에 대한 종합 관찰 (추론)
- 한국어 LINE Voice 예시 6개 가운데 4개가 좋은 예에서도 **합니다체**를 쓰고(L-1, L-4, L-5, L-6), 오류 화면 1개만 **해요체**를 쓴다(L-3). 따라서 LINE이 "해요체로 통일"한다는 근거는 없다. 핵심은 문체보다 내용이다. 원인을 넣고, 해결 방법을 넣고, 중의성을 없애고, 명사 나열 대신 문장을 쓴다.
- 대화상자 제목에 마침표를 찍는 예(L-1)와 찍지 않는 예(L-6)가 섞여 있어 마침표 규칙은 판단할 수 없다.

## 2. 네이버파이낸셜(네이버페이) — 「누구에게나 쉬운 금융을 위한 UX Writing 가이드」

- 출처: https://medium.com/naverfinancial/345b15686025 (네이버파이낸셜 공통디자인 이재혁, 2023-01-06). 본문은 r.jina.ai를 거쳐 받았다. medium은 직접 접근 시 Cloudflare로 차단된다. 표 이미지는 miro.medium.com에서 받아 직접 읽었다.
- 배경(원문): "금융 서비스는 다른 서비스들 보다 텍스트의 비중이 높고, 금융 용어와 한자어도 많이 쓰이다 보니 서비스가 더욱 어렵게 느껴지기 때문입니다."
- 구조(원문): "가이드는 '누구에게나 쉬운 금융'과 '신뢰 있는 네이버파이낸셜 서비스' 이 2가지의 가치 아래, 전체적인 톤앤매너를 위한 '원칙과 규칙'을 세우고 어려운 금융 용어와 한자어 등의 대체어를 정리한 '대체어 사전'을 만들었습니다." 원칙은 4가지인데 공개된 건 2가지("그중 2가지만 간략히 소개")이고, 규칙은 2가지다.

### N-1. 원칙 1 「누구나 쉽게 이해할 수 있도록 쓰기」
- 세부 가이드 ①(이미지 원문): "핵심적인 정보만 간결하게 작성해서 빠르고 직관적으로 이해할 수 있도록 하기"
  - 예문(기존) `새롭게 달라진 내 자산을 지금 만나보세요!` → 예문(개선) `내 자산이 새로워졌어요!`
  - 본문 설명(원문): "문장에서 불필요한 가지들을 다 제거하고 '전달하고자 하는 핵심 정보만 간결하게 작성하기' 처럼요."
  - 관찰: 광고 문구처럼 쓰인 "~을 지금 만나보세요"(영어 'Meet your new ~' 같은 투)를 주어와 서술어만 남긴 해요체 평서문으로 바꿨다.
- 세부 가이드 ②(이미지 원문, 아래가 흐리게 잘림): "어려운 금융용어는 쉽게 풀어서 가능한 모든 사람이 이해할 수 있도록 하기"
  - `이용한도` → `이용가능금액`
  - `송금` → `돈 보내기`
  - 세 번째 줄은 이미지에서 잘려 읽을 수 없음

### N-2. 원칙 2 「친절하게 설명하듯이 쓰기」
- 세부 가이드 ①(이미지 원문): "사용자가 해 야 할 일 보다는 얻을 수 있는 가치에 대해 부드럽게 제안하기" (띄어쓰기는 원문 그대로)
  - `지금 카드 연결하고 지출 관리해보세요!` → `카드 연결하면 자동으로 지출 관리 할 수 있어요`
  - `지금 동의하고 내 자산 조회하세요!` → `내 자산을 조회하려면 동의해주세요`
  - 이유(본문 원문): "우리가 무심코 사용자에게 바라는 것을 요청하거나 시키듯이 문장을 적는 경우가 많은데, 사용자가 어떤 과업을 완료하고 '얻게 되는 가치'를 중심으로 친절하게 제안하자는 가이드입니다."
  - 관찰: 개선안에 "~할 수 있어요"가 그대로 쓰였다. 따라서 이 출처는 "~할 수 있어요" 금지의 근거가 될 수 없다. 개선안에서는 느낌표와 "지금"이 빠졌다.
- 세부 가이드 ②(이미지 원문, 아래가 흐리게 잘림): "공급자 입장이 아닌 사용자 입장에서 작성하기"
  - `현재 연결된 계좌를 찾을 수 없습니다.` → `아직 계좌를 연결하지 않으셨나요?`
  - 둘째 줄은 흐리게 잘렸다. 판독되는 범위에서 기존 `카드 신청이 접수되었습니다`(추정) → 개선 `카드 신청을 완료했어요`(추정). **판독이 불완전하므로 인용할 때 주의**
  - 관찰: "~을 찾을 수 없습니다"(시스템 시점, 영어 'Cannot find ~' 투)를 사용자 상태를 묻는 말로 바꿨다. "접수되었습니다"(피동)를 "완료했어요"(능동, 해요체)로 바꾼 것으로 보인다.

### N-3. 규칙: 날짜 표기법 (이미지를 그대로 옮김)
- 규칙 문장(원문):
  - "년,월,일의 구분은 모두 마침표(.)로 구분합니다. (빗금(/) 등의 사용은 지양함)"
  - "월,일이 한자리인 경우 원칙적으로는 '0'을 붙이지 않습니다. (단, 내역 등에서는 width 영역을 통일하기 위해 모두 0을 붙여 표기함)"
  - "월,일,~기호 간 여백은 띄어쓰기를 권장하나 상황에 따라 붙여서 사용할 수 있습니다."
  - "연도 표기는 4자리 모두 표기를 원칙으로 합니다. (기간 표기 시, 같은 연도는 생략할 수 있습니다. -> 2021. 06. 01. ~ 06. 30.)"
- 표(원문 그대로):

| 구분 | 기본 | 요일 표기 | 기간 표기 | 시간과 함께 표기 |
|---|---|---|---|---|
| 월,일 숫자 – 문장 내에서 | `5. 31.` 까지 | `5. 31. (수)` 까지 | `5. 30. ~ 11. 5.` 동안 | `5. 30. 09:00`에 |
| 월,일 숫자 – 내역에서 | `05.31.` | `05.31.(수)` | `05.30. ~ 11.05.` | `05.30. 09:00` |
| 월,일 한글 | `5월 31일` | `5월 31일 (수)` | `5월 30일 ~ 11월 5일` | `5월 30일 오전 9시` |
| 년월일 숫자 – 문장 내에서 | `2021. 5. 31.` 까지 | `2021. 5. 31. (수)` 까지 | `2021. 5. 30. ~ 2021. 11. 5.` | `2021. 5. 30. 09:00` |
| 년월일 숫자 – 내역에서 | `2021. 05. 31.` | `2021. 05. 31. (수)` | `2021. 05. 30. ~ 2021. 11. 05.` | `2021. 05. 30. 09:00` |
| 년월일 한글 | `2021년 5월 31일` | `2021년 5월 31일 (수)` | `2021년 5월 30일 ~ 11월 5일` | `2021년 5월 30일 오전 9시` |

- **사용 금지 표기(원문):** `22/04/02` `05/03` `2021-5-31` `05.30` `22.05.03`
- 이유(본문 원문): "금융,결제 서비스에서 가장 많이 사용하는 '날짜' 표기법 인데요. 이 외에 시간, 금액, 부호, 띄어쓰기등의 표기법을 정리했습니다. 이 표기법들은 모두 국립국어원의 어문규정을 참고하여 작성되었습니다." 시간, 금액, 부호 표기 상세는 공개되지 않았다.
- 관찰: 금지 목록에 `05.30`(마지막 마침표 없음)과 `22.05.03`(연도 2자리)이 있다. 즉 **월·일 뒤에도 마침표를 찍고, 연도는 4자리로 쓴다.** 빗금(/)과 하이픈(-)은 쓰지 않는다. 한글 표기에서 시간은 `오전 9시`, 숫자 표기에서는 `09:00`이다.

### N-4. 대체어 사전 (이미지 일부를 그대로 옮김)
- 구분(원문): "완전히 기존 단어를 대체하는 '대체어'가 있는 반면, 상황에 따라 기존 단어를 써야하기도 하고 대체어를 써야 하기도 하는 '상황별 단어'가 있습니다. 또 어쩔수없이 기존 한자어를 유지해서 써야하는 '기존 유지'가 있고요."
- 표(원문):
  - `가입일` → `가입한 날` (대체어로 변경: "앞으로 대체어 사용")
  - `간략히` → `간단히` (대체어로 변경)
  - `개설` → 1단계 `개설` / 2단계 `만들기` (상황별 가이드: "1) 개설 : 유의사항이나 법령 등 '개설'이라는 단어가 고유명사로 사용되거나 다른 단어와 같이 쓰여 대체할 단어가 마땅하지 않을때 … 2) 만들기 : 문장등에서 풀어 쓰더라도 의미 전달에 어려움이 없을 때")
  - `개설일` → `개설한 날` (대체어로 변경, "* 참고 : 신청일 → 신청한 날")
  - `경우` → 1단계 `경우` / 2단계 `~하면 / ~되면 / ~때` (상황별 가이드: "1) 경우 : 특정 상황이 일어나는 조건이 있어 명시해야 할 때는 '경우' 유지" … 아래는 잘림)
- 표지 이미지에 '어려운 말'의 예로 강조된 단어(원문): `개설일`, `오류가 발생했습니다`의 `오류`/`발생`, `피보험자`, `이메일로 제공합니다`의 `제공`, `신규`, `다시 시도해주`의 `시도`, `이자 및 적립 … 기반 추정`, `본 서비스는`의 `본`, `전월`, `누적`, `개설이 제한되오니`의 `개설`/`제한`, `수령하지 않은 경우`의 `수령`
- 관찰(추론): "~일 → ~한 날", "경우 → ~하면/~때", "본 → (삭제)", "제공합니다/발생했습니다/시도" 같은 한자어 동사를 표적으로 삼는다. 영어 UI를 옮길 때 자주 나오는 "~의 경우", "본 서비스", "오류가 발생했습니다", "다시 시도해 주세요"가 모두 고칠 대상에 들어 있다.

## 3. 카카오 — 카카오디벨로퍼스 문서 작성 가이드 (주의: 개발자 문서용)

이 가이드는 **개발자 문서**에 쓰는 규칙이지 앱 UI 문구 규칙이 아니다. 그래서 문체 규칙(합니다체)은 앱 UI에 그대로 옮기면 안 된다. 다만 "명사형 제목과 동사형 제목을 언제 쓰나", "능동태", "수치 표기"는 위치별 규칙의 근거로 쓸 수 있다.
좋은 예/나쁜 예 판정은 HTML의 아이콘 스프라이트 위치로 확인했다. `0px -280px`가 "좋은 예입니다", `-20px -180px`가 "나쁜 예입니다"에 쓰인 아이콘이다.

### K-1. 제목의 품사 규칙: 개념/정보 묶음은 명사형, 사용자 행동은 동사형("~하기")
- 출처: https://developers.kakao.com/docs/ko/documentation-guideline/document-content-open
- 원문: "본문의 성격에 따라 동사 또는 명사형으로 제목 작성 규칙을 정하고 적용하면, 독자가 본문의 성격을 예측하는데 도움이 됩니다." / "명사형 제목은 개념, 정보를 설명하는 내용 또는 하위 제목들을 묶는 상위 제목에 사용합니다. 하위 내용 또는 제목을 대표하면서 가장 구체적인 단어를 사용합니다." / "동사형 제목은 사용자의 행동과 관련 내용의 문서 또는 본문의 제목으로 사용합니다."
- 예시(원문): 명사형 ✓ `사용자 정보 주의 사항, 이메일 사용 시 주의 사항` ✕ `기타 주의 사항` / 동사형 `카카오 API 호출, 앱 만들기`
- 같은 층위 규칙(원문): "같은 상위 제목을 갖는 하위 동일한 수준의 제목은 서로 같은 품사 규칙을 적용합니다." 예: `품사 규칙 적용하기` / `수준별 규칙 적용하기` / `목차 구성하기`
- 이유(원문): "독자가 본문의 성격을 예측하는데 도움이 됩니다."
- UI로 옮길 때(추론): 섹션 헤더와 탭은 명사형(`주의 사항`, `내 정보`)으로, 사용자가 할 일을 가리키는 항목이나 메뉴는 동사형 "~하기"(`앱 만들기`)로 쓴다. 같은 목록 안에서는 품사를 섞지 않는다. "기타"처럼 뭉뚱그린 말은 피한다.

### K-2. 제목을 본문에서 되풀이하지 말고, 중요한 내용을 첫 문장에 둔다(두괄식)
- 원문: "본문은 제목에 대한 내용을 설명하기 때문에, 대부분의 경우 제목의 문구는 생략해도 자연스럽게 읽힙니다."
- ✓ `본문은 제목에 대한 내용을 설명하기 때문에...` ✕ `제목을 그대로 반복하지 않아야 합니다. 왜냐하면 본문은 제목에 대한 내용을 설명하기 때문에...`
- 원문: "문장의 앞부분에 대상을 명시해서 주제를 강조하고 독자가 쉽게 이해할 수 있도록 작성합니다."
  - ✓ `카카오 로그인을 사용하면 사용자에 대한 인증과 인가를 간편하고 안전하게 처리할 수 있습니다.`
  - ✕ `사용자에 대한 인증과 인가를 간편하고 안전하게 처리하기 위해 카카오 로그인을 사용할 수 있습니다.`
- 관찰(추론): ✕ 예는 영어 'To ~, you can use X'의 어순을 그대로 옮긴 꼴이다. "~하기 위해 ~을 사용할 수 있습니다"는 번역투의 전형이다.

### K-3. 능동태로 쓴다. 수동태는 예외일 때만
- 원문: "능동태 문장으로 주어를 강조해 정보를 명확하고 간결하게 전달할 수 있도록 작성합니다. 수동태 문장은 주어가 생략되어 주체가 분명하지 않거나 불필요한 단어가 추가되어 복잡해질 수 있습니다."
  - ✓ `카카오 로그인은 카카오계정으로 다양한 서비스에 로그인할 수 있는 소셜 로그인 서비스입니다.`
  - ✕ `카카오 로그인은 다양한 서비스에서 카카오계정으로 로그인을 가능하게 하는 소셜 로그인 서비스로 제공됩니다.`
- 예외(원문): "대상을 행동보다 더 강조하거나, 주어를 알 필요가 없을 때에 한해 수동태를 사용합니다." ✓ `파일이 저장됩니다. 새 버전이 4월 23일 배포되었습니다.`
- 이유(원문): 위 인용대로 "주체가 분명하지 않거나 불필요한 단어가 추가되어 복잡해질 수 있습니다."
- 관찰: ✕ 예의 "~을 가능하게 하는", "~로 제공됩니다"는 영어 'enables', 'is provided as'를 직역한 꼴이다.

### K-4. 현재 시점으로 쓰고, 미래를 짐작하는 말을 쓰지 않는다
- 원문: "미래를 가정하는 표현(예: 곧, 아마, -한다면)을 사용하지 않습니다."
- 이유(원문): "현재 시점으로 작성해야 문서의 수명을 늘리고 유지 보수 비용을 줄일 수 있습니다."

### K-5. 수치와 범위는 숫자로 쓰고, "많은/대량" 같은 말과 "등/기타"를 쓰지 않는다
- 원문: "수치와 범위는 숫자와 국문 범위 표현(이상, 이하, 초과, 미만)을 사용해 작성합니다. 불확실한 표현(예: 많은, 적은, 대량, 소량)을 사용하지 않습니다."

| R11 | 섹션 헤더와 정보 묶음 제목은 **명사형**, 사용자 행동을 가리키는 항목은 **"~하기" 동사형**으로 쓴다. 같은 층위에서는 품사를 섞지 않는다. "기타" 같은 뭉뚱그린 말을 쓰지 않는다 | 카카오 K-1 (문서용) | ◐ |

| R13 | 로그인 같은 버튼 레이블은 짧은 명사·동작명사로 끝낸다: `카카오 로그인`, `LINE으로 로그인`, 축약형 `로그인`. "~하기"를 붙이지 않는다 | 카카오 K-7, LINE L-10 | ● |
| R14 | 날짜: 구분자는 마침표, 월·일 뒤에도 마침표, 연도는 4자리, 한 자리 월·일 앞에 0을 붙이지 않음(내역에서는 자리를 맞추려고 0을 붙임), 범위는 "~", 요일은 "(수)". 금지: `22/04/02` `05/03` `2021-5-31` `05.30` `22.05.03`. 한글 표기에서 시간은 `오전 9시` | 네이버파이낸셜 N-3 | ● |
| R15 | 숫자는 아라비아 숫자로, 4자리 이상은 3자리마다 쉼표. 수량과 범위는 "많은/대량" 대신 숫자와 "이상/이하/초과/미만"으로. "등/기타"로 생략하지 않는다 | 카카오 K-5·K-6 (문서용) | ◐ |
| R16 | 다른 사용자 이름에는 "님"을 붙인다(`Brown님이 LINE에 가입했습니다.`) | LINE L-4 (예시 1건) | ● (근거 얇음) |
| R17 | 느낌표는 경고처럼 위험한 순간에만 쓴다 | 카카오뱅크 분석 KB-2 | ○ |
| R18 | 한 화면에는 지금 할 행동만, 2문장 안팎으로 쓴다 | 카카오뱅크 분석 KB-1 | ○ |
| R19 | 일관성과 명확성이 부딪히면 명확성을 고른다 | LINE en "go for clarity" | ● |

**해요체와 합니다체에 대해:** 다섯 회사 가운데 앱 UI 문체를 명시한 공식 규칙은 없었다. 네이버파이낸셜은 개선안을 해요체로 쓰고, LINE은 합니다체를 주로 쓰면서 오류 화면에서만 해요체를 썼으며, 카카오는 개발자 문서에만 합니다체를 정했다. 그러니 "해요체가 업계 표준"이라는 주장은 이 조사로는 뒷받침되지 않는다. 해요체 통일의 근거는 토스 등 다른 출처에서 찾아야 한다(이 문서 범위 밖).
