## 1. 리디 (RIDI Design System – UI 텍스트 작성 가이드) [원문 확인]

출처: https://web.archive.org/web/20211022234521/https://ridi.design/writings/ (원래 주소 https://ridi.design/writings/ , © 2019 RIDI Corp.)
기본 방침 (원문): "국립국어원 등 공식기관의 권고사항을 기본으로 합니다. / 권고사항이 모두 허용해주는 경우 우리 내부 기준을 따릅니다. / 권고사항과 실제 용례가 크게 동떨어져 있다면 실제 용례를 따릅니다."

### 1-1. 능동문 쓰기 (피동 피하기)
- 원칙: "되도록 능동문으로 씁니다. 능동문은 사용자가 주체가 되기 때문에 이해하기 쉽습니다. 주체가 사용자가 아니라 시스템이라면 피동문을 쓸 수 있습니다."
- 예시: x `내 서재에서 최근 읽은 책 보이기` → O `내 서재에서 최근 읽은 책 보기`
- 이유: 원문 그대로 "사용자가 주체가 되기 때문에 이해하기 쉽습니다". 예외는 주체가 시스템일 때임.

### 1-2. 한자어 대신 우리말 ('할 수 있습니다' vs '사용 가능합니다')
- 원칙: "대체 가능하다면 되도록 한자어 대신 우리말을 사용합니다."
- 예시: `할 수 있습니다. → 친근함` / `사용 가능합니다. → 딱딱함`
- 이유: 친근함과 딱딱함의 차이. 리디는 '~할 수 있습니다'를 번역투로 보지 않고, 오히려 '가능합니다'를 대신할 권장 표현으로 씀. **'할 수 있다'를 일괄 금지하면 안 된다는 반대 근거임.**

### 1-3. 해요체를 쓰지 않음 (하십시오체가 기본) ※ 토스와 정반대
- 원칙: "해요체는 사용하지 않습니다. 해요체는 친근감을 주지만 신뢰가 떨어져 보일 수 있습니다. ('-주세요', '-보세요'에만 제한적으로 허용합니다.)"
- 예시: x `아이고, 검색 결과가 없네요. 키워드를 몇 개 빼보시면 어때요?` → O `검색 결과가 없습니다. 키워드를 다시 선택해보세요.`
- 톤 섹션: "객관적이지만 사려 깊은 어조로 씁니다. 기본적으로 '하십시오체'를 사용합니다. 진지하지만 딱딱하지 않은 톤으로 신뢰감을 줍니다."
  - x `결제를 취소하시겠어요?` → O `결제를 취소하시겠습니까?`
- 행동을 요청할 때: "'하십시오체' 대신에 '-주세요', '-보세요'를 사용합니다. '-하세요' 대신 부드럽게 행동을 요구하는 느낌을 주는 '-해주세요' 사용을 권장합니다."
  - x `키워드를 다시 선택하십시오.` / x `키워드를 다시 선택하세요.` → O `키워드를 다시 선택해주세요.` / O `키워드를 다시 선택해보세요.`

### 1-4. '-시-'는 행동을 요청하는 마지막 용언에만
- "당장 사용자에게 행동을 요구하는 경우, '-시-' 어미를 문장의 마지막 용언에만 사용합니다."
  - x `다운로드할 책을 선택하세요.` → O `다운로드할 책을 선택해주세요.`
- "직접 행동을 요청하는 경우가 아니면 '-시-'어미를 사용하지 않습니다."
  - x `공인인증서가 없으셔도 간편하게 이용하실 수 있습니다.` → O `공인인증서가 없어도 간편하게 이용할 수 있습니다.`
- 이유: 원문에 없음. (추론) 높임이 쌓이면 문장이 길어지고 굽실거리는 느낌이 든다. 영어 "you can"을 "~하실 수 있습니다"로 옮기는 번역투를 막는 효과도 있다.

### 1-5. 오류 문구에는 다음 행동, 긍정 어투
- "당황하거나 망설이지 않도록 다음에 취할 행동을 안내합니다."
  - x `오류가 발생했습니다.` → O `네트워크에 문제가 생겼습니다. 새로고침 버튼을 눌러주세요.`
- "부정적인 어투보다는 긍정적인 어투를 사용합니다."
  - x `잘못된 형식의 전화번호를 입력하셨습니다.` → O `올바른 전화번호를 입력해주세요.`
- 다이얼로그: "상태, 해결 방법을 제시해야 함"
  - x `폴더 생성에 실패하였습니다.` → O `네트워크 문제로 폴더 생성에 실패하였습니다.`

### 1-6. 전문용어 피하기, 간결하게, 지칭어 통일, 과장하지 않기
- x `오른쪽 토글 버튼을 눌러보세요.` → O `오른쪽 제외를 눌러보세요.`
- 간결: x `스마트폰, 태블릿에서는 공인인증서 없이 간편하게 이용할 수 있습니다.` → O `공인인증서 없이 간편하게 이용할 수 있습니다.` (이유: "짧은 글일수록 텍스트의 파악이 쉽고 직관성이 좋아집니다.")
- 일관성: x `…원하는 책장을 선택해주세요. 목록은 편집 가능합니다.` → O `…책장 목록은 편집 가능합니다.` (이유: "지칭어가 다르면 다른 요소로 오해할 수 있습니다.")
- 신뢰: x `리디북스는 모든 디바이스를 지원합니다.` → O `리디북스는 대부분의 기기를 지원합니다.`

### 1-7. 버튼 이름: '~하기'는 길이에 따라
- 원문: "레이블이 짧으면 '하기'를 붙이는 것이 자연스럽습니다. (예시: 가입하기) / 레이블이 길면 '하기'를 빼는 것이 자연스럽습니다. (예시: 무료체험 책 다운로드) / 공간이 좁으면 짧게 쓰는 것도 가능합니다. (예시: 선택)"
- 예시 쌍 (원문): `사용자 글꼴 설정하기 vs. 사용자 글꼴 설정` · `구매하기 vs. 구매` · `대여하기 vs. 대여` · `밝기 조절 제스처 사용하기 vs. 밝기 조절 제스처 사용` · `읽던 페이지 동기화하기 vs. 읽던 페이지 동기화` · `임시 데이터 삭제하기 vs. 임시 데이터 삭제`
- 다이얼로그 버튼: "예/아니오보다는 메시지와 호응하는 액션을 버튼 이름으로 써줍니다." x `책을 삭제하시겠습니까? (아니오/예)` → O `책을 삭제하시겠습니까? (취소/삭제)`
- 버튼 순서: "가장 오른쪽으로부터 주요 버튼을 나열합니다. Android, iOS 플랫폼의 정책을 따라가려는 목적입니다." x `삭제/취소` → O `취소/삭제`

### 1-8. 문장부호·숫자·날짜·단위
- 한 줄 메시지에도 마침표: "메시지가 한 줄이라도 마침표를 찍습니다. 영어권에서는 한 줄 텍스트인 경우 종종 생략하도록 권하지만, 한국어에서는 어색하게 느껴집니다." ← **영어 관습을 그대로 옮기지 말라는 명시적 근거**
- 날짜: "YYYY년 MM월 DD일 형식으로 적습니다. (예시: 2017년 05월 30일)" / "YYYY.MM.DD. 형식으로도 적습니다. (예시: 2017.05.30.)" / 시간과 함께: `2017.05.30. 15:30` / 요일: `2017년 05월 30일(금)`, `2017.05.30.(금)` ("소괄호는 앞말에 붙여 씁니다.")
- 시간: `오후 04시 03분 32초` / `오후 04:03:32` / `16:03:32` 모두 허용. "낮, 밤 표현을 쓰지 않고 오전, 오후로만 표기합니다."
- 물결표: "범위를 나타낼 때 사용합니다. 물결표는 앞말과 뒷말에 붙여 씁니다." 예: `점심시간: 12:50~14:00`
- 콜론: x `적립 리디포인트 : 13원` → O `적립 리디포인트: 13원`
- 숫자: "1,000자리마다 자릿점을 넣습니다. 예외: 연도, 백분율 등"
- 용량: x `1KiB, 1MiB, 1GiB` → O `1KB, 1MB, 1GB`
- 슬래시와 가운뎃점: "가운뎃점은 사용하지 않습니다. (예시: 경영/경제 도서)", 단 "메뉴, 버튼 등 UI에 한하여 가독성을 위해 가운뎃점을 허용합니다. (예시: 주문·배송)"
- 줄임표: 로딩 문구 끝에 씀. `책을 처음으로 열기 위한 준비 중입니다…` / PC에서 추가 입력이 필요한 메뉴 `내 파일 추가하기…`
- 외래어: x `어플리케이션, 컨텐츠` → O `애플리케이션, 콘텐츠`
- 대시·엠대시: 리디 가이드에 **규칙 없음.**

### 1-9. 기능 소개 문구의 톤은 따로
- "UI 텍스트보다는 좀 더 열의에 찬 어조로 씁니다. … 문장 마지막에 느낌표를 사용해도 좋습니다."
- x `매월 1일 자동충전 설정하시면 포인트가 두 배로 적립됩니다.` → O `매월 1일 자동충전 설정하고 더블포인트 적립 놓치지 마세요!`
- (추론) 수정 전 문장은 '~하시면 ~됩니다'(높임 + 피동) 구조이고, 수정 후에는 사용자가 주어인 능동 명령으로 바뀌었다.

## 2. 삼성 「Designing Words: 삼성 UX Writing 가이드」 (한국어) [원문 확인]

출처: https://design.samsung.com/kr/contents/ux-writing/ (2022-11-29, 글 제공: Samsung MX UX Team)

### 2-1. 사용자 친화는 반말·친근체가 아니다. 보안처럼 신뢰가 필요한 내용은 합니다체로
- 원문: "사용자 친화적인 UX Writing은 친구에게 대하듯 친근한 말투나 표현을 의미하는 것이 아니다. 사용자가 우리 제품과 친해지도록, 정확하고, 쉽게, 사실을 말하는 것이다."
- 예시 (원문): "휴대전화 보안에 대한 내용을 전달하는데 "이 기능을 사용하면 안전해요"라고 하면, 친근한 느낌을 주려다가 오히려 신뢰도가 낮게 느껴질 수도 있다. "보안 강화를 위한 기능입니다"와 같이 확고한 단어가 더 믿음을 실어준다."
  - 즉 `이 기능을 사용하면 안전해요` → `보안 강화를 위한 기능입니다`
- 원문: "친화적이라는 것은 적당한 선을 지키며, 너무 딱딱하지 않고, 너무 가깝지도 않은 적당함을 유지하는 것이다."
- 이미지 설명(alt): "“Let's go!”, “Hey!”, “Cool”, “Hurry up” 이라는 글자 위로 취소선이 그어져 있습니다." ← '파이팅', 'Let's go' 같은 과한 친근 표현을 거부함.
- **시사점:** 해요체와 합니다체의 선택은 신뢰가 필요한 정도에 달려 있음. 리디와 삼성은 신뢰를 이유로 합니다체를 쓰고, 토스는 일관성과 브랜딩을 이유로 해요체를 씀.

### 2-2. 할 수 없으면 솔직하게 '할 수 없습니다', 그리고 해결 방법
- 원문: "기능을 수행할 수 없다면 솔직하게 '할 수 없습니다'라고 전달해야 한다."
- 원문: "'네트워크에 연결할 수 없음' 이라는 문구를 읽고 부정적이라고 느낀 사람이 있다면, '할 수 없음'이라는 표현 때문은 아닐 것이다. 그것보다 구체적인 해결책을 제시해주지 못함에 대한 답답함이 더 큰 이유일 것이다. '할 수 없다'는 명확하게 전달하지만 이와 함께 해결 방법, 도움이 되는 방법을 알려주는 것이 중요하다."
- 참고: 삼성이 상태 문구 예로 든 `네트워크에 연결할 수 없음`은 **명사형(-음) 종결**임. 삼성 시스템 UI에서 상태와 제목을 '~음'으로 끝내는 관행이 있다는 간접 증거임. (추론, 공식 규칙 문서는 찾지 못함)

### 2-3. 과장·마케팅 수식어 빼기
- `스마트한 라이프를 위한 유용한 기능` 비판: "모든 기능에 '스마트'를 붙이면 아무것도 '스마트'하게 느껴지지 않는다."
- "UX Writing은 기능을 광고하기 위한 것이 아니다." / "과장 없이 솔직하게, 모든 사람이 쉽게 이해할 수 있어야 한다."

### 2-4. 전문용어 피하기
- 이미지 alt: "'Protocol', 'API', 'OCR'이라는 단어가 적힌 이미지" + 원문 "UX Writing은 이론서를 쓰는 작업이 아니다." Wi-Fi와 Bluetooth처럼 이미 일상어가 된 말은 허용함.

### 2-5. 첫 화면은 '시작하기'보다 '환영합니다!'
- 제목: "'시작하기' vs. '환영합니다!'". 이유 (원문): "딱딱한 안내보다는 반가운 환영의 메시지가 더 유쾌하게 느껴질 것이다. 식당에 들어갔는데 "어서 오세요"라는 인사말 없이, 다짜고짜 "주문하세요"라고 한다면…"

### 2-6. 되묻는 영어식 확인 문구는 이제 어색하다
- 원문: "PC에서는 "Are you sure you want to delete these files?"라고 썼다면 요즘 모바일 환경에서는 "Delete these files?"로 줄여 쓴다. … "Are you sure you want to"에 담긴 되묻는 뉘앙스는 요즘 사용자들이 부담스럽고 어색하게 느끼기 때문이 아닐까"
- (추론) 한국어로 옮기면 "정말 ~하시겠습니까?"보다 "~할까요?"나 "~하시겠습니까?" 한 번으로 줄이라는 근거가 됨.

### 2-7. 포용적 표현
- `Black list` 쓰지 않기. 성별 선택지에 `직접 입력`, `선택 안함` 넣기.

  - `She has a book under her arm.` 직역 `그녀는 책을 옆구리에 가지고 있다.` → 대안 `그녀는 책을 옆구리에 끼고 있다.`
  - 이유: "'have'는 '가지다'라는 식의 영어 구조가 그대로 전이되어 나타난 결과"
  - (추론) UI에서는 `n개의 알림을 가지고 있습니다` → `알림 n개`, `알림이 n개 있어요`
- **수동태**
  - `그 강도는 용감한 시민에 의하여 붙잡혔다.` → `…시민한테(에게) 붙잡혔다.`
  - `집회를 알리는 … 노력이 기울여졌다.` → `…노력을 기울였다.` / `…노력이 들어갔다.`
  - `결혼에 대한 결정들은 … 부모들에 의해 만들어진다.` → `혼인 결정을 자식 대신 부모가 했다.`
  - 이유 (원문): "영어에서는 타동사를 많이 쓰기 때문에 자연히 수동태 문장을 많이 쓴다. … 국어는 영어와 달리 자동사와 타동사의 구별이 엄격하지 않을 뿐더러, 타동사 다음에 반드시 목적어를 쓰지 않아도 된다. … 능동형으로 바꾸어 주면 훨씬 자연스러운 우리말 표현이 된다."
- **복수 '-들'**
  - `새로운 아이디어들과 방법들이` → `여러 가지 남다른 생각과 방법이`
  - 이유: "영어의 복수 접미사 '-s'를 무조건 국어의 '-들'로 바꾸는 식의 번역은 미세한 의미를 놓치거나 심하면 오역을 불러올 수도"
  - (추론) UI에서는 `파일들을 삭제할까요?` → `파일 3개를 삭제할까요?`
- **전치사구** ('~에 관하여', '~로부터', '~에 의해', '~을 통해'): 원문 "영어의 전치사구는 우리말 문장에 많은 영향을 끼쳤다."
  - `그 사람으로부터` → `그 사람에게서` / `긴장으로부터의 해방` → `긴장에서 벗어나는` / `이번 기회를 통해` → `이번 기회에` / `폭격에 의해` → `폭격으로`
  - `주점의 2층에서의 살림` → `주점의 2층에서 시작한 살림` ('-에서의' 같은 겹조사를 풀기)
- 결론 (원문): "흔히 나타나는 번역투 문장들은 다채로운 우리말 표현을 찾기 위한 노력을 조금만 더 기울이면 얼마든지 예방할 수 있는 것들이 대부분이다." 다만 "의식적으로 번역투를 사용하는 것과 … 무의식적으로 번역투를 만들어내는 것은 분명하게 구분"하라고 함.
- 관련 보도: EPN 기사에 따르면 국립국어원은 "번역 투 표현 자체가 어법적으로 틀린 표현은 아니라고" 하면서도 더 자연스러운 표현을 쓰기를 권함. (WebSearch 요약 경유. 기사 원문은 읽지 않음. https://www.edupolnews.com/news/articleView.html?idxno=13954)

### B. 해요체와 합니다체: 출처마다 정반대
- **합니다체 쪽:** 리디 "해요체는 친근감을 주지만 신뢰가 떨어져 보일 수 있습니다". 삼성 "'이 기능을 사용하면 안전해요' … 신뢰도가 낮게 느껴질 수도 … '보안 강화를 위한 기능입니다'". 강남언니도 예문이 모두 합니다체.

### C. '~할 수 있습니다/있어요'
- 금지할 근거는 **찾지 못함.** 오히려 리디는 `할 수 있습니다`를 `사용 가능합니다`의 대체어로 권하고, 삼성은 솔직한 `할 수 없습니다`를 권함.
- 문제가 되는 형태는 따로 있음.
  - (1) '-시-' 겹치기: `이용하실 수 있습니다` → `이용할 수 있습니다` (리디)
  - (2) 한자어 + 가능/불가: `상담이 가능하며 … 불가함을 알려드립니다` → `상담을 받을 수 있습니다 … 어려울 수 있습니다` (강남언니)
  - (3) 해결책 없는 불가 통보 (삼성, One UI)
- (추론) 영어 "You can ~"을 기계적으로 옮겨 모든 기능 설명을 '~할 수 있어요'로 끝내는 반복이 번역투로 느껴진다. 하지만 이것을 지적한 출처는 찾지 못했으니 '근거 없음'으로 표시해야 함.

### D. 피동, '~되었습니다'
- 능동 원칙: 리디, 요기요(능동성은 태도 원칙), breez, 국립국어원 새국어생활, delight412.
- **허용하는 예외:** 리디는 "주체가 시스템이라면 피동문을 쓸 수 있습니다". 삼성 One UI는 사용자를 탓하지 않으려고 `This file can't be deleted.`를 씀.
- 실제 교정 예: `세션이 만료되었습니다` → `로그인 시간이 지났습니다` (SKT), `내 서재에서 최근 읽은 책 보이기` → `…보기` (리디).
- 반대 사례: 강남언니는 `모든 여정이 완료되었습니다!`를 권장 예로 씀. '~되었습니다' 완료 문구가 모든 출처에서 금지된 것은 아님.

### E. '~에 대한', '~를 통해', '~로부터', '~에 의해', '-들', '가지다'
- 국립국어원 새국어생활(11장)과 delight412(12장)의 예문이 근거임. UI 출처에서 이 표현들을 직접 지적한 문구는 **찾지 못함.**

### F. 명사 나열과 한자어 명사화
- SKT `혜택이 상이합니다` → `혜택이 다릅니다`. 리디 `사용 가능합니다`보다 `할 수 있습니다`. 강남언니 `상담이 가능하며` → `상담을 받을 수 있습니다`. 토스의 '{명사}+{명사} 쓰지 않기'는 타 담당 범위라 WebSearch 요약으로만 확인함.

### G. 타이틀을 조건절·조사로 끝내기, 대시·엠대시
- **찾지 못함.** 관련 규칙은 리디의 콜론 붙여쓰기, 물결표 붙여쓰기, 슬래시와 가운뎃점, 줄임표, 한 줄 메시지에도 마침표 정도임.

### H. 숫자, 날짜, 단위
- 리디(1-8)와 강남언니(5장)를 볼 것. 두 곳 규칙이 달라서(오전/오후 표기 여부, 물결표와 하이픈) **서비스 안에서 하나로 정하는 것**만 공통임.

### I. 호칭

### J. 오류·빈 화면·완료 문구
- 오류는 원인과 다음 행동을 함께 씀 (리디, 강남언니, SKT, 삼성, One UI, 327roy, 센트비).

- 빈 화면은 막다른 길이 아니라 행동 버튼을 줌 (One UI, imjiminlee).
- 완료 문구는 확실하게. 느낌표 허용 (강남언니). 피드백을 빼면 신뢰도 빠짐 (327roy).
- 팝업은 꼭 필요할 때만, 나머지는 토스트 (One UI).

## 15. 이 리서치에서 뽑은 AI 규칙 후보 (모두 (추론): 위 출처를 조합한 제안)

1. 말투는 제품 단위로 하나만 정한다. 해요체든 합니다체든 섞지 않는다. 행동 요청은 `~해 주세요`. '-시-'는 행동을 요청하는 마지막 용언에만 쓴다. (리디, 요기요, 강남언니)
2. 사용자가 주어인 능동문으로 쓴다. 피동은 시스템이 주체이거나 사용자를 지목하지 않으려 할 때만 쓴다. (리디, One UI)
3. 행위자를 '~에 의해'로 쓰지 않는다. '~을 통해'는 '~로', '~에서'로 바꾸고, '~로부터'는 '~에게서', '~에서'로 바꾼다. '-들'과 '가지고 있다'를 피한다. (국립국어원 새국어생활)
4. 한자어 + 가능/불가/상이 대신 동사로 쓴다. `가능합니다`는 `할 수 있습니다`, `상이합니다`는 `다릅니다`로 쓴다. (리디, SKT, 강남언니)
5. 버튼은 동사형으로 쓴다. 짧으면 '~하기', 길면 '명사 + 동작명사'로 쓴다. 다이얼로그는 `취소 / [행동]` 순서로 두고 예/아니오는 쓰지 않는다. (리디, imjiminlee)
6. 불가 문구는 솔직하게 쓰고 해결책을 붙인다. 사용자 실수를 지적하는 문장을 쓰지 않는다. (삼성, SKT, 리디)
7. 한 줄 메시지에도 마침표를 찍는다. 영어 UI의 마침표 생략 관습을 옮기지 않는다. (리디)
8. 'Are you sure you want to…'를 직역한 '정말 ~하시겠습니까?'처럼 되묻는 문장은 줄인다. (삼성 Designing Words)
9. 영단어를 직역하지 말고 의미가 통하는 말로 쓴다 (`Peaceful` → `힐링`). 이미 익숙한 외래어는 허용한다. (삼성 뉴스룸)
10. AI 검수는 근거를 함께 제시하게 하고, 나쁜 예·고친 예·이유를 담은 사례 DB를 함께 넣는다. (라포랩스)
