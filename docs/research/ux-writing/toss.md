## 표기 규칙
- 「」 안의 글은 원문을 그대로 옮긴 것이다. 본문 텍스트는 curl로 받아 그대로 옮겼다.
- 예시 문구 대부분은 원문에서 **이미지**로만 제공된다. 이미지를 직접 열어 글자를 옮겼으므로 "(이미지 판독)"으로 표시한다. 줄바꿈 위치는 원문과 다를 수 있다.
- "(추론)"은 원문에 이유가 없어 내가 추론한 것이다. "(관찰)"은 원문 예시에서 일관되게 보이는 패턴이지만 규칙으로 명시되지는 않은 것이다.

## 0. 결론 요약: 번역투를 막는 데 바로 쓸 수 있는 토스 규칙

1. **모든 문구에 해요체를 쓴다.** 상황과 맥락을 가리지 않는다. 에러 메시지도 예외가 아니다. [AIT][SYS]
   - 「김토스님에게 1원을 보냅니다」 → 「김토스님에게 1원을 보낼게요」 (이미지 판독)
2. **능동형으로 쓴다.** 「됐어요」 대신 「했어요」, 「~었」은 뺀다. 수동형은 서비스 종료·기간 만료, 사용자에게 미치는 영향 안내, 사용자 안심 같은 정해진 상황에서만 쓴다. [AIT]
   - 「알림이 설정됐어요.」 → 「알림을 설정했어요.」
   - 「카드 연결을 완료했습니다.」, 「카드 연결 완료」 → 「카드를 연결했어요.」 [FEED]
3. **「{명사}+{명사}」 한자어 묶음을 쓰지 않는다.** 동사로 풀어 쓰거나, 최소한 「{명사}가 {명사}해서」 형태로 푼다. [AIT]
   - 「이자 환불을 받았어요」 → 「이자를 돌려받았어요」
   - 「잔액 부족으로 구매하지 못했어요」 → 「잔액이 부족해서 구매하지 못했어요」
4. **경어를 과하게 쓰지 않는다.** 「~시겠어요?」, 「~시나요?」, 「~께」, 「계시다」, 「여쭈다」를 쓰지 않는다. [AIT]
   - 「카드를 해지하시겠어요?」 → 「카드를 해지할까요?」
5. **부정형보다 긍정형으로 쓴다.** 「안 돼요」, 「없어요」 대신 「~하면 할 수 있어요」. 단, 정책상 쓸 수 없을 때처럼 정해진 예외가 있다. [AIT][ERR]
   - **주의:** 토스는 「~할 수 있어요」를 피하지 않는다. 오히려 권장 형태다. 「~해야 해요」라는 강요조 대신 「~할 수 있어요」라는 권유조를 쓴다고 명시한다. [ERR]
6. **명사형 종결 대신 문장형으로 쓴다.** 직접 근거는 세 가지다.
   - 초기 보이스 차트에 「어투: 문장형(명사형X), 청유형 문장(강요나 지시X)」라고 적었다. [1ST]
   - 완료 토스트 예시에서 「카드 연결 완료」를 Don't로 분류했다. [FEED]
   - 입력 오류 템플릿에서 「집 주소 입력이 필요합니다.」 대신 「집 주소를 확인해주세요.」를 쓴다. [SYS]
7. **버튼(CTA)은 「~하기」로 쓴다.** 다음 화면으로 넘기는 버튼은 「확인」, 「다음」이다. 두 버튼일 때 왼쪽 버튼에는 「취소」가 아니라 「닫기」나 「다음에」를 쓴다. [FEED][AIT]
8. **CTA는 누르면 무슨 일이 일어나는지를 말해야 한다.** 화면 가치를 반복하지 않는다. [AIT][8P]
   - 「4,000원 받고 금리 3%받는 통장 만들기」 → 「이동하기」
9. **잡초를 뽑는다.** 의미 없는 단어(문장 안), 의미 없는 문장(화면 안), 꼭 필요하지 않은 정보(화면 사이)를 없앤다. [8P]
10. **소리 내어 읽었을 때 자연스러워야 한다(Easy to speak).** 한자어, 문어체, 호흡이 너무 긴 문장을 피한다. 한 문장에는 메시지 하나만 담는다. [8P]

## 1. 앱인토스 개발자센터, UX 라이팅 가이드 [AIT]

URL: https://developers-apps-in-toss.toss.im/design/consumer-ux-guide.md (「### UX 라이팅」 섹션)

참고: 예전 경로 `…/design/ux-writing.html`은 지금 내용 없는 껍데기 페이지만 반환한다(직접 확인). 현재 내용은 consumer-ux-guide 안에 있다. 검색 요약 중 하나가 「한 줄로 말하기」라는 원칙을 언급했지만, 현행 문서에서는 **찾지 못했다**. 구버전 문서는 Wayback이 막혀 확인하지 못했다.

서문: 「본 가이드라인은 토스 앱의 보이스톤을 적용한 문구를 쓸 수 있도록 제공된 지침이에요.」

### 1-1. 해요체
- **원문:** 「제품 안의 모든 문구는 '해요체'로 써요. **일관성 있는 사용자 경험을 만들 수 있도록 상황, 맥락을 불문하고 모든 문구에 해요체를 적용해주세요.**」
- **예시 (이미지 판독):**
  - Don't: 「김토스님에게 / 1원을 보냅니다」
  - Do: 「김토스님에게 / 1원을 보낼게요」
- **이유(원문):** 일관성 있는 사용자 경험.
- 다른 토스 자료에 나온 근거:
  - [1ST] 「지표에는 크게 영향을 주지 않지만 브랜딩 적으로 임팩트 있는 해요체 적용」, 「지금 해요체가 토스의 톤을 구성하는 데에 가장 큰 역할을 하고 있지만, 제가 처음부터 말투를 고쳐야 한다고 설득했다면 아무도 공감하지 않았을 것 같거든요.」
  - [SYS] 에러 메시지도 예외가 아니다. 「"(우리 잘못인데)에러 메시지에도 해요체를 적용해야 할까요?"라는 물음에 지금은 당연하게 "네!"라고 답할 수 있지만, 긴 근거를 대며 설득해야 했을 때가 있었어요.」
- **해요체와 합니다체를 직접 비교한 이유는 토스 1차 자료에서 찾지 못했다.** 공개된 이유는 "일관성"과 "브랜딩 임팩트"뿐이다. 토스 쪽 근거 중 가장 가까운 것은 다음과 같다.
  - Casual 가치: 「금융이나 IT 업계에서 쓰던 어려운 용어와 딱딱한 뉘앙스를 쉽고 친절하게 고쳐 쓰고 있어요.」 [8P]
  - Easy to speak: 「실제로 소리 내어 읽었을 때 어색한 문장이 있어요. 한자어를 쓰거나, 문어체를 쓰거나…」 [8P]
  - (추론) 합니다체는 문어체·공지체로 들려서 Easy to speak, Casual 가치와 충돌한다고 판단했을 가능성이 높다.

### 1-2. 능동적 말하기
- **원문:** 「제품 안에서 최대한 **능동형 문장**을 써주세요. 수동형 문장은 특정 상황에서만 쓰는 게 좋아요.」
- **「됐어요 → 했어요」 (이미지 판독):** Don't 「알림이 설정됐어요.」 → Do 「알림을 설정했어요.」 (토스트)
- **「'~었' 빼기」 (이미지 판독):** Don't 「새 비밀번호로 / 바뀌었어요」 → Do 「새 비밀번호로 / 바꿨어요」
- **「동사 바꿔쓰기」 (이미지 판독):** Don't 「카드론 평균 금리가 / 13%로 높아졌어요」 → Do 「카드론 평균 금리가 / 13%로 올랐어요」
- **이유:** 원문에 따로 적혀 있지 않다. (추론) 행위 주체가 드러나고 문장이 짧아진다. 「-되다/-지다」 피동은 영어 수동태를 직역할 때 흔히 나오는 형태라서 피한다.
- **예외 (원문, 「수동형 문장을 써도 되는 경우」):**
  - 「수동형 문장이 더 명확 하고 간결한 커뮤니케이션을 만드는 때도 있어요.」
  - 「⚠️ 서비스 종료, 기간 만료」: 「주어(종료 서비스, 기간 등)를 강조할 수 있어요.」, 「'종료'와 '만료'의 뉘앙스를 정확히 전달할 수 있어요.」, 「**주기적으로 종료가 반복되는 제품에는 '`종료돼요`'를 쓰지 않아요.**」
  - 「⚠️ 사용자에게 미치는 영향을 알려줄 때 (주요 동사 : 연체, 해지, 적용 등)」: 「**인과 관계**를 명확하게 설명해요. '사용자의 행동에 의해 따라오는 결과'라는 점을 알려줄 수 있어요.」
  - 「⚠️ 사용자 안심」: 「'정보 수집 안내' 등의 민감한 상황에서 사용자를 안심하게 할 수 있어요.」
  - 「⚠️ `되어요` (X) → `돼요` (O)」: 「모바일 화면의 좁은 공간을 고려, '`되어요`'는 모두 '`돼요`'로 통일해서 써주세요.」

### 1-3. 긍정적 말하기
- **원문:** 「제품 안에서 부정적 커뮤니케이션을 최대한 줄이고 긍정형 문장을 써주세요. 예 : 안 돼요, 없어요 (X) → ~하면 할 수 있어요 (O)」
- **「없어요 → 있어요」 (이미지 판독):** Don't 「보호자가 허락하기 전에는 / 가입할 수 없어요」 → Do 「보호자가 허락해야 / 가입할 수 있어요」
- **「에러 메시지」 (이미지 판독, 다이얼로그):**
  - Don't
    - 제목: 「지금 버전에서는 쓸 수 없어요」
    - 설명: 「생체 인증을 쓰려면 앱을 최신 버전으로 업데이트 해주세요.」
    - 버튼: [닫기] [업데이트]
  - Do
    - 제목: 「앱을 업데이트해주세요」
    - 설명: 「생체 인증을 쓰려면 최신 버전이 필요해요.」
    - 버튼: [닫기] [업데이트]
- **원문 박스 「다이얼로그 왼쪽 버튼은 [닫기]」:** 「다이얼로그 왼쪽 버튼은 **닫기**로 문구를 통일해요. **취소**는 사용자가 하고 있는 작업이 취소된다고 오해할 수 있어 쓰지 않아요.」
- **「혜택을 받을 수 없을 때」 (이미지 판독, 라벨 「이탈 케이스」):**
  - Don't
    - 제목: 「모임지원금 없이 모임통장을 만들까요?」
    - 설명: 「지금 받지 않으면 모임지원금을 받을 수 없어요.」
    - 버튼: [닫기] [받지 않고 만들기]
  - Do
    - 제목: 「약관에 동의하면 모임지원금을 받을 수 있어요」
    - 버튼: [닫기] [동의하기]
- **「혜택 대상 안내」:**
  - 원문: 「**서비스는 쓸 수 있지만, 특정 혜택은 받을 수 없을 때 → 긍정형 문장** 사용자는 스캔하기 때문에 제품 전체를 쓸 수 없다고 이해하기 쉬워요.」
  - 예시 (이미지 판독)
    - Don't: 「계좌 개설 혜택은 받을 수 없어요 / (김토스)님은 한국투자증권 계좌를 만든 적이 있어요. 이번 혜택은 계좌를 처음 만드는 분에게만 드려요.」
    - Do: 「4.5% 금리 혜택만 받을 수 있어요 / (김토스)님은 한국투자증권 계좌를 만든 적이 있어요. (상품권, 주식) 혜택은 계좌를 처음 만드는 분에게만 드려요.」
- **이유(원문):** 사용자는 스캔하기 때문에 부정문 하나를 보고 제품 전체를 못 쓴다고 오해한다.
- **예외 (원문, 「부정형 문장을 써도 되는 경우」):**
  - 「사용자에게 명확하게 부정적인 내용을 알려줘야 할 때는 부정형 문장을 써도 좋아요.」
  - 「⚠️ 서비스를 정책 상 쓸 수 없을 때」: 「사용자에게 상황을 명확하게 인지시킬 수 있어요. 쓸 수 없는 이유를 함께 안내해주세요.」
  - 「⚠️ 일부 기능만 쓸 수 없을 때」: 「사용자가 어떤 기능을 쓸 수 없는지 명확하게 인지 할 수 있어요.」, 「사용자 선택의 결과를 명확하게 안내할 수 있어요.」
  - 「⚠️ 사용자 안심」: 「'정보 수집 안내' 등의 민감한 상황에서 사용자를 안심하게 할 수 있어요.」

### 1-4. 캐주얼한 경어
- **원문:** 「제품 안에서 '`~시겠어요?`', '`시나요?`', '`~께`' 같은 과도한 경어를 쓰지 않아요. 최대한 캐주얼하고 친근한 말투를 쓰는 게 좋아요.」
- **「동사에서 '~시' 빼기」 (이미지 판독):**
  - 「카드를 해지하시겠어요?」 → 「카드를 해지할까요?」
  - 「오늘 토스뱅크 시작하시는 분에게 / 5,000원을 드려요」 → 「오늘 토스뱅크를 시작하면 / 5,000원을 드려요」
- **「'계시다' → '있다'」 (이미지 판독):**
  - 「자동차를 가지고 계시나요?」 → 「자동차가 있나요?」
  - 「매달 보험료 / 얼마씩 내고 계시나요?」 → 「매달 보험료는 얼마인가요?」
- **「'여쭈다' → '확인하다', '묻다'」 (이미지 판독):** 「안전한 개통을 위해 / 몇 가지 다시 여쭤볼게요」 → 「…몇 가지 다시 확인할게요」
- **「'께' → '에게'」 (이미지 판독):** 「토스뱅크카드가 / 김토스님께 날아가고 있어요」 → 「…김토스님에게 날아가고 있어요」
- **「경어를 뺐을 때 어색한 경우」:**
  - 원문: 「사용자의 정보를 받는 질문에서 기계적으로 '`~시`'를 뺐을 때 문장이 어색할 수 있어요. **파악하고 싶은 정보를 '주어'로 써서 문장을 새롭게 써보세요.**」
  - 예시 (이미지 판독, 라벨 「정보 입력」)
    - 「어떤 목적으로 대출받으시나요?」 → 「대출 목적이 무엇인가요?」
    - 「어떤 이유로 신고하시나요?」 → 「신고 이유를 선택해주세요」
- **예외 (원문, 「경어를 써도 되는 경우」):** 「특정 상황에서 제한적으로 '`시나요?`, `셨나요?`' 의문형 어미를 쓸 수 있어요.」
  - 「⚠️ 사용자의 맥락을 활용해서 질문할 때」: 「'시나요?', '셨나요?' 형태의 경어를 활용해서 사용자의 당황스러움을 줄일 수 있어요.」
  - 「⚠️ 사용자의 상황을 추정할 때」: 「토스에 명확한 정보가 없어서 사용자에게 직접 판단하게 해야 할 때 '경어'로 정중하게 질문할 수 있어요.」
  - 「⚠️ 사용자의 선의가 필요할 때」: 「설문조사처럼 사용자의 선의를 기대해야 할 때 경어로 정중하게 질문해요.」
- **이유:** 「캐주얼하고 친근한 말투」라는 것 외에는 원문에 없다. (추론) 「~시겠어요?」는 영어 "Would you like to…?"를 옮길 때 기본으로 나오는 형태라서, 이 규칙이 번역투 제거에 직결된다.

### 1-5. 「{명사} + {명사}」 쓰지 않기
- **「한자어 풀어쓰기」:**
  - 원문: 「한자어 명사를 풀어서 동사 형태로 쓸 수 있어요.」
  - 예시 (이미지 판독)
    - 「이자 환불을 받았어요」 → 「이자를 돌려받았어요」
    - 「내일 카드값이 결제될 예정이에요」 → 「내일은 카드값 나가는 날이에요」
- **「한자어를 풀어쓰기 어려울 경우」:**
  - 원문: 「'`{명사}가 {명사}해서`' 형태로만 풀어줘도 더 캐주얼하게 쓸 수 있어요.」
  - 예시 (이미지 판독): 「잔액 부족으로 / 구매하지 못했어요」 → 「잔액이 부족해서 / 구매하지 못했어요」
- **이유:** 원문에 없다(「더 캐주얼하게」뿐). (추론) 명사 나열과 「~로 인해」, 「~될 예정」은 문어체·번역체 신호이고, Easy to speak 원칙과 맞지 않는다.

### 1-6. CTA 관련 다크패턴 (같은 문서의 「다크패턴 방지 정책」 5번)
- **원문:** 「**5. CTA 버튼만 보고 다음 행동을 예상할 수 없는 경우** 화면에서 이미 설명한 가치를 CTA에 똑같이 반복해서, 버튼을 눌렀을 때 어떤 화면이나 행동으로 이어지는지 알 수 없는 경우예요.」
- **이유(원문):** 「CTA는 사용자가 다음에 무엇을 하게 되는지 명확하게 알려주는 장치예요. 버튼 라벨이 모호하거나 설명만 반복하면 사용자는 클릭 결과를 예측하지 못해 불안함을 느껴요. 이 불안함은 클릭을 망설이게 만들고, 결국 전환율 저하로 이어질 수 있어요.」, 「또한 CTA 위에 과장되거나 중복된 보조 설명을 함께 노출하면 버튼의 역할이 흐려지고, 사용자에게 혼란을 줄 수 있어요.」
- **예시 (이미지 판독):**
  - 화면 제목: 「4,000원 받고 / 금리 3%받는 통장 만들어보세요」
  - 단계 안내: 「1 OO증권으로 이동한 후 / 2 개설하기 버튼을 눌러주세요 / 3 토스화면으로 돌아오면 끝」
  - 「예상하지 못한 것」 CTA: 「4,000원 받고 금리 3%받는 통장 만들기」
  - 「예상한 것」 CTA: 「이동하기」
- 이 문서는 이것을 「치명적인 사용성 오류로, 앱인토스 서비스로 출시할 수 없는 경우」로 분류한다.

### 1-7. 그래픽 가이드 속 문구 관련 항목
- **원문:** 「**5. 부정적이거나 호소하는 감정 표현은 피해주세요.** 사용자에게 불쾌감을 주거나 애원, 호소처럼 느껴지는 표현은 다크 패턴에 해당해요.」
- **예시 (이미지 판독, 이탈 방지 바텀시트):**
  - Don't
    - 제목: 「토스뱅크 통장 만들기, / 그렇게 간단하다던데...」 (울먹이는 이모지)
    - 설명: 「1분만에 통장 만들고 토스뱅크 혜택을 받으세요.」
    - 버튼: [나가기] [이어하기]
  - Do
    - 제목: 「지금 그만두면 연 2% 이자를 / 받을 수 없어요」 (압정 이모지)
    - 버튼: 같음
- 참고: 이 Do 예시는 [8P]의 Suggest over force 예시와 **긴장 관계**에 있다. [8P]에서는 「지금 그만두면 무제한 연 1% 이자를 받을 수 없어요」를 Don't로 보고 「다음에 할까요?」를 Do로 봤다(아래 2-6). 앱인토스 문서는 그래픽(감정 이모지)을 기준으로 한 예시라서, 사실을 진술하는 부정문은 허용한 것으로 보인다. (해석)

## 2. 토스의 8가지 라이팅 원칙 [8P]

URL: https://toss.tech/article/8-writing-principles-of-toss (김자유, 2022-11-15)

### 코어밸류 5개 (원문 요지 인용)
- **Clear 명확한:** 「메이커가 아닌 사용자가 이해할 수 있는 문장을 쓰기 위해 신경 쓰고 있어요.」
- **Concise 간결한:** 「사용자는 쏟아지는 정보를 모두 읽지 않아요. 원하는 정보를 빠르게 스캔할 수 있도록 꼭 필요한 내용만 필요한만큼 전달하는 것을 중요하게 생각해요.」
- **Casual 친근한:** 「금융이나 IT 업계에서 쓰던 어려운 용어와 딱딱한 뉘앙스를 쉽고 친절하게 고쳐 쓰고 있어요.」
- **Respect 존중하는:** 「당장의 이익을 조금 포기하더라도, 진실되고 사용자를 존중하는 커뮤니케이션을 해야 해요.」
- **Emotional 공감하는:** 「사용자가 느낄 감정에 공감하고 어떤 감동을 줄 수 있을지 고민해요.」

원칙과 가이드라인의 관계(원문): 「'의미 없는 단어를 없애자'고 제시하는 게 프린시플이라면, '[혹시]는 의미 없는 단어다'라고 결정하는 게 가이드라인이죠.」 → 잡초 단어의 예로 「혹시」가 명시돼 있다.

### 2-1. Predictable hint: 다음 화면을 예상할 수 있는 힌트가 있는가?
- **원문:** 「다음 화면을 예상할 수 있는 문장을 씁니다. … 종종 결과적으로 사용자가 얻을 수 있는 이익을 설명하느라, 당장 다음 화면에서 무슨 일이 일어날지 쓰지 않게 되는 경우가 있는데요. 사용자에게 밸류를 알려주는 것은 좋지만, 이것이 과하면 사용성을 해칠 때도 있으니 주의해야 해요.」
- **예시 (이미지 판독, 리스트 항목형 버튼):** Don't 「다른 곳에서 후불결제 하기」 → Do 「내가 쓰는 브랜드 신청하기」
- **이유(원문):** 「당장 다음 화면에서 무슨 일이 일어날지 알려주지 않았기 때문에 사용자는 불안할 수밖에 없어요.」

### 2-2. Weed cutting: 의미 없는 단어를 모두 제거했는가?
- **원문:** 「토스에서는 넣든 빼든 의사 전달에 영향이 없는 단어를 잡초라고 불러요. … 우리는 모바일 앱을 쓸 때 읽지 않아요. 스캔하죠.」, 「단, 단순히 글자 수를 줄이는 것보다 의미 없는 단어와 문장을 제거하는 것이 중요해요.」
- **예시 (이미지 판독, 리스트 라벨):** Don't 「앞으로 받을 배당금」 → Do 「받을 배당금」
- **원문 설명:** 「[앞으로]라는 단어는 이 문장에서 넣어도 그만, 빠져도 그만인 단어죠.」
- [FEED] 슬라이드 원문 (이미지 판독): 「유저들은 읽지 않습니다. 유저가 빠르게 원하는 정보를 스캔할 수 있도록 간결하게 씁니다. '-로도 충분한'문장을 지향합니다. 단, 단순히 글자 수를 줄이는 것보다 의미 없는 단어와 문장을 제거하는 것이 중요합니다. 한 문장 안에는 하나의 메시지만 담습니다.」
- [FEED] 잡초 예시 (이미지 판독, 알림 목록)
  - Don't: 「P2P 투자 제휴사인 8퍼센트와의 제휴 기간 종료에 따라 10월 23일(금)부터 'P2P 분산투자' 서비스가 종료됩니다. 1. 변경 내용 : … 2. 중단 기능 : … 3. 중단 일자 : 2020년 10월 23일(금) …」
  - Do: 「토스 P2P 분산투자 서비스가 10월 23일(금)부터 종료되어요. 자세한 내용은 알림을 눌러 확인해보세요.」
  - (주: 2021년 자료의 Do에 「종료되어요」가 있다. 이후 [AIT]가 「되어요→돼요」, 「종료돼요」 제한 규칙을 만든 것으로 보인다. 시기에 따라 규칙이 바뀌었다.)
- [1ST] 실제 피드백 원문 (이미지 판독): 「접속사(그리고)는 대부분 없어도 의미 전달에 무리가 없으므로 잡초인 것 같습니다」

### 2-3. Remove empty sentences: 의미 없는 문장을 모두 제거했는가?
- **원문:** 「한 화면 안에서 똑같은 말을 불필요하게 반복해서 쓰지 않는 거죠. 공간이 비어보인다거나, 뭔가 허전한 느낌이 든다는 이유로 의미 없는 문구를 쓰는 것도 피해야 하고요.」
- **예시 (이미지 판독):** 제목 「요즘 20대가 자주 쓰는 / 인기 서비스 6개」 아래의 부제 「발견한 인기 서비스를 써볼 수 있어요.」를 Don't로 보고, Do에서는 부제를 통째로 뺐다.
- **이유(원문):** 「그런 텅 빈 문장들은 사용자가 정말 중요한 정보에 집중하는 데에 방해가 돼요.」

### 2-4. Focus on key message: 정말 중요한 메시지만 전달하고 있는가?
- **원문:** 「사용자가 이미 알고 있는 정보는 과감하게 생략하고, 지금 꼭 확인해야 하는 내용만 추려서 전달하는 게 중요해요.」
- **예시 (이미지 판독, 바텀시트 「얼마를 갚을까요?」의 선택지):**
  - Don't
    - 「대출금의 원금을 갚습니다 / 원하는 금액만큼 대출금을 갚아요. 남은 대출금에 맞춰 월 상환금액이 자동으로 조절돼요.」
    - 「한 달치의 원금과 이자를 미리 갚을게요 / 다음 회차에 해당하는 원리금을 미리 낼 수 있어요.」
  - Do: 「금액 직접 입력하기」, 「다음 달 이자 미리 내기」
  - → 선택지 라벨을 설명 문장에서 「~하기」 동작 라벨로 바꿨다.
- **이유(원문):** 「모든 맥락을 설명해주는 것만 친절한 게 아니라, 때로는 정보를 생략해서 필요한 내용만 알려주는 것이 더 친절한 커뮤니케이션일 때가 있어요.」

### 2-5. Easy to speak: 이해하기 어려운 용어나 표현을 사용하지 않았는가?
- **원문:** 「일상에서 구두로 쓰이지 않는 단어나 금융, IT 업계에서만 쓰이는 전문 용어를 최대한 줄여…」, 「한 문장 안에는 가능하면 하나의 메시지만 담아서 짧은 호흡으로 한 번에 읽을 수 있도록 쓰고요.」, 「이 원칙의 핵심은 Easy to read가 아니라 speak이라는 점이에요. 눈으로 읽었을 때 어색하지 않더라도, 실제로 소리 내어 읽었을 때 어색한 문장이 있어요. 한자어를 쓰거나, 문어체를 쓰거나, 호흡이 지나치게 긴 문장들이죠.」
- **예시 (이미지 판독, 「프리마켓(Pre-market)이란?」 바텀시트 본문):**
  - Don't: 「미국 외 다른 나라 투자자들이 시차로 인한 거래의 불편함을 덜 수 있도록, 정규장 시작 전에 거래할 수 있는 시간을 프리마켓이라 해요. 토스증권 프리마켓을 통해 예약 주문이 가능하며, 실제 거래(체결)는 정규장에 이뤄져요.」
    - 원문 이미지에서 빨간색으로 표시된 부분: 「외」, 「로 인한」, 「시작 전에」, 「을 통해」, 「가능하며」
  - Do: 「정규장이 열리기 전에 거래할 수 있는 시간이에요. 시차로 주문하기 어려울 때 프리마켓에 예약을 걸어두면, 정규장이 열렸을 때 주문이 체결돼요.」
  - → 번역투·문어체 표지로 지목된 것: 「~로 인한」, 「~을 통해」, 「~이 가능하며」, 「외」, 「시작 전」(명사형). 번역투 규칙의 직접 근거로 쓸 수 있다.

### 2-6. Suggest over force: 특정 행동을 강요하거나 공포감을 주고 있지 않은가?
- **원문:** 「권유와 강요는 다릅니다. 스스로에게 선택권이 있다는 점을 느낄 수 있게, 사용자를 존중하는 문장을 써야 해요. … 불필요한 공포감을 조성해서 우리가 원하는 방향으로 유도하는 것도 피해야 해요.」
- **예시 (이미지 판독, 계좌 개설 중 이탈 바텀시트):**
  - Don't
    - 제목: 「지금 그만두면 무제한 연 1% / 이자를 받을 수 없어요」
    - 설명: 「토스증권 계좌는 한도 없이 이자를 매달 받을 수 있어요.」
    - 버튼: [이어서 하기] [나가기]
  - Do
    - 제목: 「다음에 할까요?」
    - 설명: 「토스증권 계좌는 한도 없이 연 1% 이자를 매달 받을 수 있어요.」
    - 버튼: [닫기] [나가기]
- **이유(원문):** 「'이 혜택을 놓치면 손해보시는 거예요'라는 뉘앙스를 함께 전달해서는 안되겠죠. 혜택을 그대로 전달하면서도 사용자가 온전히 스스로 선택할 수 있게 뉴트럴한 톤으로 문구를 바꿨어요.」
- [1ST] 실제 피드백 (이미지 판독): 「혜택을 권할 때는 강요가 아닌 청유/권유체를 사용하면 좋을 것 같습니다. '만나세요'는 강요하는 것처럼 들릴 수도 있을 것 같아요. e.g. 신규 고객 만나보세요」 → 「~하세요」보다 「~해보세요」.

### 2-7. Universal words: 모두가 이해할 수 있고 모두에게 무해한가?
- **원문:** 「연령, 교육 수준 및 종사 업계에 따라 이해도가 다른 용어를 지양하고…」, 「이 원칙은 보통 유행어, 은어, 밈 등을 쓸 때 많이 어겨지는데요.」
- **예시 (이미지 판독, 푸시):** Don't 「소리 지...르지 말고 박수 쳐! 🥳」 → Do 「지난밤 나스닥 4% 상승한 이유는?」 (본문은 둘 다 「김토스님을 위해 오늘 주식 시장을 요약해봤어요.」)
- **이유(원문):** 「특정 사용자들만 이해할 수 있는 유행어보다, 사실을 전달하는 것에 초점을 맞추면 모두가 이해할 수 있는 문구를 쓸 수 있어요.」

### 2-8. Find hidden emotion: 정보 전달을 넘어 사용자의 감정에 공감했는가?
- **예시 (이미지 판독, 대출 완납 푸시; [FEED]에도 같은 사례):**
  - Don't: 「신용 관리 / 김토스님, 대출 잔액이 달라졌어요. 잔액을 확인하세요.」
  - Do: 「드디어 대출 끝🎉 / 김토스님, 갚느라 고생 많으셨어요! 신용 점수가 달라졌는지 확인해보세요.」
- **결과(원문):** 「이 푸시를 받아 본 사용자 분들이 "힘이 됐다"라는 후기를 많이 남겨주셨었어요.」 [FEED] 「지표가 엄청 좋아졌어요」
- 참고: Do 문장에 「많으셨어요」라는 「-시-」 경어가 남아 있다. 감정에 공감하는 맥락에서는 경어를 허용한 실제 사례다. (관찰)

### 세 간결성 원칙의 범위 (원문)
「Weed cutting은 문장 안의 잡초를, Remove empty sentences는 화면 안의 잡초를, Focus on key message는 화면 간의 잡초를 없애는 것으로 좀 더 뾰족하게 정의해서 쓰고 있죠.」

### 초기 4원칙 (참고)
[1ST]와 [FEED] 슬라이드 (이미지 판독): 「Writing Principle / User-side Info / Weed Cutting / Easy to Speak / Keep Consistency」. 원칙은 「여러 시안을 A/B 테스트하면서 쌓인 위닝 전략을 모아 원칙으로 정의」한 것이다 [FEED].

## 3. 에러 메시지 6원칙 [ERR]과 에러 템플릿 [SYS]

URL: https://toss.tech/article/how-to-write-error-message , https://toss.tech/article/introducing-toss-error-message-system

- **기조(원문):** 「에러 메시지를 쓸 때 가장 중요한 가치는 Navigating, 즉 '사용자가 다음 단계로 무엇을 해야 할지 안내하고 있는가'예요.」
- 좋은 에러 메시지의 구성: 「지금 사용자가 어떤 상황에 처했는지(상황 설명) / 그것이 왜 발생했는지(이유) / 해결하려면 어떻게 해야하는지(해결책)」
- **도입부 예시 (본문 텍스트):** 「비밀번호를 틀렸어요 (X) / 김토스님의 정보가 아니에요 (O)」
- **토스 내부 Before 사례 (이미지 판독):** 「요청한 값이 부족하거나 올바르지 않습니다.」, 「Request failed with status code 500」, 「신용 정보를 찾을 수 없어요」

### 에러 템플릿 [SYS]

**서비스 점검 템플릿** (이미지 판독, 노션)
- 점검 시간이 정해져 있지 않은 경우
  - 토스트: 「지금은 {신한은행} 점검 시간이에요.」
  - 다이얼로그 제목: 「지금은 점검 시간이에요」
  - 다이얼로그 본문: 「{신한은행} 점검이 끝나는 대로 다시 쓸 수 있어요. 조금만 기다려주세요.」
- 점검 시간이 정해져 있는 경우
  - 토스트: 「지금은 {국민은행} 점검 시간이에요. (00:00-00:20)」
  - 다이얼로그 제목: 「지금은 점검 시간이에요」
  - 다이얼로그 본문: 「{농협은행} 점검이 끝나면 다시 시도해주세요. (00:00-00:20)」
- variation: 「지금은 점검 시간이에요 / {토스뱅크} 점검은 2분이면 끝나요. 조금만 기다려주세요.」

**인풋 오류 템플릿** (이미지 판독)
- 정보를 입력하지 않았을 때: 「{잘못 쓴 영역}을 확인해주세요.」
  - Don't: 「집 주소 입력이 필요합니다.」 → Do: 「집 주소를 확인해주세요.」
- 잘못된 정보나 오타를 입력했을 때: 「{잘못 쓴 영역}을 다시 확인해주세요.」
  - Don't: 「유효하지 않은 계좌번호 입니다.」 → Do: 「계좌번호를 다시 확인해주세요.」
  - Don't: 「은행명이 올바르지 않습니다.」 → Do: 「은행 이름을 다시 확인해주세요.」
  - → 번역투 직역 패턴인 「유효하지 않은 X입니다」(invalid X), 「X 입력이 필요합니다」(X is required)를 「X를 (다시) 확인해주세요」로 바꾼 직접 근거다.

**앱 업데이트 템플릿** (이미지 판독)
- 권유 업데이트, 기능을 짚어 줄 수 있는 경우: 「새로워진 {더치페이}를 써볼까요? / 앱을 업데이트하면 쓸 수 있어요. / 닫기 /업데이트」
- 권유 업데이트, 짚어 줄 기능이 없는 경우: 「최신 버전 앱을 써볼까요? / 앱을 업데이트하고 달라진 토스를 써보세요. / 닫기 /업데이트」
- 선택 업데이트(특정 기능만 못 쓰는 경우): 「앱을 업데이트해주세요 / {이 기능을} 쓰려면 최신 버전이 필요해요. / 닫기 /업데이트」
- 강제 업데이트(앱 전체를 못 쓰는 경우): 「앱을 업데이트해주세요 / 앱을 계속 쓰려면 최신 버전이 필요해요. / 업데이트」
- OS 업데이트: 「최신 버전 {안드로이드}가 필요해요 / 앱을 계속 쓰려면 최신 버전 {안드로이드}로 업데이트해주세요.」

**슬랙 사례** (이미지 판독)
- 중도 이탈: 「다음에 할까요? / 지금까지 수정한 내용은 저장되지 않아요. / 나가기 /닫기」
- 네트워크 토스트: 「(!) 인터넷 연결에 문제가 있어요. / 다시 시도」. 버튼에 대한 원문: 「버튼은 '다시 시도' 정도로 풀어서 써보면 좋을 것 같아요.」
- 리뷰 지적 원문: 「생체 인증에 실패했어요 → 에러 메시지 원인이 궁금해요. 잠시 후 다시 시도하면 해결되는 문제인가요?」, 「번호 변경에 실패하였습니다. → 해결책 / 다음 액션은 무엇인가요?」

## 4. TDS 컴포넌트에 심은 라이팅 규칙 [FEED]

- **원문:** 「예를 들면 바텀 시트라는 컴포넌트 내 타이틀은 한 줄로, CTA가 하나일 때 액션을 요청하는 문구는 '~하기'로, 다음 화면으로의 전환을 위한 문구는 '확인', '다음'으로, 두 개일 때 취소 버튼에는 '취소'가 아닌 '닫기'나 '다음에'를 쓰기로. 이런 내용을 문서화한 다음 컴포넌트 안에 심어두는 거죠.」
- **이유(원문):** 「디자이너분들이 가이드라인 문서를 따로 확인할 필요 없이, 툴 안에서 더 좋은 문구를 고를 수 있게 돼요.」
  - 「취소」 금지 이유는 [AIT]에 있다: 「취소는 사용자가 하고 있는 작업이 취소된다고 오해할 수 있어 쓰지 않아요.」
- [1ST] 실제 리뷰 피드백 (이미지 판독)
  - 「Confirmation 다이얼로그에서는 타이틀 최대 2줄, 권장 1~1.5줄로 설정하고 / 그 이상일 경우 디스크립션을 함께 사용하면 좋을 것 같은데…」
  - 「이전 화면에서 '받으세요'라고 컴하고, CTA도 받기로 컴하는데 타이틀도 받기로 컴하는 게 자연스럽지 않을까요? 강조하려고 명사형 쓰신 거라면 완료는 빼도 될 것 같습니다 '-' e.g. 20원 받았어요! or 20원 지급」
  - 「+숫자 뒤에 띄어쓰기도 붙여주세요」 (맥락상 숫자와 단위 사이 띄어쓰기에 관한 지적으로 보이나 정확한 대상은 불명확하다)
  - → 화면 사이에서 동사를 일관되게 쓴다(받으세요 → 받기 → 받았어요). 명사형을 쓸 거라면 「완료」 같은 잡초를 붙이지 않는다.
- **[TDS]와의 긴장:** TDS Mobile 개발 문서의 `ConfirmDialog`, `AsyncConfirmDialog` 등은 취소 버튼 기본값이 `@default '취소'`이고, 코드 예시에도 「취소」(예: `leftButton: '취소'`, 「결제를 취소할까요?」 / 「결제를 취소하면 되돌릴 수 없어요.」)가 나온다. 라이팅 규칙(「닫기」)과 코드 기본값이 서로 다르다. 생성 규칙에서는 라이팅 규칙을 따르는 게 맞다. (판단)

## 5. 초기 보이스 차트와 「문장형(명사형X)」 [1ST]

URL: https://toss.tech/article/1st_uxwriter

- **원문:**
  - 「제품 콘셉트: Reliable, 안심하고 돈을 맡길 수 있을 정도의 신뢰감」
  - 「라이팅 콘셉트: 신뢰를 주는 글쓰기(일관적인, 퀄리티 높은), 비문이 없고 일관적이며 퀄리티 높은 문장을 지향한다.」
  - 「어휘: 명료하지만 기계 같지 않다.」
  - 「어투: 문장형(명사형X), 청유형 문장(강요나 지시X)」
- **단서(원문):** 바로 뒤에 「만들고 보니 너무 뜬구름 잡는 이야기만 하는 것 같고 … 너무 추상적이고 … 큰 도움이 되지 않았죠.」라고 쓴다. 이후 실제 화면 사례를 모아 귀납적으로 원칙을 만들었다. 따라서 「문장형(명사형X)」은 **폐기된 초안 문서의 항목**이다. 그래도 지향점 자체는 [FEED]의 완료 토스트 예시(「카드 연결 완료」 Don't)와 [SYS]의 입력 오류 템플릿에서 유지된다.

### 완료 토스트 예시 [FEED] (이미지 판독, 같은 기사의 TDS 관련 이미지)
- Don't
  - 「카드 연결을 완료했습니다.」
  - 「카드 연결 완료」
  - 「카드 연결 끝! 이제 써볼까요? 😆」
- Do: 「카드를 연결했어요.」
- 캡션(원문): 「같은 메시지라도 디자이너마다 각자 다르게 썼었는데, 하나의 보이스 톤으로 바꿨어요.」
- **이유(원문):** 「사용자는 토스를 '하나의 서비스'로 받아들입니다. 비슷한 보이스 톤이 유지되어야 이용하는 입장에서도 혼선이 줄어들어요.」
- → 한 예시 안에 세 가지 실패 유형이 다 들어 있다. 합니다체 + 「완료했습니다」, 명사형 종결, 과한 감탄·이모지. 셋 다 「목적어 + 동사 과거형 해요체」 하나로 수렴한다.

## 8. 요청받은 쟁점별 정리

### 8-1. 위치별 명사형 종결 vs 문장형(해요체)
**원칙:** [AIT]는 「상황, 맥락을 불문하고 모든 문구에 해요체」라고 한다. 하지만 버튼이나 라벨처럼 "문장"이 아닌 요소에 대해 명시한 표는 **없다.** 아래는 원문 규칙과 예시에서 관찰한 것을 합친 것이다.

| 위치 | 토스 근거 | 형태 |
|---|---|---|
| 화면 제목·다이얼로그·바텀시트 제목 | [AIT][ERR][SYS] 예시 전부 | **해요체 문장**: 「앱을 업데이트해주세요」, 「전화로만 취소할 수 있어요」, 「지금은 점검 시간이에요」, 「얼마를 갚을까요?」, 「다음에 할까요?」. 질문형 「~할까요?」가 많다. (관찰) 제목에는 마침표를 찍지 않는다. |
| 본문·설명 | 같음 | 해요체 문장. 마침표를 찍는다. (관찰) |
| 토스트 | [AIT][FEED][SYS] | 해요체 문장 + 마침표: 「카드를 연결했어요.」, 「알림을 설정했어요.」, 「지금은 {신한은행} 점검 시간이에요.」 명사형 「카드 연결 완료」는 Don't다. [FEED] |
| 단일 CTA 버튼 | [FEED] 원문 | 「~하기」: 「이동하기」, 「동의하기」, 「전화하기」, 「문의하기」 |
| 화면 전환 버튼 | [FEED] 원문 | 「확인」, 「다음」 |
| 2버튼 중 왼쪽(보조) | [FEED][AIT] 원문 | 「닫기」(또는 「다음에」). 「취소」는 금지. |
| 2버튼 중 오른쪽(주) | [ERR][AIT] 예시 | 「~하기」나 짧은 명사: 「업데이트」, 「나가기」, 「이어하기」, 「다시 시도」. 2버튼에서는 명사형 「업데이트」도 쓴다. (관찰) |
| 리스트 항목·선택지 라벨 | [8P] 예시 | 「~하기」 동작형: 「내가 쓰는 브랜드 신청하기」, 「금액 직접 입력하기」, 「다음 달 이자 미리 내기」. 설명문(「대출금의 원금을 갚습니다」)은 Don't다. |
| 데이터 라벨(행 이름) | [8P] 예시 | 명사구: 「받은 배당금」, 「받을 배당금」, 「남은 대출금」, 「다음 납부일은 27일 뒤인 2021년 10월 5일이에요」(행 안의 설명은 해요체). 잡초만 뺀다. |
| 탭 | [8P] 이미지에 「내역」, 「찾기」 탭 | 명사 또는 짧은 동사 명사형 (관찰) |
| 섹션 헤더 | [8P] 이미지에 「자주 묻는 질문」 | 명사구 (관찰). 명시 규칙은 없다. |
| 입력 질문(제목) | [AIT] | 「대출 목적이 무엇인가요?」, 「신고 이유를 선택해주세요」. 정보를 주어로 세운 해요체 질문이나 요청. |
| 푸시 | [8P][S23] | 제목은 짧은 구나 질문(「지난밤 나스닥 4% 상승한 이유는?」, 「드디어 대출 끝🎉」), 본문은 해요체. |
| 플레이스홀더 | (2차) brunch kellypoly: 토스 송금 「얼마나 보낼까요?」, 「어디로 돈을 보낼까요?」 | 해요체 질문 (2차 관찰) |

### 8-2. 해요체 vs 합니다체
- 토스 공식 규칙: 해요체 하나로 통일한다. 에러 메시지도 포함한다. [AIT][SYS]
- 공식 이유: 일관성 [AIT], 브랜딩 임팩트 [1ST], 하나의 서비스처럼 느껴지게 하는 것 [FEED].
- 합니다체를 Don't로 고친 실제 예시
  - 「1원을 보냅니다」 → 「보낼게요」 [AIT]
  - 「카드 연결을 완료했습니다.」 → 「카드를 연결했어요.」 [FEED]
  - 「알 수 없는 종류의 신분증입니다.」 → 「기간이 만료된 신분증이에요」 [ERR]
  - 「신용 관리 서비스를 이용할 수 없는 연령입니다.」 → 「신용점수는 만 19세 이상부터 확인할 수 있어요.」 [ERR]
  - 「집 주소 입력이 필요합니다.」 → 「집 주소를 확인해주세요.」 [SYS]
- 합니다체를 피하는 이유를 직접 비교해 설명한 글은 **토스 1차 자료에서 찾지 못했다.**

### 8-3. 「~할 수 있어요」에 대해
- 토스는 「~할 수 있어요」를 **피하지 않고 권장한다.** 「~해야 해요라고 강요하는 듯한 말투보다, ~할 수 있어요라고 권유하는 말투」 [ERR], 「안 돼요, 없어요 (X) → ~하면 할 수 있어요 (O)」 [AIT].
- 다만 [8P] Remove empty sentences의 Don't 「발견한 인기 서비스를 써볼 수 있어요.」처럼, 정보 없이 빈자리를 채우는 「~할 수 있어요」 문장은 잡초로 본다.
- (추론) 금지어로 다룰 게 아니다. 판정 기준은 두 가지다. (a) 정보가 있는 권유·가능 안내인가, 아니면 빈 문장인가. (b) 같은 화면에서 반복되는가.

### 8-4. 「~되었습니다」, 「~됐어요」 수동·번역투
- 「됐어요 → 했어요」, 「'~었' 빼기」, 「되어요 → 돼요」 [AIT]
- 「세션이 만료되었습니다.」를 Don't로 들었다 [ERR]. 「번호 변경에 실패하였습니다.」를 리뷰에서 지적했다 [SYS].
- 문어체·번역투 표지로 빨간 표시를 한 것: 「~로 인한」, 「~을 통해」, 「~이 가능하며」 [8P 이미지]
- 수동형 예외 3종(종료·만료, 사용자에게 미치는 영향, 안심)이 있다. [AIT]

### 8-5. 조건절이나 조사로 끝나는 제목, 대시
- **토스 자료에서 명시 규칙은 찾지 못했다.**
- 관찰 1: 마케팅 배너 1행 「여행자 보험 준비 아직이라면」처럼 조건절로 끝나는 행은 2행 CTA와 짝을 이룰 때 쓴다. [MKT]
- 관찰 2: 다크패턴 Don't 예시 「토스뱅크 통장 만들기, / 그렇게 간단하다던데...」는 말줄임으로 끝나는 호소형 제목이라 금지됐다. [AIT 그래픽 5번]
- 대시(—, –) 사용 규칙은 찾지 못했다. 점검 시간 표기에서 「(00:00-00:20)」처럼 하이픈을 범위 표시로 쓴 예만 있다. [SYS]

### 8-6. 버튼 규칙
- 「~하기」, 「확인」·「다음」, 「닫기」·「다음에」 [FEED]. 「취소」 금지 [AIT].
- CTA는 다음 행동을 예측할 수 있게 쓰고, 화면 가치를 반복하지 않는다. 「4,000원 받고 금리 3%받는 통장 만들기」 → 「이동하기」 [AIT]
- 해결 행동을 버튼으로 준다: [확인] → [닫기][문의하기], [닫기][전화하기] [ERR]
- 「다시 시도」 [SYS]
- 이탈 확인 다이얼로그: 제목 「다음에 할까요?」 + [닫기][나가기] [8P], [SYS]의 「다음에 할까요? / 지금까지 수정한 내용은 저장되지 않아요. / 나가기 /닫기」
  - 버튼 순서는 자료마다 표기가 다르다. [8P] 이미지는 왼쪽 「닫기」, 오른쪽(빨강) 「나가기」다. [SYS] 슬랙 텍스트는 「/나가기 /닫기」 순서다.
- 확인과 취소를 짝지을 때 「예/아니오」를 쓰는 규칙은 토스 라이팅 자료에서 **찾지 못했다.** TDS 코드 예시에는 「아니오, 취소해주세요」가 한 번 나오는데, 라이팅 가이드가 아니라 개발 예제다.

### 8-7. 숫자·날짜·단위
- **토스 라이팅 원칙 문서에 숫자 표기 규칙은 없다(찾지 못함).**
- 예시에서 관찰한 표기
  - 금액: 「4,000원」, 「5,000원」, 「155,997원」, 「$2.78 (3,387원)」 → 천 단위 쉼표, 숫자와 「원」 붙여 씀
  - 퍼센트: 「연 1%」, 「13%」, 「4.5% 금리」 → 숫자와 붙여 씀
  - 날짜: 「2021년 10월 5일」, 「10월 23일(금)」
  - 나이: 「만 19세 이상부터」
  - 시간 범위: 「(00:00-00:20)」
  - 개수: 「문제 10개」, 「4개」, 「8칸」, 「1장」
  - 「3분 만에」, 「2분이면 끝나요」
- 원문 지적 「+숫자 뒤에 띄어쓰기도 붙여주세요」 [1ST]는 대상이 불명확하다. 문맥(「20원 받았어요!」)상 숫자+단위 뒤 띄어쓰기에 대한 지적일 가능성이 있다. (추론)
- [MKT] 원칙 5: 「8칸」, 「4개」처럼 구체적인 숫자를 쓰면 클릭과 전환이 올라간다. 「빈칸」, 「미션」처럼 막연한 말보다 낫다.

### 8-8. 호칭(님, 고객님)
- 예시 전반에 「김토스님」, 「(김토스)님」처럼 사용자 이름 + 님을 붙여 쓴다(님 앞 띄어쓰기 없음). [8P][ERR][AIT]
- 「~께」는 금지하고 「~에게」를 쓴다: 「김토스님께」 → 「김토스님에게」 [AIT]
- 3인칭 대상은 「분」을 쓴다: 「계좌를 처음 만드는 분에게만 드려요」 [AIT]
- **「고객님」 사용 여부에 대한 토스 규칙은 찾지 못했다.** 「고객센터」라는 단어 외에 예시 문구에서 「고객님」 호칭은 보이지 않았다. (관찰)
- 「-시-」는 원칙적으로 빼되 예외 3종이 있다. 공감 푸시(「고생 많으셨어요!」)에서 쓰인 실례가 있다. [AIT][8P]

### 8-9. 에러, 빈 상태, 완료 화면
- **에러:** 3장 전체 참고. 구조는 상황 + 이유 + 해결책이고, 해결 버튼을 준다. 원칙은 사용자 언어, 긍정형, 해요체다.
- **완료:** 「카드를 연결했어요.」 [FEED], 「알림을 설정했어요.」 [AIT], (2차) 토스 송금 완료 「~로 ~원을 보냈어요.」(brunch kellypoly), 요즘IT 2000의 「박승원 님에게 50,000원을 보냈어요.」(2차, 「송금이 완료되었습니다.」 대비)
  - (관찰) 완료 문구는 「목적어 + 했어요」로 쓰고, 「완료」라는 명사를 쓰지 않는다.
  - [1ST] 리뷰: 「강조하려고 명사형 쓰신 거라면 완료는 빼도 될 것 같습니다 … e.g. 20원 받았어요! or 20원 지급」
- **빈 상태(empty state):** 토스 라이팅 자료에서 빈 상태 전용 규칙이나 예시는 **찾지 못했다.** (추론) Remove empty sentences와 긍정적 말하기(「없어요」 → 「~하면 ~할 수 있어요」)를 적용하는 것이 맞아 보인다.
- **대기·진행 상태 (이미지 판독, [ERR] Before 사례 배경 화면):** 「토스뱅크 통장을 / 만들고 있어요」, 「김자유님의 신용점수를 / 꼼꼼히 확인 중이에요 / 지금 앱을 끄면 서류를 확인할 수 없어요. 잠시만 기다려주세요.」 → 진행형 「~하고 있어요」, 「~중이에요」

## 9. 찾지 못한 것 (조작하지 않음)
- 해요체와 합니다체를 직접 비교한 토스의 공식 이유
- 제목을 조건절이나 조사로 끝내는 것, 대시 사용에 대한 토스 규칙
- 숫자·날짜·단위 표기 규칙 문서
- 「고객님」 호칭에 대한 토스 규칙
- 빈 상태 전용 라이팅 규칙
- 확인·취소 쌍으로 「예/아니오」를 쓰는 규칙
- TDS 공식 문서 안의 컴포넌트별 라이팅 규칙 원문: 공개된 TDS Mobile 문서는 개발용 API 문서이고, 라이팅 규칙 섹션이 없다. [FEED] 인터뷰의 설명이 유일한 근거다.
- 구버전 앱인토스 `design/ux-writing.html` 원문, 그리고 검색 요약에서 언급된 「한 줄로 말하기」 원칙: 현재 페이지는 비어 있고, Wayback 접근이 막혀 확인하지 못했다.
- SLASH(개발 컨퍼런스)의 라이팅 관련 발표: 찾지 못했다.
- Simplicity 21 「어느 날 토스가 말을 걸기 시작했다」(김자유·구슬), Simplicity 25 「AI시대에 라이터로 살아남기」: 세션 페이지는 영상뿐이고 텍스트 녹취록을 찾지 못했다. [1ST]에 실린 Simplicity21 캡처 이미지만 확인했다.
- 미디엄 「토스 UX 라이터 인터뷰 - 좋은 문장을 넘어서 위대한 문장을 쓰는 일」: Cloudflare 차단으로 읽지 못했다.
