# design-harness 설계 계약

> 하네스톤 개인전(2026-09-30) 제출용 디자인 하네스. 이 문서는 스킬·스크립트·라이브러리·서브 에이전트가 모두 따르는 **단일 계약**이다. 여기 없는 규칙을 각자 만들지 않는다.
> 실행 절차는 `.claude/skills/design-harness/SKILL.md`, 사용자에게 보이는 말은 `references/ux-writing.md`.
> 이 문서의 대부분은 첫 리허설(2026-09-27~28) 중 사용자가 직접 지적한 것을 반영한 결과다(§13). 예시는 중립 예시 '동네 독서 모임'(모임장이 모임을 만들고 회원이 확인)으로 적는다.

## 1. 제약과 목표

- **사용자 개입 5회 이하, PRD 입력이 1회.** 실질 피드백 라운드는 최대 4회, 안전하게 3회로 설계한다.
- 첫 프롬프트는 PRD뿐. 이후 사용자는 AI의 질문에만 답한다.
- 결과물은 HTML 한 파일(`index.html`). 비개발자가 서비스를 이해할 만큼 충분한 화면 수.
- 평가는 UX가 아니라 **워크플로우·프롬프트 방식**. 소요 시간도 기록된다 → 속도가 곧 품질이다.
- 보는 사람은 **비디자이너**다. 구조·용어·화면 모두 "처음 보는 사람이 바로 이해하는가"가 기준이다.

## 2. 턴 구조

| 턴 | 사용자 | 하네스 |
|---|---|---|
| 1 | PRD 입력 | 질문 없이 PRD 분석 → `brief.md`·`screens.json`·`flow.json` → 서브 에이전트 병렬로 화면 조각 생성 → **초안 1 보드**(`out/board.html`)를 **자동으로 브라우저에 띄움** |
| 2 | 의견 1 (붙여넣기) | 분위기·글자·버튼 색 확정, 화면 추가/삭제, 번호 단위 수정 → **초안 2 보드** |
| 3 | 의견 2 | 번호 단위 국소 수정만 → **최종**(`out/index.html`) |
| 4·5 | 버퍼 | 사고 났을 때만 쓴다. 안 써도 된다 (3/5로 끝내는 게 목표) |

**예외 — 초안 전 확인(0~1회)**: 잘못 짐작하면 화면 대부분(절반 이상)을 다시 만들어야 하는 모호함이 PRD에 있을 때만(누가 주로 쓰는지 / 휴대폰인지 PC인지 / 핵심 기능이 무엇인지), 초안 전에 한 번 객관식 3개 이하로 묻는다. 그 외 선택은 전부 초안의 보드 안에서 받는다. 판단 기준과 묻는 방법은 SKILL.md 1.1-0.

원칙: **먼저 만들어 보여주고, 바꿀 것만 받는다.** 취향을 말로 묻지 않는다. 확정된 것은 다시 묻지 않는다. 사용자가 답하지 않은 항목은 추천값을 적용하고 `brief.md` 가정 로그에 남긴다.

## 3. 보드 — 사용자가 보고 의견을 남기는 화면

보드는 **로컬 HTML 파일 하나**(`out/board.html`)이고, `build.js --open`으로 사용자 브라우저에 **자동으로 띄운다**(사용자가 파일을 찾아 열게 하지 않는다). 배포·DB 없음.

### 3.1 두 탭: 사용 흐름 / 화면 디자인

이해와 의견을 분리한다. 흐름 화면에서 의견을 받으면 같은 화면이 여러 번 나와 헷갈린다.

**사용 흐름** (처음 열면 보이는 탭) — 서비스가 어떻게 흘러가는지 이해하는 곳. 빨간 번호·의견 창 없음.
1. **전체 흐름**: 흐름(=`flow.json`의 flow) 하나가 카드 한 장. 번호, **흐름 제목**('~하기'), 누구의 흐름인지(모임장 / 회원 / 모임장 → 회원), 상태 태그(처음 켰을 때 · 데이터 없을 때), **첫 화면 미리보기**, **화면 순서**("모임 홈 → 모임 만들기 → 일정 정하기").
2. **따라가 보기** (카드를 누르면): **지금 화면 + 다음 화면 두 장씩** 튜토리얼처럼. 지금 화면에서 **실제로 누르는 버튼에 파란 박스**, 거기서 다음 화면으로 화살표, 화살표 위에 "1단계 · '새 모임 만들기'를 누르면". ←/→로 한 칸씩, Esc 또는 "전체 흐름"으로 목록. 같은 화면이 여러 흐름에 나와도 그대로 다시 그린다.
   - **갈래**: 흐름 밖의 버튼(예: '후보 더하기', '회원 추가')이 여는 화면·창은 지금 화면 **아래 칸에 작게** 함께 보인다. 그 버튼에 **보라 점선 박스**, 아래로 보라 점선 화살표, 화살표 위에 "갈래 · '후보 더하기'를 누르면". 창이면 이름표에 "뜨는 창". 카드에는 "화면 4개 · 갈래 2개". ←/→는 본 흐름만 넘긴다(갈래는 누르면 화면 디자인으로).
3. 흐름 속 화면을 누르면 **화면 디자인** 탭의 그 화면으로 간다.

**화면 디자인** — 화면마다 한 번씩, 크게 보고 의견을 남기는 곳.
- 왼쪽 **화면 목록**: 역할별로 묶고(모임장 / 회원 / 함께 쓰는 화면), 흐름에 나오는 순서. 상태 태그, 의견을 남긴 화면에는 주황 점. 맨 위 **"전체"**: 질문(`board.ask`) · 더 있었으면 하는 것 · 지금까지 남긴 의견.
- 가운데: 고른 화면 한 장(폭에 맞춤, 길면 세로 스크롤).
- 오른쪽: 화면 정보 · **이 화면이 나오는 흐름**(누르면 사용 흐름에서 그 자리로) · 고른 곳 · 이 화면에 남긴 의견 · 화면 빼기와 메모 · 이전/다음 화면. ↑/↓·←/→로 화면 넘기기.

### 3.2 의견 남기기 — 화면 아무 곳이나 골라서

**의견 단위를 미리 정하지 않는다.** 사용자가 화면에서 고치고 싶은 곳을 직접 고른다(Figma 코멘트처럼).
- 화면 위에 마우스를 올리면 그 요소에 파란 테두리와 이름표("버튼 '새 모임 만들기'", "글자 '안녕하세요, 지현 님'", "아이콘", "부분 '1 책 고르기'")가 뜬다. 이름표의 종류 말은 버튼 · 입력칸 · 선택 항목 · 메뉴 · 링크 · 이미지 · 제목 · 표시 · 사람 표시 · 메뉴 묶음 · 맨 위 줄 · 목록 한 줄 · 글자 · 부분 · 화면 전체.
- 누르면 오른쪽에 **"고른 곳"**: 이름 + "'<항목 label>' 안에 있어요" + [더 넓게 고르기](감싸는 묶음으로) · [선택 취소].
- **바꿔주세요 / 빼주세요** 중 하나를 고르면 의견이 생기고 화면 위에 **핀 번호**(1, 2, 3… 보드 전체에서 이어짐, 바꿔 = 주황, 빼기 = 회색)가 붙는다. "바꿔주세요"는 **예시 칩**(글자 더 크게 · 더 단순하게 · 위로 올려주세요 · 잘 안 보여요 · 색을 바꿔주세요 · 다른 모양으로 · 버튼을 더 크게 · 순서를 바꿔주세요) + 메모. 핀을 누르면 다시 고치거나 지운다.
- **아이콘을 고르면 "다른 아이콘으로 바꾸기"**: 검색칸 + 허용된 Lucide 아이콘 목록(core allowlist + 프로젝트 icons.json, 보드 빌드에 전부 실린다). 고르면 화면 속 아이콘이 바로 바뀌고 핀이 붙는다. 복사 글: `화면 S · 아이콘 'plane' 바꿔: 아이콘 plane → luggage [경로]`.
- 화면 안 버튼·링크·입력칸은 실제로 동작하지 않는다(누르면 고르기만).
- 미리 정한 항목(`regions`)은 사용자 화면에 번호로 보이지 않는다. 내부에서 **위치 경로의 기준점**과 "'…' 안에 있어요" 설명으로 쓴다.

### 3.3 상단바

- 한 줄, 높이 56px, 모든 컨트롤 32px. 왼쪽부터: 제목 + "초안 n" / **[사용 흐름][화면 디자인] 탭** / **화면 느낌** 버튼(지금 값 요약: "따뜻한 크림 · 크게 · 테라코타") / (사용 흐름에서 따라가 볼 때만) 화살표 · 확대 도구 / **의견 보내기 · n개**.
- **화면 느낌** 창: 분위기 카드 3개(배경·버튼 색 미리보기 + 이름 + 이유 + 추천) · 글자 크기 · 버튼 색 조각 5개(고른 분위기에 어울리는 색, 첫 번째 추천). 잠긴 항목은 "확정: …" 글자로.
- 추천값에는 작은 **"추천"** 글자(점·색 기호만으로 표시하지 않는다). 마우스를 올리면 설명.
- 분위기·글자·버튼 색을 바꾸면 **모든 화면이 즉시 다시 칠해진다** — 화면 하나가 아니라 서비스 전체를 비교하게 한다.

### 3.4 의견 보내기

- 누르면 바로 복사하지 않고 **"이렇게 전달돼요"** 창을 먼저 연다: "아래 n가지를 전달해요. 나머지는 모두 추천대로 진행해요." + 사람이 읽는 요약(화면 느낌 / 다르게 고른 질문 / 고쳐 달라고 한 곳 / 화면 전체에 대한 의견 / 더 있었으면 하는 것) + 접힌 "실제로 복사되는 글 보기".
- [복사하기] → 클립보드 → "복사했어요. 채팅창에 붙여넣어 주세요." 사용자가 채팅에 붙여넣는 것이 개입 1회다.
- **복사되는 글의 형식은 고정**이다(`references/answer-parsing.md`가 읽는다). 화면 문구를 바꿔도 이 형식은 바꾸지 않는다. 고른 곳 의견은 `화면 <id> · <이름표> 바꿔|빼기 [<위치 경로>]` — 위치 경로는 가장 가까운 `data-region`(`@key`)부터 `태그:순번`:

```
테마 B · 글자 크게 · 강조 차분
확인: member-start=전체 모임 일정
화면 1 · 버튼 '새 모임 만들기' 바꿔: 버튼을 더 크게 [@start-club > div > button]
화면 1 · 부분 '3 출석 확인하기' 빼기 [@how-it-works > div:3]
화면 3 빼기
화면 5 메모: …
추가: 짐 체크리스트 화면
메모: 회원 화면은 버튼을 더 크게
(나머지는 추천대로)
```

### 3.5 번호

- **화면 번호는 1, 2, 3 …으로 이어진다**(사용자가 만나는 순서 = screens.json 순서). 사용자가 "화면 5"라고 부르는 번호이고, 최종본 `screens/05-…html`의 번호와 같다. 원문자·코드·접두어 없음.
- 항목 번호는 내부용이라 **101부터 따로** 센다(화면 번호와 섞여 1, 5, 10처럼 띄엄띄엄 되지 않게 — 리허설 2에서 사용자 지적).
- 라운드가 바뀌어도 번호는 바뀌지 않는다. 새 화면·항목은 다음 번호를 이어서 받고, 삭제된 번호는 재사용하지 않는다(`scripts/ids.js`). 최종본 NN은 번호 순서로 01부터 다시 이어 붙인다.

## 4. 최종 산출물 — Figma에서 넘겨받은 것처럼

평가 기준(HARNESSTON.md: 결과물은 HTML, 여러 파일이면 `index.html`에서 진입, **비개발자가 서비스를 이해할 만큼 충분한 페이지 수**)에 맞춰, 최종본은 **화면마다 독립 HTML 완성본 + 그 전체를 모아 보는 입구**다.

```
out/  (→ submissions/<id>/ 로 그대로 복사)
├── index.html              입구: [화면 전체] Figma 캔버스처럼 모든 화면을 **실제 크기 대지**로 나열(역할별 구역, 한 줄 4장, 번호·이름·상태 태그)
│                                  ⌘/Ctrl+휠·−/+ 확대·축소, 휠·드래그 이동, '전체 보기'. 대지를 누르면 그 화면으로 크게 다가간다
│                           [사용 흐름] 흐름 카드 → 두 장씩 넘겨 보기(←/→, 이전·다음), 화면을 누르면 화면 전체 캔버스의 그 화면으로
│                           ※ index.html은 다른 파일로 가는 링크를 두지 않는다 — macOS에서 Chrome에 폴더 접근 권한이 없으면
│                             처음 연 파일만 열리고 다른 파일로 가면 '파일 액세스 거부됨'이 난다
└── screens/NN-slug.html    화면별 독립 완성본 (화면 번호 순서). 보드 장치 없이 실제 화면만, 브라우저 전체 크기.
                            흐름·갈래의 버튼(data-trigger)과 **같은 글자의 다른 버튼**, **왼쪽 메뉴(roles[].nav)** 를 누르면 해당 화면 페이지로 이동(마우스를 올리면 테두리).
                            되돌아가는 버튼(data-back)은 이전 화면으로(뜨는 창이면 뒷 화면으로), 그 자리에서 바뀌는 버튼(data-stay="…")은 짧은 안내 문구를 띄운다.
                            뜨는 창 화면은 뒷 화면 위에 창이 뜬 모습. 오른쪽 아래 이동 막대: 전체 화면 · 이전 · n/N · 다음.
```

- 확정된 분위기·글자 크기·버튼 색이 적용된 **실제 HTML UI**다. 의견 창·번호·핀 없음.
- 만드는 명령은 `build.js --mode final` 하나(입구와 화면별 페이지를 같이 만든다).

## 6. 데이터 형식

### 6.1 `screens.json`

```json
{
  "project": "book-club",
  "title": "동네 독서 모임",
  "platform": "web",
  "round": 1,
  "theme": "warm",
  "toggles": { "type": "normal", "swatch": "terracotta" },
  "looks": [ { "id": "warm", "name": "따뜻한 종이", "why": "책 모임다운 포근한 느낌이에요", "mode": "light", "bg": "#FBF8F3", "ink": "#1F1B16", "shape": "round",
               "swatches": [ { "id": "terracotta", "name": "테라코타", "hex": "#D9562B" }, "… 5개" ] }, "… 3개" ],
  "roles": [
    { "key": "host", "label": "모임장", "nav": [ { "slug": "host-home", "label": "모임", "icon": "house" } ] },

    {
      "id": 1, "slug": "host-home-empty", "name": "모임 홈 (처음)", "role": "host",
      "state": "first-run", "variantOf": "host-home",
      "purpose": "아직 모임이 없을 때 새 모임을 만들게 한다",
      "pattern": "dashboard", "file": "screens/host-home-empty.html",
      "regions": [
        { "id": 101, "key": "start-club", "label": "새 모임 만들기", "why": "여기서 첫 모임을 만들어요", "prd": "§4-1" }
      ]
    },
    {
      "id": 4, "slug": "member-add", "name": "회원 추가 창", "role": "host", "overlayOf": "club-members",
      "purpose": "초대할 회원의 이름과 연락처를 적는다", "pattern": "form", "file": "screens/member-add.html",
      "regions": [ { "id": 112, "key": "member-form", "label": "회원 정보 적기", "why": "이름과 연락처만 적으면 초대 문자가 가요" } ]

```

- `id`: 화면은 1부터, 항목은 101부터 **따로** 센다(§3.5). 비어 있으면 `ids.js`가 채운다. screens.json의 화면 순서 = 사용자가 만나는 순서(역할별 처음 시작 → 핵심 작업 순), 뜨는 창은 그 뒷 화면 바로 다음.
- `slug`: 파일명·flow 참조용. 케밥케이스 영문.
- `state`(선택): `first-run`(처음 켰을 때) · `empty`(데이터 없을 때) · `input`(입력할 때). 캔버스가 태그로 보여준다. `variantOf`는 빈 상태 변형의 원래 화면.
- `overlayOf`(선택): **뜨는 창 화면**(대화상자·오른쪽 패널). 조각에는 창(`.modal-backdrop`)만 쓰고, 뒷 화면은 `build.js`가 `overlayOf` 화면을 깔아 합친다(뒷 화면의 누를 곳·항목 표시는 지운다). 이름은 '~ 창'. 이 창을 여는 버튼이 `flow.json` 흐름이나 갈래에 반드시 있다. 한 실행에 6개 이하.
- `roles[].nav`: 모든 화면의 사이드바가 그대로 복사하는 메뉴. 화면 간 일관성이 여기서 정해진다.
- `regions[].key`: 조각의 `data-region`과 1:1. `label`·`why`는 **번호를 누르면 그대로 보이는 글**(ux-writing §2), `prd`는 내부 근거.
- `theme`/`toggles`: 1턴에는 추천값, 2턴 의견으로 확정 후 `board.locked`.
- `board.focus`: 지난 라운드에 고친 화면 slug — "고친 화면" 태그.

### 6.2 `flow.json`

```json
{
  "flows": [
    {
      "key": "first-club", "name": "첫 모임 만들기", "role": "host",
      "steps": [
        { "from": "host-home-empty", "region": "start-club", "trigger": "new-club", "action": "'새 모임 만들기'를 누르면", "to": "club-create" },
        { "from": "club-create", "region": "create", "trigger": "create-club", "action": "'모임 만들기'를 누르면", "to": "schedule-empty" }
      ]
    }
  ]
}
```

- **흐름 하나 = 끊기지 않는 한 줄**: `steps[i].from == steps[i-1].to`. 중간에 홈으로 돌아가 다른 걸 누르면 별도 흐름으로 쪼갠다.
- `name` = 짧은 '~하기' 작업 이름(ux-writing §1). 누가 하는지는 `role`과 화면의 역할이 태그로 보여준다.
- `from`/`to`는 slug, `region`은 from 화면의 항목 key.
- `trigger`는 **실제로 누르는 버튼**의 key. 조각의 그 요소에 `data-trigger`(화면 안에서 유일)가 있어야 하고, `region` 안에 있어야 한다.
- **항목(region)과 트리거(trigger)는 역할이 다르다.** 항목 = 의견 단위(빨간 번호). 트리거 = 흐름 단위(파란 박스, 다음 화면으로 화살표가 나간다).
- `action` = 버튼 문구를 따옴표 안에 그대로 넣은 한 문장(ux-writing §4).

**갈래 `branches`** — 흐름 밖의 버튼이 여는 화면·창. 흐름은 한 줄로 두고, 갈라지는 길은 여기에 적는다(리허설 2: "후보 더하기를 누르면 어떤 화면이 나오는지 모르겠다").

```json
{
  "flows": [ "…" ],
  "branches": [
    { "from": "club-members", "region": "member-list", "trigger": "add-member", "action": "'회원 추가'를 누르면", "to": "member-add" }
  ]
}
```

- 형식은 step과 같다(from·region·trigger·action·to). 흐름 단계에 이미 있는 버튼은 갈래에 넣지 않는다.
- **글자가 있는 버튼(`.btn`)은 누르면 어떻게 되는지 셋 중 하나를 반드시 가진다** (lint FAIL):
  1. 다른 화면·창이 열린다 → `data-trigger` + 흐름 단계 또는 갈래
  2. 이전 화면으로 돌아간다(취소·닫기·'~로' 뒤로가기) → `data-back`
  3. 그 자리에서 바뀐다(삭제·필터·다시 알리기·복사) → `data-stay="바뀐 뒤 안내 문구"` (예: `data-stay="알림을 다시 보냈어요"`)
- 아이콘만 있는 버튼(`.btn-icon`)과 왼쪽 메뉴(`.nav-item`)는 제외.
- **갈래로 만들 화면을 고르는 기준**: 핵심 작업에 닿는 버튼이 새 입력·선택 UI를 여는 경우(추가·수정·고르기·초대)는 뜨는 창 화면을 만든다. 이미 있는 화면으로 가는 버튼은 그 화면으로 갈래만 잇는다. 나머지는 `data-stay`.

### 6.3 화면 조각 `screens/<slug>.html`

규칙 전문은 `packages/web/snippets/00-rules.md`. 요약: body 안쪽만, 스니펫 클래스만, `data-region`·`data-trigger` 표시, Lucide 아이콘만, 실제 도메인 문구, 빈 상태 화면은 `.empty` 조각으로 비워 둔다.

### 6.4 `icons.json` (프로젝트)

의미 → lucide 이름 1:1. core `allowlist.json`에 없는 아이콘만 등록한다. 같은 아이콘에 두 의미 금지.

## 7. 분위기·글자 크기·버튼 색

- **PRD마다 만든다**(`screens.json`의 `looks`, 규칙은 prd-to-screens §6). 분위기 = `{id, name, why, mode, bg, ink, shape, swatches[5]}`. 메인은 배경·글자·모양·버튼 색만 정하고, `scripts/looks.js`가 표면·테두리·흐린 글자·눌림색·연한 강조·상태색까지 계산해 `[data-theme="<id>"]`·`[data-theme][data-swatch="<id>"]` CSS를 만든다. looks가 없으면 기본 3개(깔끔한 흰색 · 따뜻한 크림 · 차분한 밤).
- 글자 크기 `[data-type="normal|large"]`. 버튼 색은 `data-swatch`(예전 `data-accent calm|vivid`는 첫째·둘째 색으로 호환).
- 잠금: `board.locked`에 `theme`·`type`·`swatch`(또는 둘을 묶은 `toggles`) — 확정된 것만 잠그고, 새로 생긴 선택지는 연다.
- 컴포넌트 CSS는 토큰 변수만 참조한다. 색·간격·반경·그림자 하드코딩 금지.

## 8. 아이콘

- Lucide만. `build.js`가 스프라이트에서 사용된 심볼만 인라인한다(id `i-` 접두). 크기 `.icon-sm`(16) · `.icon`(20) · `.icon-lg`(24).
- 아이콘만 있는 버튼은 `aria-label` 필수.

## 10. 게이트 (스크립트가 판정, LLM 자기보고 금지)

| 시점 | 명령 | 실패 시 |
|---|---|---|
| 조각 생성 후 | `node scripts/lint.js runs/<p>` | FAIL 화면만 재호출 |
| 사용자에게 보여주기 전 | `build.js --mode board` → 메인이 헤드리스 Chrome으로 검수 → 헤드리스 종료 → `build.js --mode board --open` | 깨졌으면 보여주지 않는다 |
| 최종 전 | `lint.js && build.js --mode final` → 검수 → `--open` | 동일 |

lint가 보는 것:
- 데이터: id 중복·누락, slug·key 형식, role·nav 존재, state 값, variantOf 대상.
- 조각: `data-region` ↔ screens.json 양방향, `data-trigger` 존재·유일·항목 소속, 아이콘(스프라이트·allowlist), `<style>`/`<script>`/인라인 style, Lorem·자리표시 문구, components에 없는 클래스.
- 흐름: from/to/region/trigger 존재, **끊김 없는 한 줄**, 흐름에 안 나오는 화면.
- 갈래: from/to/region/trigger 존재, 흐름 단계와 중복 금지, 뜨는 창(`overlayOf`)마다 여는 버튼 존재, 창 조각은 `.modal-backdrop` 하나.
- 버튼: 글자가 있는 `.btn`마다 `data-trigger`(흐름·갈래) · `data-back` · `data-stay` 중 하나.
- 번호: 화면 100 이하, 항목 101 이상.
- 말: 흐름 제목 '~하기'·18자 이내, 항목 이름의 컴포넌트 용어, `why` 누락, 처음 켰을 때·데이터 없을 때 화면 존재.

## 11. 검수 방법 (메인)

- 검수용 헤드리스 Chrome: `Google Chrome --headless=new --remote-debugging-port=9222 --user-data-dir=<scratchpad>/chrome-profile`. chrome-devtools MCP로 연결.
- 보는 것: (사용 흐름) 전체 흐름 카드가 모두 그려지는가 / 카드 → 따라가 보기에서 두 장과 파란 박스·화살표·단계 문장 / 갈래가 있는 화면에서 보라 점선 박스 → 아래 칸 화면 / →·Esc / 화면 클릭 → 화면 디자인으로. (화면 디자인) 화면 속 버튼이 제 모양인가 / 요소에 마우스 → 이름표 / 누르기 → 바꿔주세요 → 핀이 붙고 '의견 보내기 (n)'가 오르는가 / 콘솔 에러 0.
- **`--open` 전에 헤드리스 Chrome을 종료한다.** macOS에서 `open`이 파일을 헤드리스 인스턴스로 넘겨 사용자 화면에 아무것도 안 뜬다(build.js가 감지하면 새 창으로 우회).

## 13. 리허설에서 사용자가 정한 것 (2026-09-27~28)

하네스를 바꿀 때 이 결정을 되돌리지 않는다. 리허설 실행물과 상세 기록은 작업 브랜치에 두지 않고 보관 브랜치(`archive/rehearsal-1`)에만 있다 — 실행 중에는 참고하지 않는다.
