# 보이스톤 프리셋 검증 — 최소 비용 실험 계획

프리셋 3개(`core/foundation/voices/`)를 하네스에 연결하기 **전에**, 정말 쓸모 있는지 싸게 확인한다. 하네스 전체 구동(15분 × N)은 하지 않는다 — 이미 있는 v18 결과물의 문구만 다시 쓴다.

## 확인할 것 (각각 틀릴 수 있는 가설)

| | 질문 | 틀리면 |
|---|---|---|
| Q1 구별 | 같은 장면을 세 프리셋으로 쓰면 서로 구별되는가 | 구별 안 되는 둘을 합친다(예: 토스≈당근이면 해요체 하나 + 합니다체 하나, 선택지 2개) |
| Q2 충실 | 출력이 프리셋 규칙(문체·경어·버튼 쌍)과 공통 문법을 지키는가 | 프리셋이 모호하다 — 자리별 형태·버튼을 더 구체적으로, 또는 selfcheck로 강제 |
| Q3 자연 | v18 원본보다 자연스럽고, 실제 앱 문구와 섞어 놓으면 구별이 안 되는가 | 프리셋 문제가 아니라 공통 문법(copy.md) 문제 — 그쪽을 먼저. 실제 앱과 구별되면 무엇이 티 나는지 모아 규칙으로 |
| Q5 회사다움 | 토스 프리셋 결과가 실제 토스 화면 문구처럼 읽히는가(당근·리디도) | 가이드만으로는 그 회사 말투가 재현되지 않는다 — 실제 화면 문구를 예시로 보강하거나, 회사 이름을 빼고 성격 이름만 쓴다 |
| Q4 선택 | 비교표만 보고 고를 수 있고, 추천 이유에 납득하는가 | 질문 화면(예시 장면·이유 쓰는 법)을 고친다 |

추가로 "공통 문법만" 버전을 기준선으로 둔다 — 개선이 프리셋 덕인지 공통 문법 덕인지 가르기 위해.

## 재료 (새로 만들지 않음)

v18 결과물 3개에서 문구 15개씩, 자리별로 고른다 — 화면 제목 2, 섹션 제목 2(알려진 실패 `자리가 나면`·`취소하면` 포함), 행 보조 줄 2, 토스트·완료 2, 확인 대화상자(제목+본문+버튼 쌍) 2, 오류 2, 빈 상태 1, 큰 숫자 1, 안내문 1.

| 앱 | 도메인 | 프리셋 `fits`상 예상 추천 |
|---|---|---|
| `v18-pilates-booking` | 예약·결제 | 짧고 담백하게 |
| `v18-wedding-meetup` | 모임·사람 | 다정하게 |
| `v18-ai-saju` | 상담·콘텐츠 | 정중하게? (예상이 갈림 — Q4에서 확인) |

## 1단계 — 기계 실험 (약 10분, LLM 호출 약 40회)

`loop/voice_exp.py` 하나로:

1. **다시 쓰기**: 앱 3개 × {공통 문법만, 토스, 당근, 리디} = 12회. 문구 15개와 화면 맥락(화면 제목·자리)을 주고 sonnet이 다시 쓴다. 프리셋 JSON 전문과 공통 문법을 프롬프트에 붙인다.
2. **Q2 충실(정규식)**: 리디 출력에 해요체 종결 0(‑해주세요·‑해보세요 제외), 토스·당근에 합니다체 0(당근의 경고·`죄송합니다` 제외), 토스 `‑시‑` 0, 대화상자 보조 버튼(토스·당근 `닫기` / 리디 `취소`), 공통 문법 위반(이름표가 조건절·조사로 끝남, 줄표로 문장 잇기) 0. **통과: 규칙 준수 95% 이상.**
3. **Q1 구별(블라인드 판정)**: 다른 모델(opus)에게 프리셋의 `label`·`pitch`만 주고(규칙은 안 줌), 한 장면 묶음(문구 5개)이 어느 보이스톤인지 맞히게 한다. 3앱 × 3묶음 × 3프리셋 = 27회. **통과: 정답률 70% 이상(우연 33%), 토스↔당근 혼동 50% 미만.**

## 2단계 — 사람 실험 (수민 10분, 토요일 sync에서 팀원 각 10분)

1단계를 통과한 것만으로 HTML 한 장(`voice-exp.html`, 결과는 버튼 한 번으로 JSON 복사):

- **A. 둘 중 더 자연스러운 쪽 (20쌍)**: v18 원본 vs 추천 프리셋 10쌍 + 공통 문법만 vs 추천 프리셋 10쌍, 좌우 무작위. **통과: 원본 대비 75% 이상 승, 공통 문법만 대비 50% 이상(나빠지지 않음).**
- **B. 진짜 찾기 (10쌍)**: 실제 앱 문구(`real-strings.md`, 같은 자리·같은 상황 — 캐치테이블·테이블링·토스·당근·리디) vs 우리 생성. "어느 쪽이 실제 앱인가". **통과: 정답률 65% 이하(구별이 어려움).** 맞힌 쌍은 "무엇이 티 났나" 한 줄 메모 — 다음 규칙의 재료.
- **C. 질문 화면 그대로 (3개)**: 앱 3개 각각의 실제 질문 화면(추천 + 이유 + 4장면 비교표)을 보여 주고 고르게 한다. **통과: 추천과 같은 선택 2/3 이상, 또는 "이유가 납득된다" 5점 중 4 이상.**

## 3단계 — 회사다움 (Q5)

프리셋은 **가이드**로 만들었으므로, 검증은 가이드에 없는 **실제 화면 문구**로 한다(정답지가 섞이지 않게).

1. **정답 문구 모으기 (에이전트 1회)**: 회사마다 실제 앱·웹 화면 문구 30개 — App Store 스크린샷, 웹(toss.im·daangn.com·ridibooks.com), 고객센터. 문구마다 `{자리, 상황 한 줄, 원문, 출처}`. 가이드·블로그에 실린 예시 문구는 넣지 않는다. 현재 화면이 가이드와 다르면 그 자체가 발견이다(특히 리디 — 가이드가 2019년이라 지금 앱이 해요체로 바뀌었을 수 있다. 그러면 이 프리셋 이름은 '리디'가 아니라 '2019 리디 가이드'다).
2. **상황만 주고 다시 쓰기**: 정답 문구의 `{자리, 상황}`만 주고(원문은 숨김) 세 프리셋으로 각각 쓴다. 회사 3 × 프리셋 3 = 9회 호출, 270문구. 남의 상황(당근 상황을 토스 프리셋으로)도 쓰게 해서, 상황이 아니라 프리셋이 말투를 정하는지 본다.
3. **말투 지문 비교 (기계, 0원)**: 문구 묶음마다 지문을 센다 — 종결 분포(해요·합니다·명사·질문), `‑시‑` 빈도, 느낌표·이모지, 마침표 유무, 평균 길이, 버튼 형태(`~하기`·명사·`닫기`/`취소`), 숫자 표기. **통과: 각 프리셋 결과의 지문이 세 회사의 실제 지문 중 자기 회사에 가장 가깝다.**
4. **회사 맞히기 (LLM 판정, 기준선 포함)**: 판정 모델에게 문구를 하나씩 주고 토스·당근·리디 중 어디 것인지 맞히게 한다. 먼저 **실제 문구로 기준선**을 잰다 — 실제 문구도 60%밖에 못 맞힌다면 그 이상을 요구할 수 없다. **통과: 생성 문구의 정답률이 실제 문구 정답률에서 10%p 안쪽.** 기준선 자체가 낮으면(50% 미만) 세 회사가 글만으로 구별되지 않는다는 뜻이다 — 회사 이름을 내세우지 않고 성격 이름만 쓴다.
5. **같은 상황, 진짜는? (사람)**: 2단계 HTML에 회사별 10쌍 추가 — 같은 상황의 실제 문구 vs 그 회사 프리셋 결과, "진짜 토스 문구는?". 평소 그 앱을 쓰는 사람(팀원 다수가 토스·당근 사용자)이 판정. **통과: 정답률 65% 이하.** 맞힌 쌍은 "무엇이 달랐나" 메모 → 프리셋 보강 재료.

통과한 프리셋에는 `"verified": {"date", "fingerprint_nearest", "judge_acc", "human_acc"}`를 남기고, 실패한 프리셋은 질문 화면에서 회사 이름을 빼고 성격 이름만 쓴다.

## 하지 않는 것

하네스 전체 재구동, 큰 규모의 사람 평가, 프리셋 추가. 비용은 LLM 호출 약 50회 + 정답 문구 수집 에이전트 1회, 사람 15분 × 최대 5명이다.

## 1차 결과 (2026-10-12, 기계 단계 — `loop/voice_exp/REPORT.md`)

생성 21회(sonnet) + 판정(opus), 전체 약 3분.

| | 결과 | 기준 | 판정 |
|---|---|---|---|
| Q2 충실 | 공통만 100% · 토스 100% · 당근 99% · 리디 99% | 95% | 통과 |
| Q1 구별 | 70%(27묶음) — 리디 8/9, 토스 6/9, 당근 5/9. 당근→토스 오인 3/9 | 70%, 토스↔당근 혼동 50% 미만 | 경계 통과 |
| Q5 회사다움(같은 상황 비교) | 리디 **71%**, 토스 50%, 당근 50%(우연 33%). 당근 실제 원문에 토스 프리셋을 고른 비율이 당근 프리셋과 같음(10:10) | — | 리디만 회사다움 확인 |
| Q5 말투 지문 | 토스·리디 프리셋은 자기 회사에 가장 가깝다. 당근 프리셋은 토스에 더 가깝다(실제 당근의 묻는 자리 경어·느낌표·마침표를 프리셋이 0으로 만듦) | 자기 회사가 가장 가까움 | 당근 실패 |

**측정에서 배운 것**
- 처음 설계한 "회사 맞히기"는 쓸 수 없었다 — 판정이 말투가 아니라 **상황의 내용**(어느 서비스 이야기인가)을 따라갔다(토스 상황은 어느 프리셋으로 써도 '토스'). 실제 문구 기준선 100%도 같은 이유. → 같은 상황의 후보끼리 비교하는 방식으로 바꿨다.
- 같은 상황 비교도 잡음이 있다 — 상황 설명이 느슨해 후보의 **내용**이 원문과 달라지는 경우가 많다(원문은 안내인데 후보는 완료 토스트 등). 토스·당근 50%는 말투 차이보다 이 잡음일 수 있다.
- 규칙 검사기는 프리셋 예외(토스 법적 고지 합니다체, 당근 제재 합니다체)와 '함께'의 '께' 같은 오탐을 처음에 잡아 고쳤다.

**판단**: 리디(합니다체)와 해요체 계열은 확실히 갈린다. 토스와 당근은 실제로도(본앱 지문 차이가 작음) 프리셋으로도 잘 갈리지 않는다 — 둘을 가르는 실제 신호(확인창 보조 버튼 닫기/취소, 당근의 묻는 자리 경어·가끔의 느낌표·마침표)는 문구 몇 개 안에 드물게 나온다.
