# harness v8 스펙 — 미적 파운데이션 + 쉬운 화이트보드

> 2026-10-01 · 9/30 싱크 결론("이번 스프린트는 미적 수준 맞추기")과 사람 피드백("그냥 Claude 써도 이 정도는 나올 것 같다")을 반영한 다음 버전.
> 기준: [success-criteria.md](./success-criteria.md) §8~10 신설 · 근거: [design-criteria.md](./design-criteria.md) §8~9

## 1. 문제 정의

v7까지의 한계는 세 가지다.

1. **기준이 감점 방지뿐이었다.** 29개 기계 채점은 바닥을 올렸지만 "예쁨"을 만드는 기준이 없었다.
2. **Claude가 모르는 정보를 넣지 않았다.** 한국 앱 스타일 가이드도 Claude가 원래 아는 토스 지식의 재서술이었고, 채점자도 Claude였다 → Claude 기본값으로 수렴.
3. **사용자 선택이 가장 약한 변수(포인트 색)에만 쓰였다.**

v8은 이 셋을 **파운데이션 패키지 · 레퍼런스 기준 평가 · 선택 축 확장**으로 푼다. 캔버스는 기능을 늘리지 않고 **더 단순하게** 만든다.

## 2. 불변 조건 (v7 유지)

- 사용자 개입 ≤ 4회(PRD 포함), 선택형 답, 전문 용어 0
- 수행 시간 < 15분
- 결과물: 모바일 HTML + 캔버스 `index.html` 한 파일로 진입, 설치 0
- 상태 파생 규칙과 상한(넘침도 실패)

## 3. 구성

### A. 파운데이션 패키지 `foundation/`

디자이너의 "자기 스타일"처럼 미리 정의해 두고, 프로젝트마다 소수 파라미터만 바꾼다. (성렬님 `looks.js`·패키지 방식, 여진님 `theme.js`의 "근거 있는 값만 덮어쓰기" 방식 참고)

- **`derive.py`** — 입력 3개로 전체 컬러 토큰을 계산한다.
  - 입력: 포인트 색, 표면 톤(따뜻함·중립·차가움), 모양(각짐·보통·둥긂)
  - 출력: `text-1`(순검정 아님)·`text-2`·`text-3`·`bg`·`surface`·`line`·`brand`·`brand-tint`·`on-brand`·`danger`
  - 모든 글자·배경 조합의 대비를 계산해 AA를 통과하도록 명도를 조정한다(v1에서처럼 포인트 색을 탁하게 만들지 않도록, 버튼 글자는 흰색/짙은색 중 대비 높은 쪽을 고른다).
- **타이포 세트 (폰트별)** — 폰트마다 크기·굵기·자간·줄간격 조합을 따로 둔다. 기본 Pretendard:
  - 제목 28/700 · 섹션 20/700 · 본문 16/400(줄간격 1.5) · 보조 14/400 `text-2` · 캡션 12/500 `text-3`
  - 보기 전용 역할 화면은 한 단계씩 올린다.
  - 강약 대비 규칙: 제목 ÷ 본문 ≥ 1.5, 굵기 차 ≥ 200
- **스페이싱 세트** — 4pt 스케일 위에 "넉넉한 기본값"을 정한다.
  - 화면 좌우 24 · 섹션 사이 32 · 항목 사이 16 · 블록 안쪽 20 · 제목→본문 8
  - 밀도 손잡이: 여유 / 보통
- **컴포넌트 CSS + 조각 HTML** — 앱바·탭바·목록 행·버튼(주/보조)·칩·입력·배지·섹션·빈 상태·완료 표시·바텀시트. 빌드 에이전트는 **클래스만 쓰고 인라인 스타일·임의 값 금지**(lint로 차단).

### B. 무드 질문 개선

- 시안 3개가 **색만이 아니라 파운데이션 파라미터 조합**으로 다르다: (포인트 색 × 표면 톤 × 모양 × 밀도) 중 서로 먼 3세트.
- 시안 생성 전에 `scripts/fetch_refs.py`로 **같은 도메인 한국 앱 실제 화면**(uibowl)을 받아, 시안 에이전트가 보고 만든다.
- 질문 형식(여진님 `interview.md` 참고): 질문 위에 "고르신 것에 따라 모든 화면의 색·글자 느낌이 달라져요"처럼 **무엇이 달라지는지** 한 줄.

### C. 캔버스 v2 — 기능을 빼는 방향

- **보는 것만**: 스크롤과 "누르면 크게 보기"뿐. 편집·선택·피드백 UI 없음(피드백은 채팅에서 화면 이름으로).
- **읽는 순서 하나**: 흐름 그룹 한 줄 = 한 흐름, 왼→오. 순서대로 이어지는 화면은 배치로 보여주고 **화살표는 분기에만**.
- **화면 크기**: 축소 배율 ≥ 0.7.
- **화면 아래**: 목적 1줄 + **정책 ≤ 3줄**(`screens.json`의 `policies`). 넘치면 접기.
- **오류·성공 상태**: 칩이 아니라 흐름 줄 안의 해당 위치에 작은 화면으로.
- **맨 위**: 설계 이야기(v5)는 유지하되 3카드 이하·한 화면 안에.
- 첫 화면 컨트롤 ≤ 3, 외부 라이브러리 0, 로딩 < 1초.

### D. 평가 교체

- `score.py` 추가 체크: §8(순검정·타이포 대비·여백 밀도·파운데이션 밖 값), §9(컨트롤 수·축소 배율·화살표 수·교차·정책 줄 수)
- **처음 보는 사람 테스트**: 비개발자 가상 사용자가 캔버스 스크린샷만 보고 과제 수행
- **레퍼런스 대비 판정**: uibowl 실제 화면과 나란히 블라인드 비교
- **사람 만족도 1~5**: 매 반복 캔버스 상단 + 주요 화면 3장 첨부해 받는다. 에이전트 점수와 어긋나면 루브릭 보정.
- 기존 루브릭은 보조 지표로 격하.

## 4. 범위 밖 (이번 스프린트)

- 캔버스 안 피드백 UI (두 PR 모두 처음 보는 사람에게 복잡했다 — 방식이 정해지기 전까지 넣지 않는다)
- 애니메이션·인터랙션 표현, PC 레이아웃
- 제품화(SaaS) 논의

## 5. 진행 순서

1. `foundation/` + `derive.py` + 컴포넌트 CSS → 기존 v7 결과에 입혀 단독 확인
2. 캔버스 v2 (`build_canvas.py` 교체, `screens.json`에 `policies`·`branch` 필드)
3. `score.py` §8·§9 체크, 처음 보는 사람 테스트, 레퍼런스 대비 판정
4. 자동 루프 3회(청첩장·가족여행) + 매 회 사람 만족도
5. 실무 제품 1개에 적용해 보고 결과를 다음 싱크(수요일)에 공유
