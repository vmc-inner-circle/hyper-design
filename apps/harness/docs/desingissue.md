# AI로 UI를 개발할 때 디자이너가 알아야 할 공통 디자인 이슈

작성일: 2026-09-05

AI로 화면을 구현하면 버튼과 카드가 빠르게 만들어진다. 하지만 기본 화면이 그럴듯해 보여도 마우스를 올리거나, 다른 이미지를 선택하거나, 창을 줄이면 디자인 의도와 다른 결과가 드러날 수 있다. 작은 수정이 다른 영역의 사용성을 망가뜨리기도 한다.

이 문서는 AI와 함께 웹·앱 UI를 만드는 디자이너를 위한 사례와 점검 기준이다. 실제 개발 대화에서 발견한 문제를 범용 상황으로 재구성하고, 버튼 호버·이미지 맞춤 같은 사용자 제보와 예방용 점검 항목을 더했다. 아래의 ‘발생 배경’은 가능한 구현 원인에 대한 설명이며, AI 내부의 판단 과정을 입증한 것은 아니다. AI에만 발생하는 문제도 아니지만, 빠르게 생성하고 부분적으로 수정하는 작업에서 함께 확인할 필요가 있다.

## 1. 기본 화면은 맞는데, 상태가 바뀌면 디자인이 달라진다

### 버튼에 마우스를 올리니 갑자기 검정이 된다

**상황:** 기본 버튼은 원하는 색인데 호버하면 검정 배경이 나타난다. 글자나 아이콘은 그대로여서 읽기 어려워질 수도 있다.

**발생 배경:** 기본 색상만 수정하고 기존 버튼 컴포넌트의 호버 스타일을 남겨두었을 수 있다. 기본·호버·선택·비활성 스타일이 서로 다른 곳에서 적용되면 한 상태만 바뀌기 쉽다.

**확인할 것:** 버튼의 배경·글자·테두리·아이콘을 상태별로 함께 본다. 검정이라는 색 자체가 아니라, 의도한 상태 표현과 일치하는지가 기준이다.

**요청 예시:** “기본·호버·누름·선택·비활성·키보드 포커스 상태를 기존 버튼 체계와 맞춰줘. 배경뿐 아니라 글자와 아이콘 색도 같이 확인해줘.”

### 선택되어 있지만 무엇을 선택했는지 보이지 않는다

**상황:** 선택 테두리는 바뀌었지만 해당 썸네일은 스크롤 바깥에 있다. 또는 호버와 선택 배경이 같아 마우스를 떼기 전까지 선택 여부가 불분명하다.

**발생 배경:** 선택값 변경과 화면에서 선택을 알아보는 조건을 따로 처리했을 수 있다.

**확인할 것:** 선택 표시가 주변과 구분되는지, 선택 항목이 보이는지, 이미 보이는 항목을 선택했는데도 불필요한 자동 스크롤이 생기는지 확인한다.

### 로딩·빈 상태에서 문구나 배치가 깨진다

**상황:** 데이터가 있는 화면은 정상인데 처음 열면 숫자가 비어 있고, 로딩 중에는 다른 배경색이나 번역 오류가 나타난다.

**발생 배경:** 완성된 샘플 화면만 확인했거나 테스트용 문구와 실제 번역 파일이 달랐을 수 있다.

**확인할 것:** 처음 진입, 데이터 없음, 로딩, 성공, 실패, 비활성 상태를 각각 본다. 언어가 여러 개라면 실제 번역 문구로도 확인한다.

## 2. 아이콘이 있어도 의미와 조작 방식이 전달되지 않는다

아이콘은 장식과 조작 수단의 역할을 함께 갖는다. 크기만 통일해도 충분하다고 보기 어렵다.

| 이슈 | 화면에서 나타나는 모습 | 확인할 것 |
|---|---|---|
| 크기·선 두께 불일치 | 같은 도구모음인데 일부 아이콘만 굵거나 작아 보인다. | 아이콘 계열, 선 두께, 시각적 크기를 비교한다. 같은 수치라도 실제 도형의 여백 때문에 다르게 보일 수 있다. |
| 아이콘과 텍스트 정렬 | 아이콘이 글자보다 떠 있거나 간격이 들쭉날쭉하다. | 수직 중심과 텍스트 간격을 실제 렌더링에서 확인한다. |
| 호버·비활성 색상 누락 | 버튼은 변하는데 아이콘은 그대로거나 배경에 묻힌다. | 버튼과 아이콘의 상태 색상을 함께 본다. |
| 작은 클릭 영역 | 아이콘 그림 부분만 겨우 눌린다. | 그림 크기와 클릭 영역을 구분하고 인접 버튼과 간섭하지 않는지 본다. |
| 중요한 정보가 숨음 | 알아야 할 내용을 작은 정보 아이콘을 눌러야만 볼 수 있다. | 바로 노출할 정보와 보조 설명으로 숨길 정보를 구분한다. |
| 더보기 메뉴 남용 | 자주 쓰는 기능까지 모두 점 세 개 뒤에 들어간다. | 사용 빈도와 중요도에 맞게 액션을 노출한다. |
| 대상과 액션이 떨어짐 | 새로고침 아이콘이 무엇을 갱신하는지 알 수 없다. | 관련 제목·내용 가까이에 두고 필요하면 설명을 제공한다. |
| 중복 액션 | 상단과 내부 영역에 이름만 다른 저장 버튼이 있다. | 같은 동작인지, 다른 범위를 저장하는지 명확하게 한다. |
| 툴팁 불일치 | 아이콘마다 설명의 모양·위치·등장 방식이 다르다. | 공통 툴팁을 사용하고 키보드로도 의미를 확인할 수 있게 한다. |
| 아이콘만 있고 이름이 없음 | 그림을 이해하지 못하거나 화면 낭독기로 기능을 구분하지 못한다. | 필요한 텍스트·툴팁·접근 가능한 이름을 제공한다. |

아이콘 규격·클릭 영역·접근 가능한 이름은 예방용 점검 항목이다. 정보의 숨김, 중복 액션, 액션 위치, 툴팁 통일은 실제 대화 사례를 바탕으로 정리했다.

## 3. 이미지를 넣었지만, 이미지의 목적에 맞게 보여주지 않는다

### 전체가 보여야 하는데 잘리고, 꽉 차야 하는데 여백이 남는다

**상황:** 상품이나 작업 결과의 일부가 잘린다. 반대로 화면을 채우는 카드에서는 이미지 주변 여백이 과도하다.

**발생 배경:** 이미지 표시 방식을 영역의 목적과 연결하지 않고 일괄 적용했을 수 있다.

- `contain`: 비율을 유지하며 이미지 전체를 보여준다. 컨테이너와 비율이 다르면 여백이 생길 수 있다.
- `cover`: 비율을 유지하며 컨테이너를 채운다. 비율이 다르면 일부가 잘릴 수 있다.

**확인할 것:** 전체 확인이 중요한 상세 이미지와 크롭을 허용하는 목록 카드를 구분한다. 세로·가로·정사각형 이미지로 각각 확인한다.

**요청 예시:** “상세 미리보기는 이미지 전체가 보여야 해. 목록 카드는 같은 비율로 채우되 중요한 피사체가 잘리는지 확인해줘.”

### 썸네일을 바꿀 때 화면이 깜빡인다

**상황:** 정지 화면은 정상인데 썸네일을 연속 클릭하면 큰 이미지가 잠깐 사라지거나 영역 높이가 움직인다.

**발생 배경:** 다음 이미지가 준비되기 전에 기존 이미지를 제거하거나, 선택할 때마다 표시 영역을 새로 만들었을 수 있다.

**확인할 것:** 한 번 클릭한 최종 화면뿐 아니라 연속 선택과 느린 로딩도 본다. 전환 중 영역 크기와 선택 표시가 안정적인지 확인한다.

## 4. 위치를 바꿔달라는 요청이 다른 구조로 해석된다

| 요청 | 발생할 수 있는 오해 | 분명히 할 관계 |
|---|---|---|
| “제목을 위로 올려줘.” | 이미지 옆 제목을 위쪽으로 정렬한다. | 이미지 위의 별도 행인지, 옆에서 상단 정렬인지 |
| “정보를 오른쪽에 보여줘.” | 정보를 여는 버튼만 오른쪽으로 옮긴다. | 이동 대상이 버튼인지, 팝업인지, 팝업 내부 내용인지 |
| “세 항목을 묶어줘.” | 각 항목의 제목을 없애고 하나의 제목으로 합친다. | 배치만 묶는지, 명칭과 기능까지 합치는지 |
| “버튼들을 한 줄로 해줘.” | 줄바꿈을 막아 좁은 화면에서 버튼이 잘린다. | 한 줄을 유지할 화면 폭과 좁을 때의 배치 |
| “모달을 넓혀줘.” | 바깥 폭만 늘려 내부의 빈 공간이 커진다. | 프리뷰·옵션·목록 중 어떤 영역에 공간이 필요한지 |

**발생 배경:** 디자이너는 요소 간 관계를 말하지만, 구현에서는 위치·정렬 속성 하나만 변경해 요청을 충족했다고 판단할 수 있다.

**요청 예시:** “제목을 썸네일 위의 별도 행에 놓고, 모든 카드가 제목 → 이미지 → 설명 순서를 갖게 해줘.”

이런 오해를 줄이는 기준은 길게 설명하는 것보다 **대상·기준 요소·배치 순서**를 명확히 하는 것이다.

## 5. 보기 좋게 고쳤는데 다른 곳을 사용할 수 없게 된다

### 버튼을 하단에 고정하니 마지막 옵션이 가려진다

**상황:** 주요 버튼은 계속 보이지만 그 뒤에 있는 입력란이나 옵션은 누를 수 없다.

**발생 배경:** 고정 영역을 배치하면서 본문이 사용할 공간과 스크롤 범위를 함께 조정하지 않았을 수 있다.

**확인할 것:** 마지막 입력란까지 스크롤하고 클릭해 본다. 화면 높이가 낮거나 안내문이 길어졌을 때도 확인한다.

**요청 예시:** “하단 버튼은 계속 보이게 하되 본문과 겹치지 않게 해줘. 본문 마지막 항목까지 접근할 수 있어야 해.”

### 팝업은 커졌는데 조작부는 계속 아래에 숨어 있다

**상황:** 미리보기만 커지고 중요한 옵션은 아래로 밀려 여전히 스크롤해야 한다.

**발생 배경:** 전체 크기와 내부 정보 배치를 같은 문제로 다뤘을 수 있다.

**확인할 것:** 넓은 화면에서 미리보기와 조작부를 나란히 볼 필요가 있는지 판단한다. 작은 화면에서는 읽고 조작할 순서대로 쌓이게 한다. 스크롤을 없애려고 콘텐츠를 잘라내서는 안 된다.

### 툴팁이나 메뉴가 잘린다

**상황:** 버튼은 정상인데 설명이나 드롭다운이 모달 경계에서 잘리거나 뒤로 숨는다.

**가능한 배경:** 요소의 겹침 순서나 부모 영역의 잘림 설정이 맞지 않을 수 있다.

**확인할 것:** 화면과 모달 가장자리에서도 메뉴를 연다. 이 항목은 예방용 점검 기준이다.

## 6. 요청한 변경보다 더 많은 동작을 바꿔버린다

### 기본으로 열어달랬더니 닫을 수 없게 된다

**상황:** “정보 패널을 처음부터 보여줘”라고 요청했는데 닫기 동작까지 제거된다.

**발생 배경:** 기본 상태 변경을 고정 표시 방식으로 확대 해석했을 수 있다.

**확인할 것:** 처음의 상태와 사용자가 바꿀 수 있는 상태를 구분한다. 열기·닫기·취소처럼 기존에 가능했던 행동이 유지되는지 확인한다.

### 한 개만 선택하게 바꿨는데 안내는 다중 선택 기준이다

**상황:** 선택은 하나로 제한했지만 문구는 ‘선택 해제’로 남거나 다른 화면의 다중 선택까지 바뀐다.

**발생 배경:** 클릭 처리만 바꾸고 상태 표시·안내·공통 사용처의 차이를 놓쳤을 수 있다.

**확인할 것:** A 다음 B를 선택했을 때의 동작, 같은 항목을 다시 눌렀을 때의 동작, 다른 화면에서 필요한 선택 방식을 함께 본다.

## 7. 같은 서비스인데 화면마다 다른 제품처럼 보인다

**상황:** 한 화면의 로딩 배경은 바뀌었지만 다른 화면은 예전 색이다. 같은 편집 도구가 팝업에서는 2열이고 독립 페이지에서는 기존 배치로 남는다. 공통 저장 버튼을 추가하자 기존 저장 버튼과 중복된다.

**발생 배경:** 화면마다 개별 구현이 있거나 공통 컴포넌트 안에 표시 조건이 나뉘어 있을 수 있다. 새 공통 요소를 추가할 때 기존 요소의 존재를 확인하지 않았을 수도 있다.

**확인할 것:** 같은 역할을 하는 버튼·아이콘·로딩·툴팁·모달을 사용 화면별로 비교한다. 일관성은 모든 화면의 크기와 동작을 무조건 같게 만드는 것이 아니다. 팝업과 독립 페이지처럼 공간과 목적이 다른 경우에는 그 차이에 맞게 표현해야 한다.

**요청 예시:** “같은 도구를 사용하는 팝업과 독립 페이지에서 함께 확인해줘. 시각 규칙은 맞추고, 각 화면의 가용 공간에 맞게 배치해줘. 기존에 같은 액션이 있으면 중복하지 마.”

## 8. 문장은 정확하지만 사용자가 무엇을 해야 하는지 모른다

**상황:** 완료 안내에 내부 화면 이름만 나오거나, 짧은 보조 문구가 여러 문장으로 늘어나 버튼 아래를 차지한다. 기능은 바뀌었는데 도움말은 이전 메뉴를 안내한다.

**발생 배경:** 내부 명칭을 사용자도 알고 있다고 가정하거나, 문구의 정확성과 화면에서의 길이·위치를 따로 처리했을 수 있다.

**확인할 것:** 처음 온 사람이 다음 행동을 알 수 있는지, 안내문이 놓일 공간에 맞는지, 도움말이 현재 화면과 일치하는지 본다.

| 표현 | 더 구체적인 방향 |
|---|---|
| “상세 뷰에서 확인할 수 있습니다.” | “이미지를 클릭하면 자세히 볼 수 있어요.” |
| “처리가 불가능합니다.” | 실제 제한 이유와 다시 사용할 수 있는 조건을 안내한다. |
| 버튼 아래에 긴 기능 설명 | 지금 행동에 필요한 내용을 짧게 두고 추가 설명은 분리한다. |
| 변경 전 화면의 가이드 | 현재 메뉴 이름과 행동 순서에 맞춰 갱신한다. |

문구를 한 줄로 만드는 것만 목표로 삼으면 작은 화면에서 잘릴 수 있다. 필요한 정보를 유지하면서 길이와 배치를 함께 조정한다.

## 9. 실제 데이터가 들어오면 디자인의 빈틈이 드러난다

**상황:** 제목이 긴 카드만 높이가 다르고, 결과 하나의 정보 패널에 전체 결과의 설정이 표시된다. 항목이 많아지면 선택한 썸네일이 사라지거나 목록의 다음 항목에 접근하기 어렵다.

**발생 배경:** 짧은 샘플 데이터만 사용했거나, 현재 화면에 속하는 데이터의 범위를 잘못 연결했을 수 있다.

**확인할 것:** 짧은 이름과 긴 이름, 이미지 비율 차이, 항목 0개·1개·여러 개, 실제 언어별 문구로 확인한다. 정보가 존재하는 것뿐 아니라 현재 선택한 대상의 정보인지도 본다.

정보 귀속 문제는 실제 사례를 일반화한 내용이다. 긴 제목 등의 조합은 추가 검수를 위한 예시다.

## 10. “검사 통과”와 “디자인 의도 충족” 사이에 간격이 있다

**상황:** AI가 코드 검사와 테스트를 통과했다고 말했지만 제목은 여전히 의도와 다른 위치에 있다. 테스트용 번역 문구는 존재하지만 실제 번역 파일에는 빠져 있을 수도 있다.

**발생 배경:** 코드 검사는 문법·타입·작성된 테스트 조건을 확인한다. 테스트가 실제 데이터나 디자인 의도를 다루지 않으면 그 부분의 문제는 남는다.

**확인할 것:** 검사 결과와 함께 실제 화면에서 무엇을 확인했는지 본다. 정지 화면 캡처에 더해 호버·클릭·스크롤·창 크기 변경도 확인한다.

**요청 예시:** “구현 후 기본 화면뿐 아니라 호버, 선택, 로딩, 좁은 화면을 확인해줘. 실제로 확인한 항목과 확인하지 못한 항목을 구분해줘.”

## 디자이너가 전달하면 좋은 다섯 가지

AI가 추측해야 하는 부분을 줄이려면 다음 정보를 짧게라도 남기는 것이 도움이 된다. 모든 실패를 요청자의 설명 부족으로 돌리기 위한 기준은 아니다. 구현 과정에서도 기존 컴포넌트와 주변 맥락을 확인해야 한다.

| 전달할 정보 | 예시 |
|---|---|
| 대상과 목적 | “상품 상세 이미지이므로 제품 전체가 보여야 해.” |
| 요소 간 관계 | “제목은 이미지 위, 설명은 아래에 둬.” |
| 상태별 모습과 동작 | “처음에는 열려 있고 버튼을 다시 누르면 닫혀.” |
| 공간이 부족할 때의 대응 | “넓을 때는 2열, 좁으면 미리보기 다음에 옵션이 오게 해.” |
| 확인할 범위 | “같은 컴포넌트를 쓰는 팝업과 페이지, 긴 문구와 로딩 상태까지 봐줘.” |

## 바로 사용할 검수 목록

- [ ] 버튼과 아이콘이 기본·호버·선택·비활성·포커스 상태에서 의도대로 보인다.
- [ ] 아이콘의 크기·선 두께·정렬·클릭 영역이 일관되고 의미를 알 수 있다.
- [ ] 이미지의 비율과 잘림 방식이 영역의 목적에 맞는다.
- [ ] 썸네일의 규격·제목 위치·선택 표시가 일관되고 선택 항목이 보인다.
- [ ] 문구가 길어지거나 언어가 바뀌어도 버튼과 레이아웃이 깨지지 않는다.
- [ ] 작은 화면에서도 마지막 옵션과 주요 버튼에 접근할 수 있다.
- [ ] 고정 요소·메뉴·툴팁이 다른 콘텐츠를 가리거나 경계에서 잘리지 않는다.
- [ ] 닫기·취소·다시 선택 등 기존 조작이 의도치 않게 사라지지 않았다.
- [ ] 같은 역할의 다른 화면에도 변경이 반영되고 액션이 중복되지 않는다.
- [ ] 초기·빈 상태·로딩·실패 상태와 이미지 전환도 확인했다.
- [ ] 정보 패널의 내용이 현재 선택한 대상과 일치한다.
- [ ] 안내문과 도움말이 현재 화면의 명칭·행동 순서를 설명한다.

## 이 문서를 활용할 때

실제 대화 사례에서 뽑은 핵심은 **요소 하나의 수정이 끝나도, 주변 요소와의 관계·상태 변화·다른 화면에서의 사용 맥락까지 확인해야 디자인이 완성된다는 것**이다.

버튼 호버와 이미지 맞춤은 사용자 제보를 출발점으로 삼았고, 일부 시각 규격과 접근성 항목은 예방용 점검으로 확장했다. 예시는 독자의 이해를 위해 일반화했으며 특정 제품의 현행 버그 목록이나 AI 도구 간 성능 비교가 아니다. 후속 수정 중에는 정상적인 디자인 탐색도 있으므로 모든 수정 요청을 AI의 오류로 집계하지 않는다.
