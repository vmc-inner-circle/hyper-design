# 하네스 베이스라인 실험 (2026-09-10)

## 실험 목적

하네스(`apps/harness`)를 개선하기 전에, 이 하네스를 처음 써보는 사람이 실제로 웹앱(디자인)을 끝까지 만들어보면 각 단계에서 무엇이 문제가 되는지 확인했다. 각 단계마다 **들어간 프롬프트 → 나온 결과 → 그에 대한 사용자 평가**를 그대로 기록했다.

이 실험은 하네스를 전혀 수정하지 않은 상태(main, 커밋 `7396eca`)에서 1회 진행한 베이스라인이며, 이후 비교 실험(조건 하나씩 바꿔보는)의 기준점으로 쓸 목적으로 기록했다. **이번에 GitHub에 올라온 PR 3개(#4, #5, #6)는 이 실험과 별개로 다른 팀원이 낸 것이고, 아래는 이 베이스라인에서 관찰한 문제 중 그 PR들이 어디에 해당하는지만 정리한 것**이다.

## 조건

- 하네스 상태: main `7396eca`, 무수정
- 입력: 사용자 자연어 첫 문장 하나(PRD 파일 없음) — "결혼을 앞두고 청첩장을 주려고 사람들을 만나는데 약속을 잡고, 일정을 관리하고 하는데 어려움이 있어 그래서 이러한 문제를 해결하는 앱? 홈페이지? 같은것을 만들고 싶어, 핸드폰에서 사용할수 있으면 좋겠어"
- 사용자: 팀원 1명(본인), 예비신랑 역할 연기, n=1
- 모델: Claude Sonnet 5, effort high (메인·서브 에이전트 동일)
- Figma 미사용, 4.5단계(최종 미리보기 HTML)에서 종료
- 참고: 실행한 세션에는 실험자 개인의 Claude Code 설정(전역 훅·메모리)이 같이 로드되어 있었다. 다른 사람이 같은 입력으로 돌리면 세부 동작이 다를 수 있다.

## 관찰된 핵심 문제

1. **첫 문장에 스킬이 자동으로 안 걸림** — 일반적인 말투("앱? 홈페이지? 같은것")로는 디자인 전용 모드로 못 들어가고 개발 모드로 먼저 진입함
2. **AI가 방향을 아주 빨리(약 40초) 확정하고, 그 뒤 다시 검토받지 않음** — 0단계 추천 선택지 하나를 사용자가 "둘 다"로 수락한 뒤, 대시보드·상태 5종·예약 링크 같은 구체적인 화면 구성이 그 위에 그대로 쌓임
3. **저장 UX 결함** — 완료 표시가 항목마다 다르게 동작해서 "저장이 안 된다"는 신고가 반복됨, 완료 표시와 실제 저장 상태가 어긋난 적도 있음
4. **진행 메시지와 결과 링크를 구분할 수 없음** — "만들고 있어요"를 결과가 온 것으로 오인한 경우가 3회
5. **조사해온 자료가 화면에 반영되지 않음** — 경쟁 앱 스크린샷 10장을 모아왔지만(4분 54초, $1.04) 레퍼런스 페이지에 0장 노출. 사용자 신고 뒤 하네스가 base64 내장으로 수리(2분 47초).

   **왜 생겼나 (기록 재확인, 09-16)** — 세 겹이 겹쳤다.

   - **① 명세 충돌**: 렌더러 규격(`agents/probe-renderer.md`)은 "이미지는 data URI"라고 되어 있는데, 같은 커밋의 `references/reference-sourcing.md`에는 "스크린샷은 내부 비교용이며 산출물에 재배포하지 않는다"고 되어 있어 정반대로 읽힘.
   - **② 메인 에이전트의 지시가 규격을 덮어씀**: 메인이 렌더러에 준 지시문에 "이미지는 `<img src="../references/파일명">`으로 상대경로 참조"라고 명시(서브 에이전트 지시문 기록). 렌더러는 시킨 대로 했고, 페이지는 claude.ai Artifact로 배포되므로 그 환경에서 상대경로 이미지는 전부 차단 → 0장.
   - **③ 걸러낼 검사 없음**: `check_phase.py` probes 게이트는 라벨 수·프레임 폭·외부 스크립트만 검사하고 "이미지가 있는가, 인라인인가"는 항목이 없음. 배포된 페이지를 하네스가 눈으로 확인하는 단계도 없어 사용자가 첫 발견자가 됨.

   **처방 후보** — 충돌 문장 정리 / 렌더러 규격을 메인이 덮어쓰지 못하게(또는 템플릿에 data URI를 박아두기) / probes 게이트에 `<img src="data:` 검사 추가.

6. **확인 지점이 너무 많음(약 60개)** — 대부분 "추천대로"/"괜찮아요"로 통과되었고, 이는 동의가 아니라 "고르기 복잡해서 넘긴 것"으로 확인됨
7. **최종 결과물에 카드 왼쪽 세로 색띠, 가짜 iOS 상태바 등 AI 느낌이 남음**, 최종 미리보기 페이지 자체도 레이아웃이 일부 파손됨
8. **각 단계 HTML을 서브 에이전트가 매번 처음부터 통째로 생성** — 자기 검토를 반복하며 한 단계에 6~26분씩 걸림
9. **Figma 없이는 결과물 단계가 비어 있음** — 4.5단계 최종 미리보기는 "Figma로 만들기 전 예상 모습"일 뿐, 그 자체가 최종 산출물은 아님

## 이번에 올라온 PR 3개는 이 중 어디에 해당하는가

| PR | 이 베이스라인의 어느 문제에 해당하는가 |
|---|---|
| **#4 (과도한 variant 방지 정책)** | 문제 6(확인 지점 과다)·7(최종 결과물 파손) 과 **부분적·간접적으로** 관련. 이 베이스라인에서도 1단계 게이트가 "상태 6종 누락"으로 걸렸고, 4.5단계 화면 파손도 상태 변형(빈·로딩·실패)이 화면 밖으로 넘친 것이 원인이었음 — 상태 종류를 줄이면 이 부분의 발생 여지가 줄어들 것으로 보이나, 레이아웃 자체의 렌더링 결함(문제 7)을 직접 고치는 것은 아님. PR 본문이 말하는 "Figma 저작 시간 단축" 효과는 이 베이스라인에서는 측정되지 않음(Figma를 쓰지 않았기 때문)
| **#5 (HTML 생성 속도 개선)** | 문제 8(단계별 통째 생성·자기 검토 반복)에 **직접 대응**. 이 베이스라인에서 실측한 "투어 생성 23분(그중 자기 검토 반복 37회), 취향 4개 각 6~9분, 규칙 9분 26초, 최종 미리보기 11분 35초"가 정확히 PR#5가 지목한 병목(서브 에이전트가 처음부터 생성하며 검토를 반복)과 같은 현상. PR#5는 서브 에이전트가 파일 쓰기만 하도록 바꿔 이 반복 루프를 제거하는 방식. 부수적으로 문제 5(스크린샷 미반영)에도 **간접** 대응 — PR#5의 `03-reference.html` 템플릿이 "스크린샷 data URI"를 전제하므로, 메인이 그 템플릿을 채우는 한 상대경로로 빠질 여지가 줄어든다(단 메인이 실제로 base64를 채우는지 검사는 여전히 없음)
| **#6 (고치기 입구 + preserve 기본 경로)** | 이 베이스라인의 관찰 범위 밖. 베이스라인은 "처음부터 만들기" 경로만 실행했고, PR#6이 다루는 "이미 있는 화면을 고치는 경로"는 이 실험에서 거치지 않았음

**이 베이스라인에서 관찰된 문제 중 위 세 PR 어디에도 해당하지 않는 것**: 스킬 자동 트리거 안 됨(문제 1), AI의 40초 방향 확정(문제 2), 저장 UX 결함(문제 3), 진행 메시지/링크 혼동(문제 4), 조사 자료 미반영(문제 5), 결과물의 AI 느낌(왼쪽 색띠·가짜 상태바, 문제 7 중 레이아웃 파손 외 부분), Figma 없이 결과물 단계가 빈 것(문제 9).
