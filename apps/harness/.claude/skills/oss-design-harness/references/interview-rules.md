# 인터뷰 규칙 — 디자인 초보 사용자용

대상은 "디자인을 한 번도 해본 적 없고, 무엇을 고려해야 하는지 모르는" 사용자다. 이 사람은 미적 어휘가 없고, 사용자 플로우를 머릿속으로 그려본 적이 없으며, 자기 취향을 말로 설명하지 못한다. 그래서 **묻는 대신 보여주고, 고르게 하고, 가리키게 한다.**

## 공통 규칙

| 규칙 | 이유 |
|---|---|
| 한 라운드 질문 최대 4개 | 초보자는 5개 넘으면 앞 질문을 잊는다 |
| 추천 옵션을 첫 번째에, `(추천)` 표시, 한 줄 근거 | 고를 게 없으면 추천을 고르면 된다는 안전망 |
| 모든 질문에 "모르겠어요 / 알아서 해주세요" | 막히지 않게. 선택 시 기본값 + brief.md 가정 로그 |
| 질문 앞에 "이걸 정하면 ○○가 달라집니다" 한 줄 | 왜 묻는지 모르면 대충 답한다 |
| 라벨형 질문 금지 (모던/미니멀/고급스러운/깔끔한) | 어휘 이해가 다르다. 시안으로 대체 |
| 다이어그램 금지 | 박스+화살표도 전문 표기법. 시나리오 문장 + 클릭형 로우파이로 대체 |
| 보여주는 모든 화면에 번호 라벨 ①②③ (화면당 최대 5개) + 페이지 안 의견 패널 | 사용자는 위치를 설명할 어휘가 없다. 번호 칩을 눌러 저장하게 하고 스킬이 읽어온다. 터미널에 번호를 적게 하지 않는다 |
| 한 번에 화면 하나, 회색 박스 나열 금지 | 와이어프레임 열몇 장은 초보자에게 전문 표기법이다. 투어형으로 한 장면씩 |
| 자유서술 원문 보존 | brief.md에 원문 → 그 옆에 역추출 기준. 섞지 않는다 |
| 확정된 것은 다시 묻지 않는다 | 반복 질문은 신뢰를 깎는다. design/ 파일이 기억이다 |
| 위치·배치 요청은 대상·기준·순서로 되풀이 확인 | "위로 올려줘"는 최소 두 가지로 해석된다 (docs/desingissue.md §4) |

## 역추출 방법

사용자의 자유서술에서 판단 기준을 뽑는 패턴. 원문은 그대로 두고 기준은 따로 적는다.

| 사용자 원문 예 | 역추출 기준 | 반영되는 규칙 항목 |
|---|---|---|
| "B는 너무 빡빡해요" | 정보 밀도: comfortable 이상 선호 | spacing scale, 카드 패딩, 목록 행 높이 |
| "A가 제일 무난한데 심심해요" | 무채 기본 + 강조색 1개 원함 | accent 성격, CTA 색 |
| "③ 버튼이 튀어요" | 버튼이 위계에서 너무 강함. secondary 톤 다운 | 버튼 variant 위계 |
| "여기서 뭘 눌러야 할지 모르겠어요" (로우파이) | 그 화면의 primary action이 안 보임 | 화면당 primary CTA 1개, 위치 고정 |
| "썸네일이 잘리는 게 싫어요" | 이미지 목적: 전체 확인 → contain | 이미지 맞춤 규칙 |
| "저 서비스 카드는 좋은데 색은 싫어요" | 카드 형태(radius/shadow)만 가져오고 팔레트는 별도 | 형태 축 확정, 색 축은 열어둠 |

## 1단계 — 구조 (PRD 빈구멍 채우기)

PRD를 읽고 **먼저 표를 만든 다음** 빈 칸만 묻는다. 사용자에게 "화면 목록을 말해주세요"라고 하지 않는다.

1. 화면 인벤토리 표를 만든다. 열: 화면명 / 목적(한 줄) / 진입 경로 / 주요 액션 1개 / 부가 액션 / 데이터 종류(목록·상세·폼·캔버스) / 상태(초기·빈·로딩·성공·실패·비활성 중 PRD에 언급된 것).
2. 빈 칸을 세고, 아래 우선순위대로 **허브 첫 탭 "구조" 설문**에 질문으로 넣는다(상한 7개, 각 질문은 추천값이 선택된 상태, 탭 상단은 "추천대로 할게요 / 다르게 할래요"). 스펙은 `structure-survey.md`. 설문 저장이 0건일 때만 터미널로 **최대 4개씩** 묻는다.
   - 진입점: 사용자가 맨 처음 보는 화면은 무엇인가 (로그인 유무 포함)
   - 핵심 작업: 이 제품에서 사용자가 가장 자주 반복하는 행동 1개
   - 플랫폼: iOS / Android / 둘 다 (기본값: 둘 다, 디자인은 iOS 기준 1벌 + Android 차이는 규칙에 메모)
   - 태블릿·가로 모드 지원 여부 (기본값: 세로 전용, 태블릿 미지원)
   - 하단 내비: 탭바 필요 여부와 탭 개수 (기본값: 3~5개 탭바, 화면이 3개 이하면 탭바 없음)
   - 빈 상태: 데이터가 0개일 때 무엇을 보여줄지 (기본값: 안내문 + 첫 액션 버튼)
   - 실데이터 범위: 제목은 얼마나 길어지나, 항목은 몇 개까지 (기본값: 제목 2줄 말줄임, 항목 무제한 스크롤)
   - 다국어 여부 (기본값: 단일 언어)
3. PRD에 없지만 거의 항상 필요한 것은 묻지 않고 **가정으로 추가**한다: 로딩 상태, 실패 상태, 빈 상태, 긴 텍스트, 항목 0/1/많음. brief.md 가정 로그에 남긴다.
4. 완성된 표를 설문 탭 안에 그대로 보여주고, 표 아래 "빠진 화면 있어요" 자유 입력 1개만 둔다. 사용자가 "다 봤어"라고 하면 `read_db`로 읽어 brief.md §1을 채운다.

## 2단계 — 플로우

`lofi-flow.md` 참고. 요약:

1. 1단계의 핵심 작업 1~3개마다 시나리오 문장을 쓴다. 2인칭, 현재형, 화면 이름 대신 "보이는 것"으로. 예: "앱을 열면 지난번에 만든 결과물들이 격자로 보입니다. 오른쪽 위 '새로 만들기'를 누르면…"
2. `probe-renderer`에 KIND=flow로 위임해 "따라가 보기" 투어를 Artifact로 띄운다(장면별 폰 1개, 상태 세그먼트, 의견 패널). 반환된 장면↔화면↔영역 대응표를 보관한다.
3. 사용자에게 링크만 주고 "다 보시면 말씀해 주세요". 사용자가 "다 봤어"라고 하면 `read_db`(collection `feedback`)로 장면별 👍🤔👎·번호·원문을 읽는다. 0건일 때만 "막힌 장면 / 순서 이상한 곳" 두 가지를 터미널로 묻는다.
4. 답을 brief.md §플로우에 원문 + 수정된 시나리오로 남긴다. 👎·🤔 장면만 고쳐서 다시 보여준다.

## 3단계 — 레퍼런스·취향

`taste-axes.md`, `probe-page.md` 참고. 순서:

1. 스킬이 경쟁 앱 3~5개를 찾아 레퍼런스 페이지로 보여준다 (`reference-sourcing.md`). 사용자는 번호로 "가져올 것 / 안 가져올 것 / 이유"만 답한다. 사용자가 가진 캡처가 있으면 같은 페이지에 추가한다.
2. 고정 5축을 순서대로 시안화한다. 앞 축의 확정값을 뒤 축 시안의 고정값으로 쓴다.
3. 프로젝트 도메인에 따라 추가 축을 0~2개 붙인다 (예: 이미지 도구 → 캔버스 배경 톤, 썸네일 밀도).
4. 반응은 축당 페이지 안 의견 패널(가장 좋은 것 / 가장 싫은 것 / 번호 칩 / 이유)로 저장받고 `read_db`로 읽는다. 한 페이지 축 2개.

## 4단계 — 규칙

`design-rules.md` 참고. 순서:

1. 기본값 표를 복사해 `design/design-rules.md`를 만들고 1~3단계 결과로 덮어쓴다. 덮어쓴 항목은 출처(어느 단계, 어떤 원문)를 적는다.
2. 규칙 미리보기 HTML을 만들어 Artifact로 띄운다. 섹션마다 번호 라벨 + 의견 패널.
3. 저장된 의견을 `read_db`로 읽어 👎·🤔 섹션만 다룬다. 그 섹션에만 국소 질문 허용.
4. `status: confirmed` 기록.

## 라운드 마무리 문장

각 단계가 끝날 때 사용자가 **답한 것**과 **가정한 것**을 두 묶음으로 나눠 보여준다. 가정 묶음이 수정이 들어올 자리다. 수정이 오면 반영해서 다시 보여준다. 수정된 요약을 확인받기 전에는 다음 단계로 가지 않는다.
