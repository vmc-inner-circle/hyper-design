# 레퍼런스 소싱 — 스킬이 경쟁 앱을 직접 찾는다

사용자에게 "좋아하는 앱이 있나요"라고 묻지 않는다. 디자인 초보는 무엇을 봐야 하는지 모른다. 스킬이 PRD 도메인의 경쟁 앱을 찾아 **무엇을 보라고 번호로 짚어주고** 반응만 받는다.

## 1. 검색

1. brief.md §1에서 도메인 키워드 3개를 뽑는다 (예: 이미지 편집, AI 필터, 썸네일 그리드).
2. WebSearch로 `<키워드> 앱 추천 2026`, `best <keyword> app iOS`, `<keyword> app store` 3~4회 검색. 앱스토어·플레이스토어 링크가 있는 앱만 후보.
3. 후보 8~10개에서 3~5개를 고른다. 선정 기준:
   - 같은 핵심 작업(1단계 핵심 작업)을 하는 앱 2개 이상 — 직접 경쟁
   - 다른 도메인이지만 같은 컴포넌트 문제(썸네일 그리드, 하단 CTA, 바텀시트 옵션)를 잘 푼 앱 1~2개 — 간접 레퍼런스
   - 스타일이 서로 다른 앱을 섞는다 (라이트/다크, 밀도 높음/낮음). 취향 축의 대비를 미리 보여주기 위해
4. 앱마다 "왜 골랐는지" 한 줄과 "볼 곳" 컴포넌트 2~3개를 적는다.

## 2. 스크린샷 수집

우선순위 순서로 시도한다. 가능한 방법 하나면 된다.

1. **앱스토어 페이지 스크린샷**: Chrome 도구가 있으면 `apps.apple.com/kr/app/...` 페이지를 열어 스크린샷 캐러셀 영역을 캡처한다. 앱당 2~4장.
2. **WebFetch로 스토어 페이지의 이미지 URL 추출** 후 curl로 다운로드.
3. 둘 다 안 되면 스크린샷 없이 앱 이름·링크·"볼 곳" 텍스트만으로 레퍼런스 페이지를 만들고, 사용자에게 링크를 직접 열어보라고 한다. 이 경우 brief.md 가정 로그에 "스크린샷 미확보"를 남긴다.

파일은 `design/references/<앱이름>-<n>.png`. 장당 폭 390으로 리사이즈(`sips -Z 390` 또는 Python). 출처 URL을 brief.md §3에 남긴다. 스크린샷은 내부 비교용이며 산출물에 재배포하지 않는다.

## 3. 페이지 구성 (probe-renderer KIND=reference)

- 앱당 섹션 1개: 이름 · 스토어 링크 · 선정 이유 한 줄 · 스크린샷 2~4장 가로 배치
- 각 스크린샷 위에 컴포넌트 번호 라벨 오버레이: 앱바 / 탭바 / 카드·썸네일 / primary 버튼 / 옵션 시트 / 색 / 글꼴 중 그 앱에서 볼 만한 것만
- 라벨 지도: `앱A-① 탭바`, `앱A-② 썸네일 그리드` 형식

## 4. 반응 받기 (페이지 안 의견 패널)

스킬이 **추천 앱 3개**(직접 경쟁 2 + 겹침·달력 같은 핵심 컴포넌트를 잘 푼 간접 1)를 정해 위에 펼치고, 각 앱에 "가져오면 좋을 번호" 2~3개를 미리 선택해 이유 한 줄을 붙인다. 나머지 앱은 "나머지 n개 보기"로 접는다. 앱 섹션마다 패널은 "추천대로 할게요 / 다르게 할래요" 두 버튼, "다르게"일 때만 가져올 번호·싫은 번호·이유가 펼쳐진다 → `feedback/app-<영문이름>`. 사용자가 "다 봤어"라고 하면 `read_db`로 읽는다. 0건일 때만 터미널로 "가져오고 싶은 번호 / 싫은 번호 / 이유 / 따로 가진 캡처" 네 가지를 묻는다.

## 5. 기록·역추출

brief.md §3 표에 앱·번호·원문·가져오는 것/안 가져오는 것을 적는다. 역추출은 컴포넌트 단위로만 한다: "앱B-③ 카드 좋다" → 카드 형태(radius·shadow)를 축 3 시안의 한 후보로 반영. **앱 전체 스타일을 따라 하지 않는다.** 가져온 컴포넌트 값은 취향 시안(3단계 뒤 절반)의 A/B/C 중 하나로 들어가서 다시 검증받는다.

## 6. 하지 않는 것

- 앱 5개 초과. 초보자는 비교 대상이 많으면 답을 못 한다.
- 스크린샷 없이 앱 이름만 나열하고 "아시죠?"라고 묻기.
- 경쟁 앱의 브랜드 색을 accent 후보로 그대로 제안하기. 색은 축 4에서 따로 고른다.
