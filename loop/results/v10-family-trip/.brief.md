## 원칙
1. 이해가 먼저, 예쁨은 나중. 화면마다 핵심 메시지 한 문장. 설명 문구로 이해시키는 UI는 실패다.
2. 기능을 만들기 전에 여정부터. 요구사항을 새 버튼·새 화면으로 바꾸기 전에 기존 행동의 부산물로 풀 수 있는지 본다(예: "확정하면 곧 공유"). 항목마다 요약·설명을 따로 쓰게 하는 입력칸도 새 할 일이다. 사용자에게 새 할 일(보내기·정리하기)을 얹는 해법은 마지막 수단. 메신저·지도·예약·결제처럼 이미 쓰는 앱이 하는 일은 하지 않는다.
3. 사람을 역할 이름으로 나누지 않는다. 모두 같은 기본 화면을 보고, 권한이 있는 사람에게 요소가 더 붙는다. "보기만·읽기 전용·게스트·확인만" 같은 수동적 호칭 금지.
4. 덜어낸다. 모든 섹션은 "누구를 위해, 언제 보는가"가 있어야 한다. 같은 목적의 버튼 중복 금지. 데이터가 빈약한 통계·장식 금지.
5. 뻔한 게 이긴다. 국내 대중 앱 골격(회색 바탕 + 흰 블록, 큰 제목, 64px 목록 행, 56px 하단 버튼). 한 화면에 한 가지 일.
6. 하단 고정 CTA는 폼·확인·결정·결과 화면에만. 홈·탭 첫 화면에는 두지 않는다. 문구는 확정 동사(저장·보내기·함께하기) — "~보기"는 링크. 상황에 따라 생기는 할 일은 해당 블록 안 인라인 버튼으로, 할 일이 있을 때만.
7. 색·글자·여백은 파운데이션 토큰만. 인라인 style·색 값 하드코딩 금지. COMPONENTS.md의 클래스만 조합한다.
8. 채워진 버튼은 흰 글자.
9. 배지는 뜻마다 다른 색, 앱 전체에 하나의 표: 확정 is-brand / 바뀜 is-warning / 궁금해요 is-info / 완료 is-success / 마감 지남 is-danger / 후보 회색. 시간·순서(지금·다음·~까지)는 배지가 아니라 글자. 아직 정하지 않은 것(추천·후보)에 확정 색 금지. 선택 상태(칩·세그먼트·체크·스위치)는 전부 브랜드 색 하나.
10. 아이콘은 용도로: 사물·주제 = 컬러 일러스트(assets/fluent/), 누르는 것(+·뒤로·›·체크·스위치) = 선 아이콘, 사람 = 아바타. 체크리스트는 왼쪽 일러스트·오른쪽 체크. 오류 문구에는 경고 아이콘. 유니코드 이모지 금지.
11. 한국어 조판: 제목은 짧게. 더미 데이터는 PRD 맥락의 실제 같은 이름·날짜·장소.
12. 탭바는 목적지가 3곳 이상일 때만. 이 앱은 탭바 없음 — 홈 한 장에서 블록으로 들어간다.
13. PRD의 동사마다 조작 수단이 있어야 한다. 적기·고치기·추가·지우기·순서 바꾸기·나누기 → 목록 끝 "+ 추가" 행, 끌기 손잡이, 편집 화면의 "지우기".
14. 입력 순서: 뒤 입력의 규칙을 바꾸는 선택은 앞에. 필수 입력은 실행 버튼보다 위. 선택지에는 빠져나갈 답을 둔다.
15. 오류 상태는 같은 화면·같은 요소에서 문제 칸만 바뀐다. 밖으로 내보내는 행동(링크·초대·공유)은 결과 표시(--done 상태)가 있다.
16. 권한으로 요소가 붙는 화면은 두 모습을 다 그린다(home / home-edit).
17. 사용자에게 보이는 모든 글은 한국어.
비평(반드시 피할 것): 누른 뒤 갈 곳 없는 버튼, 하단 CTA가 마지막 내용 가림(has-cta), 선택 상태 두 모양, 시간을 배지로, 설명 카드 반복(화면당 부가 설명 1개, "~를 누르면" 조작법 설명 금지), 한 번뿐인 행동의 눌린 뒤 모습 없음, 오류 문구가 화면에 없는 선택지를 가리킴.
