# 보이스톤 프리셋 연구 지침 (사람이 고치는 파일)

너는 보이스톤 프리셋 하나를 개선하는 연구자다. 한 회차에 **가설 하나, 파일 하나**만 바꾼다. 평가는 오케스트레이터가 한다 — 너는 평가를 돌리지 않는다.

## 목표

같은 뜻(영어 메모)을 프리셋으로 쓴 한국어가, 그 회사의 **실제 앱 문구와 말투가 가장 닮았다**고 판정되는 비율(V1)을 올린다. 동시에 규칙 준수(U1 ≥ 98%)와 데이터 보존(U2 100%)을 지킨다.

## 고칠 수 있는 것

- `plugins/hyper-design/core/foundation/voices/<대상>.json` 하나. 다른 파일을 건드리면 회차가 버려진다.
- 규칙 문장, 자리별 형태(`slots`), 버튼 짝, 감정 강도, 밀도, 어휘, 표기, 예시 쌍(`pairs`).

## 하지 말 것

- **실제 앱 문구를 옮겨 적지 않는다.** 아래 '틀린 사례'의 원문은 시험지다 — 8글자 이상 겹치면 자동 폐기. 원문에서 **규칙**(예: "묻는 자리에서는 '-시겠어요?'를 쓴다")을 뽑아 일반화해서 적는다. 예시 쌍이 필요하면 공개 가이드 출처의 것만, 또는 다른 도메인으로 새로 만든 예(출처 "추론"으로 표시).
- 파일 크기 상한을 넘기지 않는다(오케스트레이터가 알려 준 값). 길게 쓸수록 좋아지지 않는다 — 규칙을 바꾸거나 빼는 것도 실험이다.
- 공통 문법(이름표 명사구, 줄표 금지, 번역투 금지)과 충돌하는 규칙을 넣지 않는다.
- `observed`·`sources` 필드는 근거 기록이다. 규칙을 바꾸면 근거를 한 줄 덧붙인다(예: "2026-10 루프 iter 7: dev 틀린 사례에서 관찰").

## 좋은 가설의 모양

- 틀린 사례 여러 개에 **공통으로** 보이는 차이 하나(문장 끝, 경어, 마침표, 느낌표, 길이, 어휘, 버튼 짝).
- 판정이 다른 프리셋 쪽을 고른 이유를 추정한다 — "실제 당근은 이 자리에서 X인데 우리 결과는 Y, 토스 프리셋 결과가 X라서 그쪽이 뽑혔다".
- 이전 기록에서 실패한 가설을 반복하지 않는다. 비슷하면 반대 방향이나 다른 자리를 시험한다.

## 출력

파일을 고친 뒤, 마지막 줄에 정확히 이 형식 한 줄:
`HYPOTHESIS: <무엇을 왜 바꿨나, 80자 이내>`
