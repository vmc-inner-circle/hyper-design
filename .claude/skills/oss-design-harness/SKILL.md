# oss-design-harness

PRD 하나로 **클릭되는 HTML 프로토타입**과 **화이트보드 캔버스**를 만든다. 캔버스에는 화면 전체 흐름이 화살표로 이어져 있고, 다른 화면으로 넘어가는 버튼은 빨간 테두리로 표시된다. 지침(왜 이렇게 만들었는지)은 `brief.md`에 남긴다. 사용자는 Excalidraw 도구로 화면 위에 적고 그리고, 에이전트는 그 표시가 가리키는 **요소**(`data-id`)를 정확히 알고 고친다.

## 개입 예산 — 5회

사용자 메시지는 PRD를 포함해 **최대 5번**이다. 사용자는 인터뷰에만 답하고, 인터뷰가 끝나면 캔버스까지 AI가 혼자 간다.

| 단계 | 사용자가 하는 일 | 에이전트가 하는 일 |
|---|---|---|
| 1턴 | PRD를 넣는다 | PRD 분석·범위 검토 → 첫 질문 (§1) |
| 2턴~ | 번호별로 짧게 답한다 | "만들어도 되나" 점검 → 모자라면 다음 질문, 충분하면 생성으로 (`references/interview.md` §8) |
| 생성 | (개입 없음) | 인터뷰 문서 → 화면 목록 → 토큰 → 컴포넌트 → 화면 → 자체 점검 → 캔버스 (§2) |
| 남으면 | (선택) 캔버스 코멘트 → "피드백 남겼어" | 반영 (§3) |

- **인터뷰 상한**: 답 4턴(PRD 포함 5회). 사용자가 PRD와 **별도로** "연습"이라고 적었을 때만(PRD 본문 안의 단어는 해당 없음) 연습 모드로 답 10턴까지 — 연습 모드는 개입 5회 규칙을 적용하지 않는다.
- 턴 수는 정해 두지 않는다. 답을 받을 때마다 점검해서 충분하면 바로 생성한다. 상한에 닿으면 남은 빈칸은 가정으로 두고 생성한다.
- 질문 메시지 끝에 남은 답 기회를 한 줄로 알린다 (예: `남은 답 기회 2번 — 충분해지면 더 묻지 않고 바로 만들어요`).
- 확인만 받는 질문("이대로 진행할까요?")은 금지. 한 턴이 통째로 날아간다.
- 질문은 `AskUserQuestion` 같은 선택 UI를 쓰지 않고 **채팅 본문**으로 한다.

## 산출물 위치

```
design/                  # 작업 폴더 (gitignore)
  brief.md               # PRD 분석, 범위 검토, 턴별 질문·답 원문, 지침 목록(G1..), 화면 목록, 가정 로그 — templates/brief.md 복사
  prd-review.json        # 답 → PRD 판단(덜어냄·다음 버전·핵심·명확화·유지 J1..) — templates/prd-review.json 복사
  prd-updated.md         # 판단을 반영한 PRD 사본 (원본 PRD는 수정하지 않음)
  theme.js               # 토큰: Basecoat 기본값 위에 근거 있어 바꾸는 값만(주로 색·radius), 값마다 근거 G — templates/theme.js 복사
  components.md          # 강조 위계 P1~P4 + 공통 컴포넌트: data-id·Basecoat 컴포넌트·변형·상태 + HTML 조각 — templates/components.md 복사
  screens/*.html         # 화면 1장 = 파일 1개. 화면끼리 <a href>로 연결 → 그대로 프로토타입
  board.json             # 보드 구성: 화면·기기·줄·화살표 (schema/board.schema.json)
  index.html             # 프로토타입 보기 페이지 (make_prototype.py가 만든다 — 직접 쓰지 않음)
  feedback.json          # 캔버스가 저장한 피드백 — 에이전트는 이것만 읽는다 (schema/feedback.schema.json)
  canvas-state.json      # 캔버스 복원용 (읽지 않음)
  prompt-log.md          # 사용자 메시지 원문 기록
  started_at.txt         # 시작 시각
submissions/{github_id}/ # 마무리 때 복사 (제출물)
```

## 0. 시작 (PRD를 받은 즉시, 묻지 않고)

1. `design/`이 이미 있으면 지우지 말고 `design.prev-{YYYYMMDD-HHMM}/`으로 이름을 바꾼다(지난 실행 결과가 섞이지 않게). `submissions/{github_id}/`는 건드리지 않는다. 그다음 `design/`을 만들고 현재 시각을 `design/started_at.txt`에 적는다. `{github_id}`는 `git remote get-url origin`의 소유자(`github.com/{소유자}/…`)로 정한다 — git user 이름과 다를 수 있다. origin이 없으면 git user 이름.
2. `design/prompt-log.md`를 **제출 형식 그대로**(`submissions/README.md`) 만든다 — 맨 위에 `# prompt-log — {github_id}`, `- 하네스: …`, `- 모델·에이전트: …`, `- 총 개입 횟수: 1 / 5`, 그 아래 `## 1회 (PRD 입력)` + PRD(파일명 또는 "PRD 원문 그대로"). 이후 **사용자 메시지를 받을 때마다** `## n회` 제목으로 원문을 즉시 추가하고 `총 개입 횟수`를 같이 올린다. 에이전트 판단은 `> (에이전트 판단)` 줄로 원문과 나눈다.
3. `templates/brief.md`를 `design/brief.md`로 복사한다.

## 1. PRD 검토 → 질문 (R1 응답)

**실무 킥오프에서 기획서를 검토하는 디자이너**처럼 묻는다. 디자인안을 먼저 내밀고 동의를 받지 않는다. 질문 틀·말투·점검 목록은 **`references/interview.md`**.

1. PRD를 읽고 `brief.md` §PRD 분석을 채운다: 사용자 역할, 역할별 핵심 과업, 화면 목록 초안, PRD가 "판단해주세요"라고 넘긴 지점, 빈 구멍.
2. `brief.md` §범위 검토를 채운다: 요구사항·유저스토리 문장마다 핵심 문제를 푸는지, 넣으면 화면이 몇 장 늘어나는지, 빠지면 누가 곤란한지, 두 가지로 읽히는지.
3. 화면에 가장 영향이 큰 것부터 **첫 턴 질문 1~3개**를 보낸다. 다음 턴을 할지, 무엇을 물을지는 답을 받은 뒤 `references/interview.md` §8로 정한다.

**무엇을 묻는가**
- 이해 확인을 먼저: 기획서에서 두 가지로 읽히는 곳, 서로 부딪히는 두 구절, 경계가 애매한 용어.
- 필요성 확인 **2개 이상**: 핵심 문제와 거리가 있는 요구를 첫 버전에 둘지, 필요하다면 이유가 무엇인지.
- 선호·분위기는 꼭 필요할 때만 1개.
- 묻지 않는다: 색상 값, 간격, 폰트, 아이콘, 이미지, 더미 데이터, 상태 처리 → AI가 정하고 `brief.md` 가정 로그에 남긴다.
- 모바일/PC는 PRD에서 판단한다. 애매할 때만 질문 하나에 넣는다.

**형식** — 질문마다 아래 순서. 질문 문장은 `references/interview.md` §3의 틀(두 구절 대조형·경계형·A인지 B인지형·필요성 + 이유형·조건 제시형) 중 하나로 쓴다.

```
## 1. [제목 — 무엇을 정하는 질문인지 짧게]

"[기획서 구절]"이라고 돼 있는데,
"[기획서 구절]"이라고 돼 있거든요.

제가 헷갈린 건,
[해석 1]인 건지,
아니면 [해석 2]인 건지예요.

어느 쪽으로 이해하면 될까요?

([어느 화면]의 [어느 부분]이 [어떻게] 달라집니다)

A. [해석·선택지]
B. [해석·선택지]
C. 직접 설명할게요
```

왜 이 순서인가: 답하는 사람은 기획서를 쓴 비전공자다. **자기 문장(인용) → AI가 어디서 걸렸는지 → 무엇을 묻는지 → 고르면 화면이 어떻게 달라지는지**를 차례로 읽고 나서야 선택지를 고를 수 있다. 달라지는 것이 선택지 뒤에 오면 이미 고른 뒤라 쓸모가 없고, 굵은 한 문단이나 한 줄에 붙은 선택지는 읽히지 않는다 (리허설에서 사용자가 두 번 고쳐 확정한 형식).

- 틀에 따라 가운데 문단만 바뀐다. 필요성 + 이유형은 "제가 헷갈린 건" 대신 "핵심 문제와 조금 떨어져 보여서요 + 넣으면 늘어나는 것" 문단 → "첫 버전에서는 ~까지만 하고, ~는 나중에 넣어도 괜찮을까요? 꼭 필요하다면 이유가 궁금해요." 문단. 순서(제목 → 인용 → 가운데 → 묻는 문장 → 괄호 → 선택지)는 같다.
- 한 줄은 한 문장 또는 한 생각. 채팅 창에서 두 줄을 넘기면 끊는다.
- 기획서 구절은 따옴표로만 인용한다. **§번호는 쓰지 않는다** (근거 절은 `brief.md` 질문 표에만).
- 질문을 한 덩어리 굵은 글씨로 쓰지 않는다. 인용 · 헷갈린 지점 · 묻는 문장 · 달라지는 것을 빈 줄로 나누고, 해석이 둘이면 한 줄에 하나씩.
- 달라지는 것은 라벨 없이 괄호 한 문장으로, **선택지 바로 위**에. 선택지는 글머리표 없이 `A.` `B.` `C.` 한 줄에 하나씩.

마지막에 두 줄: `번호별로 짧게 답해주세요 (예: 1-A, 2-B, 3-모르겠어요). 모르겠거나 질문이 헷갈리면 제가 정하고, 무엇을 가정했는지 화면을 보낼 때 함께 알려 드릴게요.` + 남은 답 기회.

- 괄호의 달라지는 것에는 **화면 이름과 요소**를 적는다. "카드 높이가 달라져요" 수준이 아니라 "○○ 홈 화면에 후보 카드가 보일지 말지가 달라집니다" 수준으로.
- 전문 용어에는 괄호로 쉬운 말을 붙인다.
- 보내기 전에 `references/interview.md` §6 점검 목록을 확인한다.

## 2. 인터뷰 종료 → 정의 → 화면 생성 (마지막 답에 대한 응답, 사용자 개입 없음)

1. 답을 `brief.md`에 **원문 그대로** 적고, 해석은 옆에 따로 적는다. "모르겠어요"·질문이 헷갈린다는 답은 다시 묻지 않고 AI가 정한 뒤 가정 로그에 남긴다.
2. **PRD 판단**: `templates/prd-review.json`을 `design/prd-review.json`으로 복사해, 답을 근거로 판단 `J1`, `J2`…(덜어냄·다음 버전·핵심·명확화·유지)을 적고 고친 PRD 사본 `design/prd-updated.md`를 쓴다. 규칙은 `references/interview.md` §7. 원본 PRD는 고치지 않는다.
3. **지침 목록**을 만든다: `G1`, `G2`… 한 줄씩, 출처(`J3 (Q2 답변)` / `PRD §4-3` / `가정`) 필수. 지침은 PRD 판단에서 뽑고, 덜어내거나 미룬 기능의 화면은 만들지 않는다. 화면은 이 지침으로만 설명된다.
4. **기기**를 정한다: 기본 `["mobile"]`. `references/screen-generation.md` §생성 순서 1의 신호가 있을 때만 `tablet`·`desktop`을 **화면별로** 더하고, 이유를 지침 G로 남긴다.
5. **정의 → 조립** 순서로 만든다. 규칙은 **`references/screen-generation.md`** §생성 순서. 앞 단계가 끝나기 전에 다음 단계 파일을 쓰지 않는다.
   1. 화면 목록: `brief.md` §화면 목록 (화면 × 기기 × 상태, 근거 G)
   2. 토큰: `templates/theme.js` → `design/theme.js` (바탕은 Basecoat 기본값, **근거 있어 바꾸는 값만**, 값마다 근거)
   3. 컴포넌트: `templates/components.md` → `design/components.md` (**공통 컴포넌트만**, 모양은 Basecoat 컴포넌트·변형, HTML 조각)
   4. 화면: 머리의 외부 자원(CDN)은 `schema/stack.json`의 active만 계층 순서대로, 공통 조각 + Basecoat로 조립 (모바일 우선 반응형, `data-devices`, `data-id` 2단계)
6. **정의 점검**: 화면이 토큰 이름만 쓰는지(기본 팔레트·임의 값 없음), 공통 컴포넌트가 조각과 같은지, `references/screen-generation.md`의 "쓰지 않는 것"에 걸리는 곳이 없는지 훑고 고친다.
7. `design/board.json`을 쓴다 — 형식은 `schema/board.schema.json`의 `examples`, 판단 규칙은 **`references/canvas.md`**. **`flows`(사용자 흐름 3~5개, 목적 한 문장 + 근거)와 화면별 `purpose`**를 넣는다. `rows`·`arrows`·`row`·`order`는 쓰지 않는다.
8. `design/index.html`: **직접 쓰지 않고** `python .claude/skills/oss-design-harness/scripts/make_prototype.py --root design`으로 만든다 — `templates/prototype.html`에 `board.json`을 넣은 보기 페이지(왼쪽 흐름·단계, 가운데 실제 크기 기기 틀 안에서 눌리는 화면, 모바일·PC 전환, 화면 제목·목적). 파일로 바로 열어도 된다. `board.json`을 고치면 다시 돌린다.
9. **자체 점검**: `python .claude/skills/oss-design-harness/scripts/check.py --root design`. `[FAIL]`이 있으면 고치고 다시 돌린다. 사용자에게 묻지 않는다.
10. 서버를 백그라운드로 띄운다: `python .claude/skills/oss-design-harness/canvas/server.py --root design --port 4321` (이미 떠 있으면 재사용).
11. 사용자에게 보낸다 — 짧게:
   - 캔버스 링크 `http://localhost:4321/` + 남은 개입 횟수 (0이면 이 응답에서 바로 §4 마무리까지 한다)
   - 사용법 3줄: 맨 위 흐름 지도로 전체를 보고, 흐름 줄 끝 완성본은 클릭해서 켠 뒤 직접 눌러 보기(PC 화면이 있으면 오른쪽 위에서 전체·모바일·PC 전환) / 화면 아래 노란 상자를 더블클릭해 피드백 적기 / 화면을 더블클릭하면 카드·버튼을 끌어 옮기거나 지울 수 있음(그대로 피드백이 됨), 빨간 테두리 버튼이나 화살표를 고르면 뜨는 "→ ○○ 화면으로 이동" 버튼으로 흐름 따라가기, 자동 저장 / 다 하면 채팅에 "피드백 남겼어", 고칠 게 없으면 "완성"
   - 만든 화면 수와 지침 요약 3줄
   - PRD에서 덜어내거나 미룬 것, 답 없이 가정한 것 (`prd-review.json` 기준, 한 줄씩)
12. **제출 폴더를 바로 만든다** — §4의 1~5를 이 응답 안에서 한다. 사용자가 "완성"이라고 하지 않고 끝나도 제출물이 남아야 한다. 이후 피드백을 반영하면 다시 덮어쓴다.

## 3. 코멘트 반영 (남은 개입이 있을 때만)

사용자가 "피드백 남겼어"라고 하면:

1. `design/feedback.json`을 읽고, **먼저 `board.json`의 `round`를 1 올린 다음** `feedback.json` → `feedback-r{n}.json`, `canvas-state.json` → `canvas-state-r{n}.json`으로 옮긴다 (n = 올리기 전 round). round를 먼저 올려야 열려 있던 페이지의 저장이 서버에서 거부되어 옮긴 피드백이 되살아나지 않는다. 각 항목의 텍스트와 대상(`screen · device · dataId`)을 `prompt-log.md`의 이번 회차에 붙인다.
2. 해석 규칙은 **`references/canvas.md`** §feedback.json 읽기. `items`는 대상 요소를 찾아 고치고(`move`·`remove`는 HTML 구조를 바꾼다), `renderChecks`(가로 넘침·작은 터치 요소 등)는 묻지 않고 고치고, `discovered`는 `board.json`에 넣을지 판단한다. 표시되지 않은 곳은 건드리지 않는다.
3. 피드백에서 새 지침이 나오면 `G` 번호를 이어 붙이고 출처를 `피드백 R3`처럼 적는다. `brief.md`의 지침 목록에 이어 적는다.
4. 여러 코멘트가 같은 방향 문제를 가리키면(예: 전체 분위기가 무겁다) `theme.js`나 지침 자체를 고친다.
5. `check.py` 통과 → `board.json`이 바뀌었으면 `make_prototype.py` 다시 → 제출 폴더를 다시 만든다(§4의 1~5) → 사용자에게 "피드백 → 어떻게 해석했고 무엇을 바꿨는지" 표를 보낸다. 캔버스는 `board.json`·화면 파일이 바뀌면 스스로 새로고침된다.

"완성"이라고 하거나 개입이 5회에 닿으면 반영 후 **반드시** 마무리로 간다.

## 4. 마무리

1. `{github_id}`는 §0-1과 같다 (origin 원격 소유자).
2. `submissions/{github_id}/`에 복사: `screens/`, `theme.js`, `index.html`, `board.json`, `components.md`, `brief.md`. 캔버스 코드는 복사하지 않는다 — 스킬 폴더의 서버가 `lib/`·`schema/`를 함께 준다.
3. `prompt-log.md`: `design/prompt-log.md`를 복사한다 — 회차별 원문(`## n회`), `총 개입 횟수: n / 5`(회차 수와 같게, 5 이하).
4. `elapsed.txt`: `started_at.txt`부터 지금까지, 세 줄 — `시작: YYYY-MM-DD HH:MM` / `종료: YYYY-MM-DD HH:MM` / `소요: N분`.
5. **점검**: `python .claude/skills/oss-design-harness/scripts/check_submission.py --root submissions/{github_id}` — `[FAIL]`이 없을 때까지 고친다 (index.html에서 이어지는 링크·theme.js, 개입 횟수, elapsed 형식).
6. 사용자에게 제출 폴더 경로와 소요 시간을 알린다. 프로토타입은 `index.html`(흐름별로 눌러 보는 보기 페이지)을 바로 열면 되고, 보드는 `python .claude/skills/oss-design-harness/canvas/server.py --root submissions/{github_id} --port 4322`로 다시 볼 수 있다고 적는다.

## 하지 않는 것

- 레퍼런스 수집·경쟁 앱 스크린샷 (현재 범위 밖)
- 스킬·템플릿에 특정 도메인(청첩장, 여행 등)의 이름·화면·데이터를 넣는 것 — 프로젝트 값은 `design/`에만
- 사용자 원문과 해석을 섞어 적는 것
