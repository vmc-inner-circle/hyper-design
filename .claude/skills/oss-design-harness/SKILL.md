# oss-design-harness v13

**PRD 한 장 → (PRD 요구사항을 뺄 때만) 확인 한 번 → 15분 안에 모바일 화면 + 캔버스.** 짧은 기획 브리프면 여정에서 10~16장, 화면을 나열한 명세서면 명세의 화면 전부. 사용자는 디자인을 모른다고 가정하고, 디자인·제품 결정은 하네스가 내리고 이유를 남긴다. 단, **PRD에 적힌 것을 빼거나 가볍게 바꾸는 결정만은 만들기 전에 사용자에게 확인**한다 — 그건 사용자의 권한이고, 빌드 뒤에 되살리면 비싸다.

모든 경로는 이 스킬 폴더 기준이다: `SK=.claude/skills/oss-design-harness`. 산출물은 `out/`.

## 원칙 (모든 서브에이전트 프롬프트에 그대로 붙인다)

1. **이해가 먼저, 예쁨은 나중.** 화면마다 핵심 메시지 한 문장. 설명 문구로 이해시키는 UI는 실패다.
2. **기능을 만들기 전에 여정부터.** 요구사항을 새 버튼·새 화면으로 바꾸기 전에 **기존 행동의 부산물**로 풀 수 있는지 본다(예: "확정하면 곧 공유"). 항목마다 요약·설명을 따로 쓰게 하는 입력칸도 새 할 일이다. 사용자에게 새 할 일(보내기·정리하기)을 얹는 해법은 마지막 수단. 메신저·지도·예약·결제처럼 이미 쓰는 앱이 하는 일은 하지 않는다.
3. **사람을 역할 이름으로 나누지 않는다.** 모두 같은 기본 화면을 보고, 권한이 있는 사람에게 요소가 더 붙는다. "보기만·읽기 전용·게스트·확인만" 같은 수동적 호칭 금지.
4. **덜어낸다.** 모든 섹션은 "누구를 위해, 언제 보는가"가 있어야 한다. 같은 목적의 버튼 중복 금지. 데이터가 빈약한 통계·장식 금지.
5. **뻔한 게 이긴다.** 국내 대중 앱 골격(회색 바탕 + 흰 블록, 큰 제목, 64px 목록 행, 56px 하단 버튼). 한 화면에 한 가지 일.
6. **하단 고정 CTA는 폼·확인·결정·결과 화면에만.** 홈·탭 첫 화면에는 두지 않는다. 문구는 확정 동사(저장·보내기·함께하기) — "~보기"는 링크. 상황에 따라 생기는 할 일은 해당 블록 안 인라인 버튼으로, 할 일이 있을 때만.
7. **색·글자·여백은 파운데이션 토큰만.** 인라인 style·색 값 하드코딩 금지. `$SK/foundation/COMPONENTS.md`의 클래스만 조합한다.
8. **채워진 버튼은 흰 글자.** (짙은 글자 버튼은 대비를 넘어도 버튼답지 않다 — 토큰이 알아서 처리한다.)
9. **배지는 뜻마다 다른 색, 앱 전체에 하나의 표**: 확정·핵심 `is-brand` / 바뀜·마감·겹침 같은 주의 `is-warning` / 실패·불가만 `is-danger` / 요청·안내 `is-info` / 완료 `is-success` / 실패 `is-danger` / 후보 회색. 표는 `screens.json`의 `badges`에 선언하고 그것만 쓴다(한 색에 뜻 하나). 시간·순서(지금·다음·~까지)는 배지가 아니라 글자. 아직 정하지 않은 것(추천·후보)에 확정 색 금지. **선택 상태(칩·세그먼트·체크·스위치)는 전부 브랜드 색 하나**. 배지 이름은 보는 사람이 아니라 **대상의 상태**다 — 누가 보든 같은 뜻("답 기다림"이 어떤 화면에선 내 차례, 어떤 화면에선 남의 차례면 실패).
10. **아이콘은 용도로**: 사물·주제 = 컬러 일러스트(`assets/fluent/`), 누르는 것(+·뒤로·›·체크·스위치) = 선 아이콘, 사람 = 아바타 — 인물 일러스트(mother·father·jieun·minsu·hayun)는 나이·관계가 맞을 때만, 나머지 사람은 글자 아바타(`avatar is-text`, 이름 첫 글자). 사물 일러스트를 사람 자리에 쓰지 않는다. 체크리스트는 왼쪽 일러스트·오른쪽 체크. 오류 문구에는 경고 아이콘. 유니코드 이모지 금지. **사진 자리에는 실제 이미지**(`assets/photos/`·`assets/domain/`) — "사진 1" 같은 글자만 든 빈 박스 금지.
11. **한국어 조판**: 제목은 짧게, 줄바꿈이 단어 중간에서 나지 않게(파운데이션이 `keep-all` 처리). 더미 데이터는 PRD 맥락의 실제 같은 이름·날짜·장소.
12. **탭바는 목적지가 3곳 이상일 때만.** 적으면 홈 한 장에서 블록으로 들어간다.
13. **PRD의 동사마다 조작 수단이 있어야 한다.** 적기·고치기·추가·지우기·순서 바꾸기·나누기 → 목록 끝 "+ 추가" 행, 끌기 손잡이, 편집 화면의 "지우기". 화면이 "있다"로 끝내지 않는다. **조작은 시작점까지 그린다**: "+ 추가"·"새 ~"는 다른 화면이나 시트로 이어지고(자기 화면 링크 금지), 사용자가 만드는 분류(무리·폴더·태그)를 고르는 칩이 있으면 그 분류를 만들고 이름 바꾸는 곳도 있다.
18. **규모가 보이면 찾기.** PRD에 수십 명·수십 개가 나오면 그 목록 맨 위에 검색 칸 + 걸러 보는 칩(`traits.large_list: true`). 제목이 "~ 23명"처럼 일부를 약속하면 화면도 그 23명만 보여 준다.
19. **사실은 한 번만 정하고 모든 화면이 인용한다.** 날짜·시간·인원·겹침·상태는 `journey.md`의 사실 표에만 있고, 화면은 그 표를 그대로 옮긴다. 같은 대상을 화면마다 다른 상태 이름으로 부르지 않는다.
14. **입력 순서**: 뒤 입력의 규칙을 바꾸는 선택(1:1인지, 누구와 함께인지 등)은 앞에. 필수 입력은 실행 버튼보다 위. 선택지에는 "다 안 돼요" 같은 빠져나갈 답을 둔다.
15. **오류 상태는 같은 화면·같은 요소**에서 문제 칸만 바뀐다(새 칸을 붙이지 않는다). **밖으로 내보내는 행동**(링크 만들기·초대·공유)과 **한 번 누르는 요청**(궁금해요·참석 답)은 `traits.shares` — 기본 화면에 누르기 전 모습, `--done`에 눌린 뒤 모습(+되돌리기). **권한 요청·대량 작업**(연락처 불러오기 등)은 거부·대기 처리를 화면 정책에 한 줄로.
16. **권한으로 요소가 붙는 화면은 두 모습을 다 그린다**(권한 없음 / 있음 — 예: `home`, `home-edit`).
17. **사용자에게 보이는 모든 글과 마지막 메시지는 한국어.**

## 진행 — 보통 한 턴, PRD 요구사항을 뺄 때만 두 턴

첫 줄에 한 문장으로 알린다: "바로 만들게요. 10분쯤 걸려요."

### 1단계 — 동시에 시작 (목표 3분)

- **맨 먼저(1초)**: `python3 $SK/scripts/save_prd.py out` — 붙여넣은 PRD 원문을 `out/prd.md`로 저장(파일로 받았으면 `--from <파일>`). 실패하면 그때만 직접 쓴다.
- **먼저 30초**: PRD에서 도메인(예: 여행·생활·커머스·교육·결혼)과 제품 성격 키워드 3개를 정한다 — 키워드는 라이브러리 어휘에서 고른다: 따뜻함·감성·친근·활기·선명·강렬·밝음·산뜻·신뢰·차분·고급·모노·에디토리얼·생활·여행·자연·건강·기록·커뮤니티. 도메인은 구체적으로(예: "뷰티,헤어", "운동,예약") — 라이브러리에 맞는 도메인이 없으면 승인된 브랜드 시드에서 색을 만든다(자동). 그리고 **감정 온도**: 축하·결혼·선물·돌잔치처럼 **설렘 자체가 제품의 핵심**이면 `warm`, 금융·업무·의료처럼 믿음이 핵심이면 `cool`, 여행·생활·가족 일상처럼 둘 다 아니면 비운다(대부분 비운다).
- **백그라운드로 즉시**: `python3 $SK/scripts/setup_out.py out --domain "<도메인>" --tags "<키워드,…>" [--temp warm|cool]` — 공통 파일 복사 + 팔레트 라이브러리(`$SK/foundation/palettes/`)에서 **기본 1 + 대안 2 자동 결정**. 사용자에게 색을 묻지 않는다.
- **같은 메시지에서 서브에이전트 1개 — 명세 목록**: `$SK/references/spec-mode.md`의 프롬프트로 `out/prd.md`에서 `out/spec_inventory.json`을 뽑는다(화면·단계·요소·규칙, 항목마다 원문 인용).
- **메인은 그동안** `out/journey.md`를 쓴다:
  - **여정표**: 시기(사용 전·중·후) × 사람 × {할 일, 궁금해지는 것, **막히는 순간**}. 궁금한 것은 "물어보기 미안한 사소한 것"까지. 막히는 순간(아무도 답이 없음·마감이 지남·전부 안 됨·거절)은 그 순간을 푸는 화면이나 상태로 이어져야 한다.
  - **범위**: 커버한다 / 커버하지 않는다(이유) / 경계(추천 결정). 사람 나누는 방식(권한).
  - **시나리오 데이터 표 + 사실 표**: 등장인물·주요 항목 3~5개, 그리고 화면에 나올 **모든 사실**(날짜·시간·인원 수·누가 어디에 속하는지·무엇이 무엇과 겹치는지·각 대상의 상태 이름)을 한 표에. 모든 화면이 이 표만 인용한다(원칙 19). 숫자를 쓰는 제목("23명")은 표에서 센 값.
  - **가정 로그**: 하네스가 대신 정한 것과 이유(팔레트 선택 이유 포함 — `out/palettes.json`의 why).
- 명세 목록이 오면 **병합**: 같은 화면의 탭·섹션으로 쪼개진 screen은 feature로 합친다. screen+step ≥ 15면 `mode: "spec"` — screen·step은 **전부 화면**이 된다(빼려면 1.5단계 결정 + 확인). 아니면 `brief` — 지금처럼 여정에서 화면을 끌어낸다. 각 항목의 `covered_by`(화면 id) 또는 `decision`을 채운다. rule은 `target`(화면 id)·`state`(error|confirm|done) 또는 `policy`(정책 문구로만 반영할 화면 id).
- 이어서 `out/screens.json`:

```json
{"groups": ["처음 들어올 때", "홈 — 시기마다 맨 위가 바뀐다", "…"],
 "story": {"headline": "이 앱이 PRD의 갈등을 푸는 방식 한 문장(<em>강조</em>)", "summary": "2~3문장",
           "ideas": [{"title": "", "desc": ""}]},
 "screens": [{"id": "home", "file": "screens/home.html", "title": "홈 · 출발 50일 전", "group": "…",
   "purpose": "한 줄", "role": "everyone|editor", "policies": ["화면 정책 1~3줄: 규칙·경계·엣지 케이스"],
   "branches": [{"to": "home-edit", "label": "갈래 조건"}],
   "traits": {"list_first_use": false, "form": false, "shares": false, "large_list": false, "long_task": false}, "kind": "home|list|detail|form|result"}],
 "photo_centric": false,
 "badges": {"확정": "is-brand", "바뀜": "is-warning", "요청": "is-info", "완료": "is-success", "후보": ""},
 "prd_coverage": {"F1": ["…"], "US1": ["…"]}}
```

  - 화면은 **여정의 궁금해지는 순간**에서 끌어낸다. 같은 화면이 시기에 따라 달라지면 별도 화면 id로(예: `home`, `home-d7`, `home-trip`).
  - `kind: "list"` 화면은 `large_list`(30개 넘게 쌓일 수 있나)를 반드시 적는다 — true면 검색 칸 필수(selfcheck).
  - **기본 화면만 쓴다. 상태 화면 항목·`states`는 손으로 쓰지 않는다** — `expand_states.py`가 traits와 명세 규칙에서 펼친다: 목록 + 첫 사용 → `empty`, 폼 → `error`, 밖으로 내보내는 행동·한 번 누르는 요청 → `done`, 사용자가 지켜봐야 하는 긴 작업(사진 여러 장 업로드 등, `long_task`) → `progress`, 명세 규칙 → 그 규칙의 `error`(같은 요소 오류) 또는 `confirm`(되돌릴 수 없음·중복 경고 대화상자). `loading`·`success`는 상태가 아니다. 화면당 상태 2개 이하(기본 포함 3) — 넘으면 규칙을 정책 문구로 내린다.
  - `photo_centric`: 사진·이미지가 사용자가 만들거나 보는 **핵심 콘텐츠**면 true.
  - `branches`는 **갈래에만**(조건에 따라 다른 곳으로 가는 경우). 순서대로 이어지는 흐름은 적지 않는다 — 캔버스가 배치로 보여준다.
  - brief는 10~16장(하한을 채우려고 늘리지 않는다). spec은 명세 목록대로 — 명세에 없어도 여정의 시기별 변형(예: 단계별 홈)은 그대로 끌어낸다.

### 1.5단계 — 제품 판단: 가장 중요한 것만 남긴다 (목표 2분)

**같은 메시지에서 함께**: `python3 $SK/scripts/expand_states.py out`(상태 펼치기, 실패하면 규칙을 정책으로 내리고 다시) + **이미지 서브에이전트 1개**(`$SK/references/images.md`의 프롬프트, 사진·그림 자리가 하나라도 있으면). 이미지 에이전트는 자리표시 파일을 먼저 만들고 경로를 돌려준다 — 빌드는 기다리지 않고 그 경로를 쓴다.

`out/decisions.json`:
```json
{"core": "이 앱이 푸는 단 하나의 갈등 한 문장",
 "items": [{"id": "F5", "name": "변경 사항 전달", "source": "PRD|여정|하네스",
            "verdict": "keep|lighten|cut|later", "how": "가볍게 바꾼다면 어떻게(예: 알림 대신 '바뀜' 표시)",
            "why": "판단 이유 한 줄", "ask": true}]}
```
- 후보 = PRD의 기능·유저스토리 + 여정표에서 떠오른 것 + 하네스가 떠올린 것. 각각 다섯 질문에 답해 판정한다:
  1. 핵심 갈등을 푸는가 2. **이미 쓰는 앱·통로(카톡·전화·지도·예약 앱)가 하는가** 3. 누구에게 새 할 일·새 알림이 생기는가 4. 없으면 무슨 일이 생기나(빈도 × 피해) 5. 더 가벼운 형태로 대신할 수 있나
- **core를 푸는 기능은 keep이고, 사용자가 결정하는 화면에 반드시 보인다**(예: "겹치지 않게 확정"이 core면 겹침은 후보 화면뿐 아니라 확정 화면에도). core 기능을 lighten하면 그 결정은 사실 표와 모든 화면에 같은 방식으로 반영한다.
- **요구사항은 문구가 아니라 의도를 충족한다**(예: "변경 사항 전달"의 의도 = 묻지 않아도 안다 → 알림 대신 열면 보이는 표시로 충족 가능). 대신 근거를 남긴다.
- **반대 입장 서브에이전트 3개를 한 메시지에 병렬로**: 여정표의 주요 사람 둘(각자의 하루를 따라가며 "이건 귀찮다/이건 꼭 필요하다") + "30%를 빼야 하는 PM". 각자 장부 초안에 반박만 돌려준다. 판정은 메인이 다섯 질문 기준으로 한다.
- **확인이 필요한 것** = `source: "PRD"` 이면서 `cut` 또는 `lighten`인 항목(`ask: true`). 하네스가 떠올렸다가 뺀 것은 묻지 않는다(캔버스에만 공개).
- **확인이 필요 없으면** 바로 2단계로. **필요하면** 여기서 턴을 끝낸다(최대 3개, 영향 큰 순). 형식:

```
만들기 전에 이렇게 정했어요. 괜찮으면 "그대로", 다시 넣을 게 있으면 번호만 알려주세요.
1. (무엇이 달라지는지 쉬운 말로 한 문장) — (이유 한 줄)
2. …
[[ASK]]
```
  전문 용어 금지. 답을 받으면 되살릴 번호는 `verdict: keep`으로 바꾸고 2단계로.

### 2단계 — 병렬 빌드 (목표 4분)

- 서브에이전트 **ceil(전체 화면 수 / 5)개(최대 8)를 한 메시지에** 띄워 나눠 맡긴다(같은 흐름끼리, 상태 화면은 기본 화면과 같은 에이전트). 각자 자기 파일만 쓴다.
- 각 에이전트에게 붙이는 것: 위 **원칙 전문**, `$SK/foundation/COMPONENTS.md` 전문, `out/journey.md`의 시나리오 데이터 표, 맡은 화면의 screens.json 항목, 모범 답안 경로 `$SK/foundation/examples/*.html`(구조만 참고).
- 각 에이전트에게 맡은 화면의 **명세 항목**(spec_inventory의 covered_by·rule — PRD 원문 인용 포함)과 **이미지 자리 경로**(`image_slots.json` 중 그 화면 것)도 붙인다. 상태 화면은 `rules`에 적힌 규칙이 보이는 모습으로.
- 각 에이전트에게 **사실 표**도 붙이고 "표에 없는 날짜·숫자·상태를 지어내지 말 것"을 지시한다.
- 파일: `out/screens/<id>.html` — COMPONENTS.md의 뼈대 그대로(`../tokens.css`·`../components.css`·`../palette.js`, 일러스트 `../assets/fluent/<이름>.svg`). 갈래·이동은 실제 `<a href>`로 잇는다.

### 3단계 — 검증·수정 (목표 3분, 동시에)

한 메시지에서 동시에(**포그라운드로 실행해 같은 턴에서 결과를 받는다 — 백그라운드로 돌려 놓고 "끝나면 알려드릴게요"로 턴을 끝내지 않는다. 턴이 끝나면 다시 이어지지 않는다**):
- `python3 $SK/scripts/build_canvas.py out` — 캔버스 `out/index.html`(Screens·Foundation·Components 탭, 드래그 이동, 색 점 3개, 갈래 화살표, 정책 3줄 — 스크립트가 만들고 AI는 손대지 않는다)
- `python3 $SK/scripts/selfcheck.py out` — 매니페스트·파일·상태·금지 문구
- `python3 $SK/scripts/audit.py out --shots out/.shots` — 렌더링 측정(대비·토큰 밖 색·의미 배지·CTA·터치·캔버스) + 화면 캡처
- **사실 대조 서브에이전트 1개**(같은 메시지에서): `journey.md` 사실 표와 모든 `screens/*.html`의 글자를 대조해 어긋남(날짜·시간·인원·겹침·상태 이름)과 "누른 뒤 갈 곳이 없는 조작"만 목록으로 돌려준다. 고치지는 않는다.

❌ 항목과 캡처를 보고 고친다. 여러 화면에 걸친 문제는 공통 원인부터. 고칠 화면이 많으면 흐름별로 서브에이전트에 나눠 **병렬로** 고친다. 수정 후 selfcheck·audit를 한 번 더(최대 2회). 그래도 남는 항목은 마지막 메시지에 적는다.

비평 체크리스트(캡처를 볼 때, P0·P1이면 반드시 고친다):
- 탭 첫 화면·홈에 하단 고정 버튼이 있는가 / 문구가 "~보기"인가 (P1)
- 사용자에게 새 할 일(보내기·정리)을 얹는 기능이 있는가 (P1)
- 사람을 역할 이름으로 부르는가 (P1)
- 뜻이 다른 배지가 같은 색인가 (P1)
- 채워진 버튼에 짙은 글자인가 / 버튼이 버튼처럼 안 보이는가 (P1)
- 누른 뒤 갈 곳이 없는 버튼, 빈 상태가 결과 있는 것처럼 보이는 목록, 링크·초대 뒤 결과 표시 없음 (P0)
- 하단 고정 버튼이 스크롤 끝의 마지막 내용을 가린다 (P1)
- 선택 상태가 두 모양(검정/브랜드)이다, 시간·순서를 배지로 썼다 (P1)
- PRD 동사(추가·순서 바꾸기·지우기)에 조작 수단이 없다 (P1)
- 오류·안내 문구가 화면에 없는 선택지를 가리킨다 (P0), 한 번뿐인 행동(요청·확인)의 눌린 뒤 모습이 없다 (P1)
- 화면끼리 같은 사실(날짜·겹침·인원·상태 이름)이 다르다 / 결정 화면에서 core 정보(예: 겹침)가 사라진다 (P1)
- 수십 개 목록에 검색이 없다 / 사용자가 만드는 분류를 만들 곳이 없다 (P0~P1)
- 명세 화면·단계가 빠졌다 / 규칙 상태가 규칙을 보여 주지 않는다 (P0~P1)
- 사진 자리가 회색 박스·글자뿐이다 / 사진이 내용과 안 맞는다 (P1)
- confirm 대화상자를 되돌릴 수 있는 행동에 썼다 (P1)
- 설명 카드("~를 누르면 ~돼요")가 반복된다 — 화면당 부가 설명 1개, 조작법 설명 금지 (P1)

### 끝 — 마지막 메시지

- 무엇을 만들었는지 3줄(핵심 한 문장, 화면 수, 기본 색과 그 이유 — 캔버스에서 색 점으로 바꿀 수 있다고 안내)
- 뺀 것(하네스가 떠올렸다 뺀 것 포함)은 캔버스 맨 위 "정한 것 · 뺀 것"에 있다고 안내
- 하네스가 대신 정한 것 중 사용자가 알아야 할 것 2~3개
- 남은 ❌ 항목(있으면)
- 마지막 줄: `[[DONE out/index.html]]` — 이 줄 없이 턴을 끝내면 미완성으로 처리된다. 기다릴 작업이 남았으면 기다린 뒤에 쓴다.
