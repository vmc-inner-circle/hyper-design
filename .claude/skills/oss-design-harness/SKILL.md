# oss-design-harness v7

PRD → 질문 1회(무드 고르기) → 병렬 빌드 → 캔버스. 사용자는 디자인을 모른다고 가정한다.

## 불변 원칙

1. **사용자에게는 렌더링된 시안을 보여주고 고르게만 한다.** 전문 용어(타이포, 레이아웃, 위계, 그리드, 톤앤매너, 컴포넌트, IA, UX, UI, 플로우, 와이어프레임, 팔레트, 폰트명) 금지. 답은 글자 하나(`A`)로 끝나게.
2. **화면 구성·흐름은 묻지 않고 스스로 정한다.** 정한 것은 `out/brief.md` 가정 로그에 남긴다.
3. **이해가 먼저, 예쁨은 나중.** 화면마다 핵심 메시지 한 문장 + 주요 행동 1개. 설명 문구로 이해시키는 UI는 실패다.
4. **덜어낸다.** 모든 섹션은 "누구를 위해, 언제 보는가"를 가져야 하고, 없으면 지운다. 같은 목적의 버튼을 두 번 두지 않는다. 데이터가 빈약한 통계·인사이트 칸, 장식용 이모지·일러스트 금지.
5. **뻔한 게 이긴다 — 한국 대중 앱 규격.** `references/korean-app-style.md`가 골격(회색 바탕+흰 섹션 블록, 26px 큰 제목, 64px 목록 행, 56px 하단 버튼, 탭바, 배지, 칩)의 **기본값**이다. 모든 서브에이전트 프롬프트에 이 파일 전문을 붙인다. 독창적 레이아웃 금지. 한 화면에 한 가지 일.
6. **절제된 비주얼 — 토큰 밖 값 금지.**
   - 색: 포인트 컬러 **1개**(+ 그 옅은 틴트 1개). 오류 표시도 포인트 컬러 계열이나 무채색으로 — 빨강·파랑을 따로 추가하지 않는다. 무채색은 흰색 포함 **5단계**만(`--gray-0`~`--gray-4`). 틴트도 회색 단계로 세므로 합쳐 6개 이하.
   - **대비**: 글자색은 배경 대비 4.5:1 이상. 보조 글자 회색도 흰 배경에서 4.5:1 이상(#6B6B6B보다 밝으면 안 됨). 포인트 컬러는 **흰 글자와 4.5:1 이상**이 되도록 충분히 진하게 잡고, 포인트 컬러를 글자로 쓸 때도 4.5:1. 비활성·요일 라벨 등 "흐린 글자"도 예외 없음.
   - 글자: 크기 ≤ 6종, 굵기 400/600/700 3종, 패밀리 Pretendard 1종. `button, input, select, textarea { font: inherit; }` 리셋 필수.
   - 여백: `--space-*`(4·8·12·16·20·24·32·40) 토큰만. 1px·2px·음수 margin 금지(테두리는 border로).
   - radius 4종(6 배지·12 작은 버튼·16 버튼·섹션·999 칩), 그림자 1종(바텀시트용).
   - 선택 상태(칩·세그먼트)는 `#191F28` 채움 + 흰 글자 한 가지. 탭바 선택은 아이콘·글자 색만. 채워진 포인트 컬러는 화면의 주요 버튼 1개 전용.
   - 모든 눌리는 요소(칩·탭·세그먼트·목록행·아이콘 버튼)는 **높이 44px 이상**.
7. **AI 티 금지.** 흰 섹션 블록은 회색 바탕 위 한 겹만(블록 안에 카드 금지). 탁한 색·테두리 박스 버튼 남발·검정 배지 금지. 그라데이션·이모지 아이콘·텍스트 그라데이션 금지. 아이콘은 인라인 SVG(선 1.75px, 24px) 또는 텍스트 라벨.

## 진행 (턴 구조)

사용자 턴은 최대 4번(PRD 포함). 이 하네스는 **2번**만 쓴다: ① PRD 입력 ② 무드 선택 답.

### 턴 1 — PRD를 받으면 (목표 4분)

1. 첫 줄에 안내: "질문은 딱 1번 드립니다. 고르신 뒤 약 10분 동안 알아서 만듭니다."
2. `out/brief.md` 작성 (직접, 빠르게):
   - 역할: 만드는 사람 / 보기만 하는 사람 등 PRD에서 읽히는 역할과 각자의 화면 차이
   - **화면 인벤토리 12~14개**: id(영문 kebab) · 제목 · role(`planner`/`viewer`/`shared`) · 핵심 메시지 한 문장 · 주요 행동 1개 · 섹션 목록(각 섹션의 대상·시점) · traits · 연결 화면
   - PRD 커버리지: 기능 요구사항(F1..)·유저스토리(US1..)·**사용자 상황/조건 문장(S1..)** 마다 담당 화면 id와 "화면의 어떤 요소가 그 상황을 푸는지" 한 줄. 유저스토리의 "한 번에·매번 묻지 않고·헷갈리지 않고" 같은 표현은 화면 요구사항으로 옮긴다.
   - **역할마다 진입 → 합류(초대 수락 등) → 첫 사용 흐름**이 화면으로 존재해야 한다. 다른 사람을 초대하는 기능이 있으면 초대받은 사람이 들어오는 화면도 만든다.
   - 홈 헤드라인은 **그 사용자가 지금 해야 할 행동** 기준으로 정한다.
   - **시나리오 데이터 표**: 등장인물(이름·역할), 주요 항목 3~5개(이름·날짜·상태)를 한 번 정해 두고 모든 화면이 이 데이터만 쓴다. 화면 A에서 항목 X를 누르면 화면 B도 X를 보여준다.
   - 화면에 표시되는 사용자 입력값(장소·메모 등)은 그 값을 입력하는 화면이 있거나, 가정 로그에 "입력 화면 생략" 이유가 있어야 한다.
   - 가정 로그
   - 상태 파생(아래 규칙)
3. 무드 시안 3개를 **서브에이전트 3개로 병렬** 생성(Agent 도구, 한 메시지에 3개). 모두 **같은 화면**(보기만 하는 사람의 홈, 없으면 메인 홈)을 같은 콘텐츠로 만들되 무드만 다르게:
   - A·B·C는 `references/korean-app-style.md`의 "무드 시안 3종"(토스처럼·카카오처럼·29CM처럼) 값을 그대로 쓴다. 골격은 셋 다 같은 한국 앱 규격이다.
   각 에이전트는 `out/ask/mood-X.html`(375px 폰 화면 1장, 자체 `<style>`에 CSS 변수로 토큰 선언)을 쓴다. 불변 원칙 전부를 프롬프트에 붙여 넣는다.
4. `python3 .claude/skills/oss-design-harness/scripts/ask_page.py out/ask` 실행 → `out/ask/index.html`(세 시안을 나란히, 큰 A/B/C 라벨).
5. 답변 마지막 줄을 정확히 이 형식으로 끝낸다:
   `[[ASK out/ask/index.html]] 세 가지 화면 중 이 앱에 가장 어울리는 느낌을 골라주세요. (A / B / C)`

### 턴 2 — 답을 받으면 (목표 8분)

1. 고른 시안의 CSS 변수를 그대로 가져와 `out/tokens.css`(토큰 + 공통 클래스: 앱바, 버튼 primary/secondary/text + `.btn.is-loading`, 목록행, 섹션 제목, 칩, 체크, 라디오, 세그먼트, 공통 `.is-selected`, 입력, 탭바, 하단 고정 버튼 영역, 바텀시트, 스켈레톤, 상단 완료 표시)를 쓴다. 시안에 없던 값은 원칙 6 안에서 정한다.
2. `out/screens.json` 매니페스트 작성 (스키마 아래).
2-1. `out/partials.html`에 **앱바·탭바·하단 고정 버튼 영역의 마크업 원본**을 쓴다(탭 아이콘 SVG 포함). 모든 화면은 이것을 그대로 복사하고, 현재 탭만 `aria-current="page"`로 바꾼다.
3. 화면 빌드: 서브에이전트 **4개 병렬**(한 메시지에), 화면을 3~4개씩 나눠 맡긴다. 각 에이전트에 전달: 불변 원칙 전문, `out/brief.md`, `out/tokens.css` 경로, 맡은 화면 목록(id·제목·role·핵심 메시지·주요 행동·섹션·links·states), 화면 규칙:
   - 파일: `out/screens/<id>.html`, 상태 변형은 `out/screens/<id>--<state>.html`
   - `<link rel="stylesheet" href="../tokens.css">` 사용, 화면 전용 스타일은 최소한. 새 색·새 폰트 크기 금지.
   - `<h1>`은 정확히 1개(앱바 제목 또는 화면 제목). 채워진 포인트 컬러 버튼은 화면당 최대 1개.
   - 터치 영역 44px 이상. 본문 15px 이상, 최소 글자 13px.
   - **`viewer` 화면은 모든 글자 17px 이상**(보조 정보 포함). 보기만 하는 사람은 글자 크기에 민감하다.
   - 입력칸 아래 도움말 문장·`help`/`tooltip` 클래스 금지 — 설명이 필요하면 구조를 바꾼다.
   - 이동하는 요소는 `<a href="<id>.html">`로 실제 연결(links의 화면으로). 탭바도 링크.
   - 더미 데이터는 PRD 맥락의 현실적인 한국어(실제 이름·지명·날짜·시간). "텍스트", "제목", lorem, TODO, "여행 1" 금지. 이미지가 필요하면 단색 블록+라벨이나 SVG로, 외부 이미지 URL 금지.
   - `title` 속성, 물음표 도움말 아이콘, 툴팁 금지.
   - 375px 폭에서 가로 스크롤이 생기면 안 된다.
   - 하단 고정 버튼·탭바가 있으면 본문 아래 여백을 그 높이만큼 둔다. **필수 입력은 모두 고정 버튼 위에서 보여야** 한다(812px 높이 기준).
   - 헤드라인·배너·섹션 제목이 같은 말을 반복하지 않는다. 탭·필터 아래에는 그 범주의 항목만.
   - 앞 단계에서 이미 정한 값을 다음 단계에서 다시 고르게 하지 않는다.
   - 한 화면에서 받는 입력이 3종류 이상이면 단계를 나눈다(한 화면 한 가지 일).
   - 항목이 20개를 넘을 수 있는 목록에서 고르는 화면은 맨 위에 검색 입력.
   - 경고·추천·주요 버튼이 서로 반대 말을 하지 않는다(경고가 뜬 선택지를 추천하지 않는다).
   - `out/brief.md`의 시나리오 데이터 표만 사용한다. 링크로 이어지는 화면은 같은 항목을 이어서 보여준다.
   - 선택 상태는 전부 `tokens.css`의 `.is-selected` 한 가지 스타일을 쓴다(칩·체크·라디오·세그먼트 공통). 화면에서 선택 스타일을 새로 만들지 않는다. 포인트 컬러를 분류 태그 색으로 쓰지 않는다(분류는 무채색 배지).
   - 서버로 보내는 버튼(보내기·확정·저장·답하기)은 **누른 뒤의 결과가 화면으로 이어져야** 한다: 결과 화면으로 링크하거나, 결과가 반영된 화면에 짧은 완료 표시(상단 한 줄). 보내는 동안은 `tokens.css`의 `.btn.is-loading`(버튼 안 스피너) — 별도 로딩 화면은 만들지 않는다.
4. 모든 에이전트가 끝나면 `python3 .claude/skills/oss-design-harness/scripts/build_canvas.py out` 실행 → `out/index.html` 캔버스.
5. 검증 두 가지를 실행한다.
   - `python3 .claude/skills/oss-design-harness/scripts/selfcheck.py out` (파일·링크·상태 규칙)
   - `python3 .claude/skills/oss-design-harness/scripts/audit.py out` (렌더링 기준 측정: 대비·색 수·여백·터치 영역·글자 크기·위계·AI 티)
   ❌ 항목을 고친다. **여러 화면에 걸친 문제는 `tokens.css` 한 곳에서** 고치고(색·회색·대비·리셋·칩 높이), 화면별 문제만 해당 파일을 고친다. 고친 뒤 두 스크립트를 다시 실행. **최대 2회**, 그래도 남으면 남은 항목을 마지막 메시지에 적는다.
6. 마지막 줄: `[[DONE out/index.html]]`

## 상태 파생 규칙 (넘침도 실패)

상태는 traits에서만 나온다. 규칙에 안 걸리면 default 하나가 정답이다.
- `empty` ← `list_first_use`: 목록 화면이고 처음 쓰는 사람이 빈 목록을 보게 됨. 빈 상태는 다음 행동 1개를 제시한다.
- `error` ← `form`: 입력 폼 화면. 인라인 검증 메시지.
- `disabled` ← `readonly_role`: 같은 화면을 보기만 하는 역할이 봄(편집 요소가 비활성/숨김).
- `loading`·`success`·`initial` 금지. 짧은 대기는 스켈레톤 클래스, 긴 작업·완료는 별도 화면.
- 화면당 default 포함 최대 3개.

## screens.json 스키마

```json
{"screens":[{"id":"home","file":"screens/home.html","title":"홈","role":"viewer",
  "purpose":"핵심 메시지 한 문장","primary_action":"..",
  "sections":[{"name":"..","audience":"..","when":".."}],
  "traits":{"list_first_use":false,"form":false,"readonly_role":false},
  "states":[],"links":["detail"],"group":"부모 화면"}],
 "prd_coverage":{"F1":["..."],"US1":["..."]},
 "story":{"headline":"PRD의 갈등을 이 앱이 어떻게 푸는지 한 문장(강조할 말은 <em>로)",
   "summary":"왜 그 갈등이 생기고 이 앱은 무엇을 나눠서/묶어서 푸는지 2~3문장",
   "ideas":[{"title":"핵심 설계 아이디어(짧게)","desc":"화면에서 실제로 어떻게 보이는지 2문장","refs":"US1 · F2","screens":["home"]}],
   "roles":[{"name":"역할 이름","sees":["이 역할에게만 보이는/다르게 보이는 것"]}]}}
```
`story`는 캔버스 맨 위 설명이 된다. ideas는 정확히 3개, roles는 PRD의 역할 수만큼. 전문 용어 없이, 비개발자가 읽고 "아 이래서 이렇게 만들었구나"가 되게 쓴다.
`group`은 캔버스에서 한 줄로 묶일 흐름 이름(예: "계획 만들기", "부모가 보는 화면"). `links`가 캔버스 화살표가 된다.
