# WORKFLOW — K15 분위기 하나만 고르면 끝 · 실제 유명 서비스 디자인 · 디자인 단계 Opus (사용자 10-12)

> K15 = K14 + (1) **겉모습(화면을 그리는) 서브 에이전트만 Opus** — Agent 도구를 부를 때 `model: "opus"` 를 꼭 넣는다. **마무리 교정은 세션 모델(Sonnet)** — `model` 을 넣지 않는다(10-12 사용자: 15분을 지키려고 "교정을 Sonnet으로")(뼈대·화면 내용·조립은 지금 세션 모델 그대로) (2) 벌마다 **대표 화면 3~4장을 직접 그린다**(홈만이 아니라 핵심 화면까지) (3) 마무리 교정에 **디자이너 눈 점검표** (4) **한글 = `KOREAN.md`**(은유는 겉모습에만, 글은 표준 용어).
> 사용자(10-12): "더 이쁘고, 디자이너가 작업한 느낌이 날 수 있도록" · "용어들이 일반적으로 한국 사람들이 많이 쓰는 형식이 아니야 — 작업대라는 말은 잘 안 쓰거든" · "디자인 단계만 Opus".

> 사용자(10-12): "표로 정리된 내용을 화면에 띄워 사용자가 선택 — 사용자는 이 부분만 선택하면 끝" · "모든 기능을 만드는 시간을 15분 내외" · "최대한 미적인 감각을 반영, 전문 디자이너가 만든 것처럼" · (10-08) "국내·해외 유명 사이트의 디자인을 참조" · "AI 슬롭 최소화".
> **질문 = 분위기 고르기 하나뿐**(질문 페이지 1장). 나머지(역할별 첫 화면, 가정, 품질 방침)는 하네스가 판단하고 `decisions.md` 에 남긴다. PRD 입력은 질문으로 세지 않는다.
> **결과 = 디자인 5벌.** 같은 화면·같은 내용(공통) 위에, 벌마다 **실제 유명 서비스 하나의 디자인 시스템(DESIGN.md)**을 출발점으로 겉모습을 입힌다. 스타일 라이브러리(`styles/`)는 쓰지 않는다.
> **시간 = 하네스 작업 15분**(답 기다리는 시간 빼고). 시작 턴 1분 + 답 받은 턴 14분.

## 시작 (PRD 를 받은 턴) — 1분. 그리지 않는다. 서브 에이전트 없음. 스크립트를 읽지 않는다.

1. PRD 를 읽고 `design/brief.md` 를 짧게: 핵심 갈등 한 문장 · 역할(유저스토리마다) · 기능 F목록(PRD 번호 그대로) · 필수 흐름 · 가정 4~6개(질문하지 않고 하네스가 정한 것).
2. 이 서비스를 쓰는 사람·상황에 맞는 분위기 2개를 고른다(`python scripts/refs.py list` 로 12가지 확인). 
3. `python scripts/refs.py ask design/ask/q1.json --recommend <id1>,<id2> --title "<서비스 이름>, 어떤 분위기로 만들까요?"` → `python scripts/ask.py design/ask/q1.json`.
4. 마지막 줄 `[질문 1] design/ask/q1.html`.

## 답을 받은 턴 — 14분. 다시 묻지 않는다.

| 분 | 누가 | 일 |
|---|---|---|
| 0~3 | 메인 | 답 풀기 → 레퍼런스 5곳 → 공통 뼈대 → 5벌 설계표 |
| 3~9.5 | 에이전트 동시(한 응답에서 전부) | 화면 내용 2~3개(세션 모델) + 겉모습 5개(Opus, 대표 화면 3~4장씩) |
| 화면 내용이 끝나면 | 메인(겉모습을 기다리는 동안) | 공통 조립 + `coverage.py` — 겉모습을 기다리는 빈 시간에 끝낸다 |
| 겉모습이 하나 끝날 때마다 | 메인 → 에이전트(Sonnet) | 그 벌만 `build --only <k> --no-gallery`(10초 안팎) → 바로 그 벌의 교정 에이전트를 띄운다. 다른 벌 겉모습은 계속 그리는 중 |
| ~13 | 마지막 교정 에이전트 | 가장 늦은 벌의 교정이 끝나면 |
| 13~14 | 메인 | `variants.py gallery` → 완료 |

### 0~3분 — 메인

1. `python scripts/ask.py --read design/ask/q1.json "<답 코드>" && python scripts/app.py --engine-css design/app/engine.css` → `design/decisions.md`(엔진 부품 CSS `engine.css` 와 화면 JSON 형식 `design/app/BLOCKS.md` 를 이 명령이 같이 만든다 — BLOCKS.md 를 손으로 쓰지 않는다). `DESIGNER.md` 는 에이전트용이라 메인은 읽지 않는다. 스크립트(`coverage.py` 등)를 읽지 않는다. 메모가 있으면 메모 우선(분위기 안에서 특정 사이트를 말했으면 그 사이트를 v1 로).
2. `python scripts/refs.py pick <고른 분위기 id들> --n 5` → 레퍼런스 5곳(v1~v5). 이 PRD 에 명백히 안 맞는 곳(예: 사진이 거의 없는 서비스에 사진 갤러리형)은 같은 분위기의 다른 사이트로 바꾸고 이유를 decisions.md 에 한 줄.
3. **화면 이름·탭 이름·버튼 글은 `KOREAN.md` 2절(표준 용어 사전)에서 고른다.** 은유·만든 말 금지(예: 작업대·안내장·소식길 ✗ → 일정·공유하기·소식 ✓). 서비스 이름(앱 이름)만 자유롭게.
   `design/brief.md` 에 **전체 화면 목록**(12~18장: id·이름·역할·목적 한 줄·features)과 **내용 데이터**(실제 같은 한국 이름·장소·날짜·금액). **여러 화면에 나오는 사실**(시각·집합 장소·"확정 N개·후보 N개" 같은 합계·이름)은 여기서 한 번 정해 적는다 — 겉모습·화면 내용 에이전트는 이 값만 쓰고 새로 만들지 않는다(안 정해 두면 5벌이 서로 다른 값을 지어내 메인이 벌마다 고치게 된다). 역할별 첫 화면을 어떻게 할지 하네스가 정하고 한 줄.
4. `design/app/base.json`: name·tagline·tokens(중립 기본값)·roles(역할마다 nav 2~5개, **nav[0] = 그 역할의 홈**)·features·flows·order(전부)·decisions·assumptions·tour(8~12단계).
5. **대표 화면 3~4장**을 정한다(5벌 공통): 역할별 홈 + 이 서비스의 핵심 행동 화면 1~2장(예: 일정 편집, 상세). `brief.md` 에 id 목록.
6. **5벌 설계표**를 `brief.md` 에: | 벌 | 레퍼런스 | 이 앱에서의 이름(두세 단어) | 레퍼런스에서 가져올 것 3가지(색 역할·글자 체계·부품 모양 등) | 이 서비스에 맞게 바꿀 것 | 폰 nav · PC pcnav | 홈 주인공 |

### 3~9분 — 에이전트 동시 (한 응답 안에서 전부. 하나씩 띄우지 않는다)

1. **겉모습 에이전트 5개를 먼저**(가장 오래 걸린다 · 벌마다 1개, **`model: "opus"`**), 그다음 **화면 내용 에이전트**(2~4개, 화면 5~7장씩, 세션 모델) — 같은 응답에서 이 순서로. 지시문은 아래 한 줄 틀에 벌 정보만 채운다(공통 지시문은 `DESIGNER.md` 에 있다 — 길게 다시 쓰지 않는다).
- 겉모습: "작업 폴더 <경로>. `.claude/skills/oss-design-harness/DESIGNER.md` 의 'A. 겉모습'을 그대로 따른다. 벌 `<k>` = '<이름>', 레퍼런스 `<site>`. nav=<tabbar|…>, pcnav=<side|…>. 방향: <설계표의 '바꿀 것'·홈 주인공>. 대표 화면(`hero`): <id>: <그 화면에 들어갈 내용 한 줄>, …"
- 화면 내용: "`design/brief.md`, `design/app/base.json`, `design/app/BLOCKS.md`, `.claude/skills/oss-design-harness/KOREAN.md` 를 읽고(화면 글은 KOREAN.md 대로) 아래 화면들을 `design/app/screens/<id>.json` 에 화면 JSON 으로 써라. 그리거나 다른 파일을 읽지 마라. 홈(nav[0]) 화면도 블록으로 써 둔다. 화면 목록(**화면마다 '어느 화면에서 들어오는지'를 같이 적는다** — 어디서도 `to` 를 못 받는 화면은 coverage FAIL 이다): …" + SKILL '도구' 의 블록 요약 줄.

### 겉모습을 기다리는 동안 — 메인 (화면 내용 에이전트가 끝나면 바로)

`python scripts/app.py design/app && python scripts/coverage.py design/app/app.json` — FAIL 이면(들어오는 링크 없는 화면 등) 공통 화면 `design/app/screens/*.json` 을 고치고 다시. **벌 빌드보다 먼저 끝낸다**(벌 빌드가 공통 화면을 복사해 가므로 나중에 고치면 5벌 다시 빌드). 글(K1·K2)이 의심되는 공통 글은 `KOREAN.md` 2·3절 대로 지금 고친다 — 교정 에이전트는 공통 화면을 못 고친다.

### 겉모습이 끝나는 대로 벌마다 (다 끝나길 기다리지 않는다)

겉모습 에이전트 하나의 완료 알림이 오면 그 즉시 한 응답에서: (1) `python scripts/variants.py build design --only <k> --no-gallery` (그 벌만 조립·캡처·예쁨/슬롭 검사·`design/v/<k>/fix.md`·흐름 지도, 10~20초 · 여러 벌이 동시에 끝났으면 `--only v1,v4`) (2) 이어서 그 벌의 교정 에이전트를 띄운다. **빌드와 교정 에이전트 호출 사이에 다른 명령(sed·grep·사실 확인)을 끼우지 않는다** — 직접 그린 화면의 시각·장소·개수가 brief.md 와 다르면 교정 에이전트가 맞춘다(DESIGNER B). 조립 실패(Traceback)만 메인이 고쳐 다시 `--only <k>`. (직접 그린 화면 `var/<k>/screens/<id>.html` 의 공통 블록은 빌드가 알아서 비운다.)

교정 에이전트: **세션 모델 그대로(`model` 을 넣지 않는다 — Opus 아님)**, 지시문은 한 줄(공통 지시문은 `DESIGNER.md`):
"작업 폴더 <경로>. 너는 `<k>` 벌의 마무리 디자이너다. `.claude/skills/oss-design-harness/DESIGNER.md` 의 'B. 교정'을 그대로 따른다. 레퍼런스 `<site>`."
남은 FAIL 은 `decisions.md` 의 '남은 문제'에 적는다.

### 마지막 교정이 끝나면 — 마무리

1. `python scripts/variants.py gallery design` → `design/index.html` + 벌마다 마지막 검사 줄(교정 에이전트가 이미 마지막에 빌드했다 — **전체를 다시 빌드하지 않는다**, 다시 빌드하면 20초 낭비).
2. 마지막 줄 `[완료] design/index.html`. 완료 메시지: 5벌(레퍼런스 → 이 앱에서의 이름, 한 줄 컨셉), 고른 분위기 → 반영, 검사 결과(벌마다 교정 전→후).

## 금지

스크립트 파일 읽기 · 기다리는 동안 상태 확인 명령(공통 조립·coverage 는 예외) · 겉모습 5개가 다 끝나길 기다렸다가 한꺼번에 빌드·교정하기 · 에이전트를 하나씩 띄우기 · 메인이 화면을 직접 그리기 · 스타일 라이브러리(`styles/`) 쓰기 · 레퍼런스의 로고·문구·사진·브랜드 이름을 결과에 넣기.
