# 인터뷰 — PRD 검토 질문 규칙

인터뷰 턴마다 보내는 질문을 만드는 규칙. **실무 킥오프에서 기획서를 검토하는 디자이너**처럼 묻는다. 디자인안을 들고 동의를 받는 인터뷰가 아니다. 정해 둔 답을 확인받는 자리가 아니라 기획서에서 모르는 것을 알아내는 자리다.

- 답하는 사람은 **기획서를 받은 사람**이다. 실제 사용자가 아니므로 "사용자는 보통 어떻게 할까요?"처럼 남의 행동을 예측하게 하지 않는다.
- 목적은 두 가지다: ① 기획서에서 두 가지로 읽히는 곳을 하나로 정한다 ② 핵심 문제와 거리가 있는 요구를 첫 버전에 둘지 정한다. 답은 PRD 판단(덜어냄·다음 버전·핵심·명확화·유지)으로 이어지고, 그 판단이 곧 화면이 된다.
- 덜어내는 것 자체가 목표는 아니다. "꼭 필요하다"는 답도 이유가 남으면 좋은 결과다.

## 1. 범위 검토 — 질문을 고르기 전에

`brief.md` §범위 검토에 요구사항·유저스토리·상황·조건 문장마다 적는다.

| 관점 | 묻는 것 |
|---|---|
| 핵심인가 | 기획서가 풀라고 한 핵심 문제(배경)를 직접 푸는가, 곁가지인가 |
| 비용 | 넣으면 화면·흐름이 대략 몇 장 늘어나는가 |
| 겹침 | 다른 요구와 겹치거나 부딪히는가 |
| 빠지면 | 첫 버전에서 빠지면 누가 어떤 곤란을 겪는가 (아무도 없으면 뺄 후보) |
| 해석 | 두 가지 이상으로 읽히는가 |

## 2. 질문 고르기

- **순서**: 이해 확인 먼저 → 필요성 확인 **2개 이상** → 선호·분위기는 꼭 필요할 때만 1개. 개수는 인터뷰 전체 기준이다 (한 턴 안에서가 아니라).
- **고르는 기준**: 답에 따라 바뀌는 화면이 많은 것 × 기획서를 받은 사람이 답할 수 있는 것.
- 한 질문에 한 주제. 한 질문에 결정 두 개를 섞지 않는다.
- 묻지 않는 것(색·간격·폰트·아이콘·상태 처리 등)은 SKILL.md §1을 따른다.

## 3. 질문 틀 5가지

틀 하나를 골라 빈칸을 채운다. `[ ]`는 PRD에서 가져오는 자리다. 기획서 구절은 짧게 따옴표로 인용한다. 질문에는 §번호를 쓰지 않는다 (근거 절은 `brief.md` 질문 표에). 줄 나눔·순서는 SKILL.md §1 형식.

### 두 구절 대조형 — 기획서 두 곳이 다른 방향을 가리킬 때
> "'[구절 1]'이라고 돼 있는데, '[구절 2]'라고 돼 있거든요. 제가 헷갈린 건, [해석 1]인 건지, 아니면 [해석 2]인 건지예요. 어느 쪽으로 이해하면 될까요?"

첫 질문으로 쓰기 좋다. 에이전트가 어떻게 이해했는지가 드러나고, 어느 쪽으로 진행할지를 묻기 때문이다.

### 경계형 — 용어가 어디까지인지 애매할 때
> "'[용어]'가 어디까지인지 궁금해요. [구체 예시 1]만 [용어]인가요, 아니면 [구체 예시 2]도 [용어]로 보면 될까요?"

예시는 추상어가 아니라 PRD에 나오는 사람·수치·상황으로. 뒤쪽이면 다른 용어와 어떻게 다른지도 한 줄 덧붙일 수 있다.

### A인지 B인지형 — 한 구절이 두 가지로 읽힐 때
> "'[구절]'에서요, [해석 A]인 건지, [해석 B]인 건지 어느 쪽으로 이해하면 될까요?"

문장이 길어도 두 해석이 분명히 갈리면 고르기 쉽다. 길이보다 선택 구조가 중요하다.

### 필요성 + 이유형 — 핵심 문제와 거리가 있는 기능
> "[기능]이 있는데요, 기획서가 풀려는 핵심 문제([핵심 문제 한 줄])와는 조금 떨어져 보여서요. [넣으면 늘어나는 것 — 예: 화면이 서너 장 생겨요]. 첫 버전에서는 [줄인 형태]까지만 하고, [기능]은 나중에 넣어도 괜찮을까요? 꼭 필요하다면 이유가 궁금해요."

또는: "이 기능이 빠지면 누가 어떤 점이 불편해질지 궁금해요."
필요하다는 답이 오면 그 이유를 PRD 판단의 reason에 남긴다.

### 조건 제시형 (UX 관점) — 비슷해 보이는 두 요구가 겹칠 때
> "[요구 A]와 [요구 B]가 비슷한 역할 같은데, 둘 다 따로 필요할까요? [사용자 상황 1]이라면 따로 필요하고, [사용자 상황 2]라면 합쳐도 될 것 같아서요."

답하는 사람에게 판단 기준(어떤 상황이면 어느 쪽)을 함께 건넨다.

## 4. 말투

- 동료에게 묻는 1인칭 대화체. "제가 헷갈린 건 ~예요", "~해 보여서요".
- 소리 내어 읽어도 걸리지 않는 문장. 한 문장에 질문을 두 개 붙이지 않는다.
- 헷갈린 지점을 구체적으로 짚는다 — "이 부분이 궁금해요"가 아니라 "~인지 ~인지가 궁금해요".
- 서비스를 쓰는 사람들은 높여 부른다 ("~하시는 분", "~분들").
- 전문 용어에는 괄호로 쉬운 말을 붙인다. AI가 넣은 수치는 가정임이 드러나게 ("예를 들어 3일쯤").

## 5. 선택지와 달라지는 것

- 선택지 2~3개 + "직접 설명할게요". 선택지는 서로 겹치지 않게.
- 선택지 순서로 답을 기울이지 않는다. 사람은 첫 보기를 더 고르므로, AI가 기운 쪽(AI의 해석, 덜어내는 쪽)을 늘 첫 번째에 두지 않는다.
- 질문마다 선택지 바로 위에 괄호로 "([어느 화면]의 [어느 부분]이 [어떻게] 달라집니다)".
- "모르겠어요"나 "설명이 필요해요" 답은 **다시 묻지 않는다** (개입 예산). AI가 정하고 PRD 판단에 basis=assumed로, `brief.md` 가정 로그에 이유와 함께 적는다. R2에서 화면을 보낼 때 가정한 것을 한 줄씩 함께 알린다.

## 6. 보내기 전 점검

- [ ] 첫 턴의 첫 질문이 이해 확인이다
- [ ] 인터뷰를 끝낼 때까지 필요성 확인이 2개 이상이다 (범위 검토에 곁가지가 없으면 예외 — 가정 로그에 이유)
- [ ] 한 턴 질문이 3개 이하이고, 끝에 남은 답 기회가 있다
- [ ] 질문마다 기획서 구절을 따옴표로 인용했다 (§번호 없이)
- [ ] 디자인안을 먼저 내민 질문이 없다
- [ ] 사용자 행동을 예측하게 하는 질문이 없다
- [ ] 한 질문에 한 주제, 한 문장에 질문 하나
- [ ] 선택지가 서로 겹치지 않고, AI가 기운 쪽이 늘 첫 번째에 오지 않는다
- [ ] 선택지 위 괄호(달라지는 것)에 화면 이름과 요소가 있다
- [ ] 기획서가 이미 답한 것을 다시 묻지 않는다. 확인이 꼭 필요하면 "맞나요?"(예/아니오) 대신 AI가 읽은 두 가지 뜻을 나란히 두고 고르게 한다
- [ ] 메시지 끝에 "그 밖에 바라는 점 있으세요?" 같은 열린 개선 질문을 붙이지 않았다 (없는 흠을 찾게 만든다)

## 7. 답을 받은 뒤 — PRD 판단

`templates/prd-review.json`을 `design/prd-review.json`으로 복사해 채운다.

| 판단 | 뜻 | 화면 |
|---|---|---|
| remove 덜어냄 | 첫 버전에서 없앤다 | 그 화면을 만들지 않는다 |
| defer 다음 버전 | 미룬다 | 첫 버전 화면에 없음, PRD에 [다음 버전] |
| emphasize 핵심 | [핵심]으로 올린다 | 가장 먼저 보이게 |
| clarify 명확화 | 두 가지로 읽히던 문장을 한 뜻으로 | 화면 수 그대로, 내용이 정해짐 |
| keep 유지 | 그대로 둔다 | 필요하다는 답의 이유를 reason에 |

- 기능이나 화면을 "따로 두지 않기로" 했다면 clarify가 아니라 remove다.
- 판단마다 근거(basis): 답 원문(answered) / PRD 구절(prd) / AI 가정(assumed). 판단 안에 섞인 가정 세부는 `assumptions`에 따로 적는다.
- 원본 PRD는 고치지 않는다. 고친 사본 `design/prd-updated.md`: 맨 위 변경 요약(덜어낸 것 / 강조한 것 / 명확히 한 것), 본문에 `[덜어냄]` `[다음 버전]` `[핵심]` `[명확화: …]` + 판단 번호.
- 지침(G1…)은 이 판단에서 뽑는다. 출처는 `J3 (Q2 답변)`처럼.

## 8. 턴 진행 — 몇 번 물을지

턴 수는 정해 두지 않는다. 답을 받을 때마다 아래를 점검하고, 충분하면 더 묻지 않고 바로 생성한다(SKILL.md §2).

**한 턴에 묻는 양**: 1~3개. 첫 턴은 범위 검토에서 화면에 가장 영향이 큰 것부터. 짧게 여러 번이 한 번에 많이보다 낫지만, 턴도 개입 1회라 서로 독립인 질문은 한 턴에 묶는다.

**"만들어도 되나" 점검** — 모두 예면 인터뷰를 끝낸다.
1. 두 가지로 읽히는 곳 중 **화면 수·흐름을 바꾸는 것**이 모두 정해졌다
2. 곁가지 요구를 첫 버전에 둘지(필요성)가 정해졌다
3. 토큰·기기를 정할 근거(서비스의 성격·느낌, 누가 어디서 어떤 일을 하는지 — 이동 중 확인인지, 책상에서 많이 입력하는지)가 PRD나 답에 있다 — 없고 화면 수가 달라지면 한 번 묻는다
4. 남은 빈칸은 AI가 가정해도 **화면 구조가 바뀌지 않는** 것뿐이다

**다음 질문 고르기** — 점검에서 "아니오"인 항목에서 고른다.
- 방금 답이 새로 연 애매함을 먼저 (답이 PRD의 다른 구절과 부딪히면 그 둘을 두 구절 대조형으로)
- 그다음 범위 검토 표에서 남은 것 중 바뀌는 화면이 가장 많은 것
- 이미 답한 것, "모르겠어요"라고 한 것은 다시 묻지 않는다

**상한**: 답 4턴 (연습 모드 10턴). 상한에 닿으면 점검 결과와 상관없이 남은 빈칸을 가정으로 두고 생성한다.

**기록**: 턴마다 `prompt-log.md`의 그 회차 아래에 에이전트 판단을 한 줄로 남긴다 — 사용자 원문과 섞지 않는다.
```
> (에이전트 판단) 점검 1✓ 2✗ 3✓ 4✗ → 계속. 다음 질문: [무엇] — [고른 이유]
> (에이전트 판단) 점검 모두 ✓ → 인터뷰 종료 (답 n턴 / 질문 m개)
```
