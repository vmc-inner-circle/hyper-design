# design-harness

비디자이너가 PRD만 주면 **질문 없이 먼저 만들어 보여주고, 바꿀 것만 받아** 끝내는 하네스. 디자이너처럼 레퍼런스를 조사해 시안 5개를 먼저 보여주고, 고른 시안으로 전체 화면을 만든다.

- 계약(무엇을 만드는가): `docs/harness-design.md`
- 사용자에게 보이는 말: `references/ux-writing.md` — **데이터를 쓰기 전에 반드시 읽는다**
- PRD → 데이터 규칙: `references/prd-to-screens.md`
- 의견 해석: `references/answer-parsing.md`
- 이 문서: 실행 절차

## 절대 규칙

1. **사용자 개입은 PRD 포함 5회 이하.** 계획은 PRD → 시안 고르기 → 초안에 의견 → 제출 확인(4회), 5회째는 여유.
2. **기본은 질문 없이 바로 초안.** PRD에 없는 것은 추천값으로 정하고 `brief.md` 가정 로그에 남긴다. 질문은 보드 안(`board.ask`, 최대 3개)에서 한다. **예외는 하나** — 잘못 짐작하면 화면 대부분을 다시 그려야 하는 모호함이 PRD에 있을 때만 초안 전에 한 번 묻는다(1.1-0).
3. **취향을 말로 묻지 않는다.** 분위기·글자 크기·버튼 색은 보드 상단에서 눌러 보고 고르게 한다.
4. **확정된 것은 다시 묻지 않는다.** 2라운드부터 `board.locked`.
5. **"끝났다"는 스크립트가 판정한다.** `lint.js` exit 0 + `build.js` 성공 + 메인의 브라우저 검수 전에는 사용자에게 보여주지 않는다.
6. **결과는 사용자 브라우저에 자동으로 띄운다.** 마지막 빌드는 항상 `--open`. 띄우기 전에 검수용 헤드리스 Chrome을 종료한다.
7. **번호가 나온 화면만 다시 쓴다.**
8. **사용자에게 보이는 말은 ux-writing 규칙대로.** 컴포넌트·디자인 용어 금지, 흐름 제목은 '~하기'.
9. 채팅 메시지는 짧게: 무엇을 띄웠는지 + 할 일 한 줄.
11. **예전 실행물을 보지 않는다.** 실행 중에는 다른 `runs/*` 폴더와 `submissions/`를 읽지 않는다. 형식은 계약 문서(`docs/harness-design.md` §6)와 `packages/core/schema/README.md`로 충분하다. 다른 PRD의 화면·문구·구조를 가져오면 "PRD만으로 시작"이라는 조건이 깨진다.
10. **사용자에게 묻는 것은 전부 객관식이다.** 초안 전 확인, 보드의 질문, 마지막 확인(더 고칠지·제출할지)까지 모두 `AskUserQuestion`(또는 보드의 라디오)으로 선택지를 주고, 첫 번째가 추천이며 "(추천)"을 붙인다. "어떻게 할까요?" 같은 열린 질문을 채팅으로 던지지 않는다. 자유 입력은 선택지에 없는 답을 위한 "기타"로만 둔다.

## 사용자가 보게 되는 것 (계약 §3 요약 — 검수 기준)

0. **1턴 시안 고르기**(보드가 이 화면 하나뿐): 살펴본 서비스 카드 → 시안 5개(A 추천 · 이름 · 이유 · 특징 · 참고한 곳 · 메인 화면 3~6장을 좌우 캐러셀로 — 모두 같은 높이, 넘치는 내용은 화면 안 스크롤, 이름을 누르면 크게) · '이 안으로 할게요' · 안마다 적는 칸 → '시안 X(으)로 보내기'.

2턴부터는 두 탭으로 **이해**와 **의견**을 나눈다.
1. **사용 흐름** 탭(처음 열림) = **구역 보드**(디자이너 보드처럼 한 캔버스): 구역 띠(가입·처음 시작 / 홈 / …) → 단계 이름표 → 화면을 순서대로 나란히(오류·완료 상태는 원래 화면 옆) → 화면 아래 검은 **정책 메모**. 화살표는 **조건이 갈리는 곳에만**(`when`, 초록 화살표 + 조건 이름표, 누르는 버튼에 초록 테두리). 위쪽에 구역 바로가기·확대 도구. 화면을 누르면 화면 디자인으로.
2. **화면 디자인** 탭: 왼쪽 화면 목록(역할별, 맨 위 "전체" = 질문·남긴 의견) · 가운데 화면 한 장 · 오른쪽 의견(+ **이 화면의 규칙** · 사용 흐름에서 보기). 화면에서 **아무 요소나 눌러 고르고**(마우스를 올리면 "버튼 '…'" 이름표) 바꿔주세요/빼주세요 + 예시 칩 → 화면 위에 핀 번호. **아이콘**을 고르면 허용 Lucide 목록에서 바로 바꿔 볼 수 있다.
3. 상단 **화면 느낌**: 분위기(시안 수만큼, 고른 시안의 분위기가 추천) · 글자 크기 · 버튼 색 5개를 한 창에서 — 고르면 모든 화면에 바로 적용.
4. 상단 **의견 보내기 · n개**(n = 추천과 다르게 고른 것 + 남긴 의견) → "이렇게 전달돼요" 확인 창 → 복사. "전체"에서 항목별 지우기·모두 지우기.

## 시간표 (elapsed.txt)

| 구간 | 목표 |
|---|---|
| 1턴: PRD → 시안 보드 | ≤ 8분 (초안 전 확인을 했으면 답을 받은 뒤부터) |
| 2턴: 시안 고르기 → 초안(전체 화면·흐름) | ≤ 15분 |
| 3턴: 의견 → 최종 | ≤ 10분 |
| 4턴: 제출 확인(+의견이 있으면 반영) | ≤ 8분 |

턴 계획: **PRD(1) → 시안 고르기(2) → 초안에 의견(3) → 제출 확인(4) → 여유(5)**. 사용자 요청(리허설 2): "맨 처음에 시안을 선택하고 그 이후에 사용 흐름과 화면 디자인을 주는 게 맞다", "시안은 5개로".

## 1턴 — PRD → 시안 보드 (`stage: "concept"`)

디자이너처럼: 레퍼런스 조사 → 화면 구성이 다른 시안 5개 → 고객이 하나 고른다. **전체 화면은 아직 만들지 않는다**(고른 뒤 2턴에).

### 1.0 기록 시작
- `runs/<project>/` 생성(영문 케밥케이스). `templates/prompt-log.md`·`templates/brief.md` 복사. `harness-notes.md` 빈 파일.
- `elapsed.txt`에 `시작: YYYY-MM-DD HH:MM`(`date`로 확인). `prompt-log.md` 1회에 PRD 원문.

### 1.0-1 레퍼런스 조사 시작 (ref-scout 5개, 백그라운드)

디자이너처럼 **비슷한 서비스를 먼저 살펴보고** 그 근거로 화면 구성이 다른 시안을 만든다(색만 다른 안 금지). PRD를 읽자마자 ref-scout 5개를 **백그라운드로 동시에** 띄우고, 메인은 기다리지 않고 1.1로 간다.

```
Agent(subagent_type: "ref-scout", model: "sonnet", run_in_background: true, prompt: "
PRD=<누가 · 무엇을 · 핵심 작업 3줄>
ANGLE=<아래 5개 중 하나>
AVOID=<다른 조사원에게 준 예상 후보 이름 — 겹치지 않게>
")
```
- `ref-scout`가 목록에 없다고 나오면(에이전트 파일을 이번 세션 중에 만든 경우) `subagent_type: "general-purpose"`로 띄우고 프롬프트 첫 줄에 "먼저 .claude/agents/ref-scout.md를 읽고 그 지침대로만 일한다(WebSearch·WebFetch만, 파일 쓰기 금지, 최종 답은 JSON 하나)."를 붙인다.

관점 5개: ① 같은 일을 하는 국내 서비스 ② 같은 일을 하는 해외 서비스 ③ 핵심 작업이 닮은 다른 분야 서비스 ④ 같은 사용자층이 매일 쓰는 앱 ⑤ 디자인 갤러리에서 이 작업의 화면 모음.

- 동시에 돌아 서로를 못 보므로 **같은 서비스가 겹칠 수 있다** — 이름이 같으면 하나만 남기고 가져올 점을 합친다(4곳이어도 진행). 겹침을 줄이려고 AVOID에 흔한 후보(관점별로 떠오르는 유명 서비스)를 미리 나눠 적는다.
- 결과(JSON 5개)는 `runs/<p>/references.md`에 표로 모으고 `screens.json`의 `references`에 넣는다(prd-to-screens §7). 3분이 지나도 안 온 조사원은 기다리지 않는다(3곳 이상이면 진행).
- 결과가 오기 전에 할 수 있는 것(brief·화면·흐름·갈래)을 먼저 한다. 시안(`concepts`)만 결과를 본 뒤 정한다.

### 1.1-0 초안 전에 물을지 판단 (메인, 1분)

PRD를 읽고 아래 표로 판단한다. **대부분의 PRD는 묻지 않는다**(묻지 않는 것이 기본값).

| 먼저 묻는다 — 틀리면 화면 대부분이 바뀜 | 묻지 않는다 — 초안으로 보여주면 됨 |
|---|---|
| 누가 주로 쓰는지가 두 가지로 읽힌다 (예: 예비부부 둘만 / 초대받은 지인도 가입) | 화면 한두 개만 달라지는 선택 (할 일을 사람별 / 날짜별) → `board.ask` |
| **어디서 쓰는지가 PRD에 없다 (휴대폰 / 컴퓨터)** — 모바일·웹은 패키지가 달라 화면 전부가 바뀐다 | 첫 화면에 무엇을 보여줄지 → `board.ask` |
| 핵심 기능이 둘 중 하나일 수 있다 (일정 조율 도구 / 기록·공유 도구) | 색·분위기·글자 크기 → 보드의 화면 느낌 |

판단 기준: **"이걸 반대로 짐작했을 때 화면의 절반 이상을 다시 만들어야 하는가?"** 아니면 묻지 않는다.

물을 때:
- 초안 전에 **딱 한 번**, `AskUserQuestion`으로 **질문 3개 이하**, 전부 객관식. 각 질문의 첫 번째 선택지가 추천이며 라벨 끝에 "(추천)", 선택지에 **"알아서 해주세요"** 를 둔다(고르면 추천값).
- 질문 앞에 한 줄: "초안을 만들기 전에 방향이 크게 갈리는 것만 확인할게요."
- 쉬운 말로 묻는다(ux-writing). "플랫폼", "타깃 페르소나" 같은 말 대신 "주로 휴대폰으로 쓰나요, 컴퓨터로 쓰나요?".
- 이 답도 개입 1회다: PRD(1) + 확인(1) + 시안(1) + 의견(1) + 제출 확인(1) = 5회로 버퍼가 없다 — 그래서 정말 필요할 때만 묻는다. `prompt-log.md`에 "초안 전 확인"으로 원문을 남기고, `brief.md` 가정 로그에 `[확인]`으로 적는다.
- **휴대폰/컴퓨터**: PRD에 "앱·휴대폰·푸시" 또는 "웹·PC·관리자 페이지"가 분명하면 묻지 않는다(prd-to-screens §1). 둘 다 없거나 섞여 있으면 이 질문 하나를 꼭 넣는다: "주로 휴대폰으로 쓰나요, 컴퓨터로 쓰나요?" [신호가 조금이라도 강한 쪽 (추천) / 다른 쪽 / 알아서 해주세요]. 사용자 결정(2026-10-07): 항상 묻지 않고 PRD에 없을 때만 — 개입 4회를 지킨다.
- 묻지 않기로 했으면 그 판단을 `brief.md` 가정 로그 첫 줄에 한 줄로 남긴다(예: "[판단] 초안 전 확인 없음 — 누가·어디서·핵심이 PRD에 분명함").

### 1.1 PRD 분석 → brief.md (메인, 5분 — 레퍼런스 조사와 동시에)
`references/prd-to-screens.md`대로:
- 플랫폼: `web`(1280×800) 또는 `mobile`(390×844, `packages/mobile` — web 위에 겹침). prd-to-screens §1.
- 역할 2~3개 + 역할마다 `nav`.
- 화면: **핵심 8~14개 + 처음 시작용 3~5개**(빈 홈·등록·빈 목록·초대 받았을 때 등, `state`·`variantOf`). 순서 = 사용자가 만나는 순서(번호 1, 2, 3…).
- 흐름: **처음 시작 흐름을 역할마다 맨 앞에** + 핵심 흐름. 전부 끊김 없는 한 줄, 흐름 6~9개.
- **갈래**: 화면마다 글자 버튼을 훑어 흐름 밖에서 다른 화면·창을 여는 버튼을 `branches`로(prd-to-screens §5-1). 새 입력·선택 UI를 여는 핵심 버튼은 **뜨는 창 화면**(`overlayOf`, 3~6개).
- **오류·완료 상태**: 입력 화면 중 틀리기 쉬운 곳에 `state: "error"`, 핵심 작업 끝에 `state: "success"` 변형(`variantOf`) — 합쳐 2~4개(prd-to-screens §3).
- **구역 보드 데이터**(prd-to-screens §5-2): `sections` 2~6개, 화면마다 `section`·`step`(단계 이름표), 상태 변형을 뺀 모든 화면에 `policy`(정책 메모 — 처음 상태·제한·표기·예외, ux-writing §9), 조건이 갈리는 step·branch에 `when`("처음 가입이면").
- 항목: 화면당 3~6개, `label`·`why`는 ux-writing §2.
- 가정 로그: PRD에 없어서 정한 것 전부.

### 1.2 시안 5개 (레퍼런스가 모인 뒤, prd-to-screens §6-1)
- `references`: 조사 결과(겹치면 하나로). `runs/<p>/references.md`에도 표로.
- `looks` 5개(분위기, 시안마다 하나) + 분위기마다 버튼 색 5개(prd-to-screens §6).
- `concepts` 5개: 메뉴 구조(`shell` sidebar·top·rail을 모두 쓴다) · 첫 화면 구성(`home`) · 밀도 · 분위기(`look`)가 **서로 다른** 안. 첫 번째가 추천. 안마다 참고한 곳(`refs`)과 비교할 **메인 화면 3~6장**(`screens`, 모든 안이 같은 slug — 역할별 메뉴 화면 먼저, 남는 칸에 핵심 작업 화면. PRD를 보고 정한다).
- `"stage": "concept"`, `"concept": "<추천 id>"`.

### 1.3 데이터 파일 → 시안 화면 — screen-writer 병렬 (시안마다 3장씩 1개, 최대 10개 동시, sonnet)
- `screens.json`(계약 §6.1), `flow.json`(§6.2, 모든 step에 `trigger`, 제목 '~하기', `branches`), `icons.json`. 달력이 있으면 `node scripts/calendar.js …`로 격자를 미리. `node scripts/ids.js runs/<project>`. `node scripts/lint.js runs/<project>` — 이때 FAIL은 "시안 조각 없음"만.

**화면을 빨리 쓰는 방법(라이브러리·모듈)**: 에이전트마다 먼저 작업 묶음을 만든다 — `node scripts/pack.js runs/<project> --screens <3장> [--concept <id>] --name <이름>` → `runs/<project>/packs/<이름>.md`. 에이전트는 **그 파일 하나만 읽고 화면마다 한 번씩 쓴 뒤 끝낸다**(셸 없이 `<main>`만, 짧은 부품 태그). 셀프 테스트 측정: 3장에 4~8분 · 도구 호출 15~38회 → **1.8분 · 4회**.

```
Agent(subagent_type: "screen-writer", model: "sonnet", prompt: "
PACK=runs/<project>/packs/<이름>.md
RUN=runs/<project>
CONCEPT=<a|b|c|d|e>
SCREENS=<그 시안의 screens 중 3장 — 4장 이상이면 에이전트를 나눠 같은 CONCEPT로 하나 더>
DOMAIN=<도메인 한 줄 + 고정 더미 데이터: 인물(역할 포함)·장소·날짜 범위·상태 어휘. 모든 시안이 같은 값>
시안 메모: <이름 · 첫 화면에 무엇을 먼저(home) · 밀도 · 참고한 곳에서 가져올 점(borrow)을 화면별로 구체적으로>
각 화면은 screens.json의 항목(name·purpose·pattern·regions)과 flow.json의 trigger·branches를 따른다(고르면 그대로 옮겨 쓴다).
이 PACK 파일 하나만 읽고, 화면마다 Write 한 번으로 쓴 뒤 끝낸다(다시 열어 점검하지 않는다).
")
```

- 끝나면 **`node scripts/expand.js runs/<project>`**(짧은 부품 태그를 펼치고 셸을 붙여 파일에 다시 씀) → `lint.js`. FAIL 시안만 FAIL 원문과 함께 재호출(최대 2회), 그래도 실패면 메인이 고친다.

### 1.4 검수 → 띄우기
1. `node scripts/build.js runs/<project> --mode board` (시안 단계면 시안 고르기 화면만 만든다)
2. 헤드리스 Chrome(계약 §11)으로 1440×900: 살펴본 서비스 카드 / 시안 5개(그 시안의 메뉴 구조·분위기로 메인 화면 3~6장이 가로로) / '이 안으로 할게요' → 보내기 버튼이 '시안 X(으)로 보내기' / 칸에 적으면 개수 / 콘솔 에러 0.
3. **헤드리스 Chrome 종료** → `node scripts/build.js runs/<project> --mode board --open`
4. `elapsed.txt`에 `시안: HH:MM`. 사용자에게 (이 형식 그대로):

```
시안을 브라우저에 띄웠어요. (runs/<project>/out/board.html)

다른 안에서 가져오고 싶은 점은 그 안의 칸에 적어 주세요. 다 되면 오른쪽 위 버튼으로 내용을 확인하고 복사해 여기에 붙여넣어 주세요.
고른 안으로 전체 화면과 사용 흐름을 만들어 드릴게요.
```

## 2턴 — 시안 고르기 → 초안 (`stage` 없음 = draft)

1. `prompt-log.md` 2회에 (AI 질문 요약 = "시안 보드") + 붙여넣은 원문. `brief.md` 답변 로그에 **원문 | 해석 | 반영**.
2. `시안 <id>(이름)` → `screens.json`: `concept = <id>`, `stage` 삭제, `theme = 그 시안의 look`, `board.recommend.theme`도 같게, `board.locked = ["concept"]`, `round: 1`(초안 1).
3. `시안 <id> 메모: …` → 고른 시안의 메모면 그 시안을 고칠 점, 다른 시안의 메모면 **그 안에서 가져올 요소**(예: "B의 달력") — 모두 이번 초안의 전역 힌트로(answer-parsing §1).
4. 고른 시안의 메인 화면 `concepts/<id>/<slug>.html`을 `screens/<slug>.html`로 복사(메모가 그 화면을 건드리면 복사 뒤 revise). 셸은 expand.js가 붙였으므로 그대로 맞다(시안을 바꿔 셸만 바꿀 때는 `expand.js --reshell`).
5. 나머지 화면: 3장씩 `pack.js`로 작업 묶음을 만들고(`--concept <고른 id>`로 시안의 메뉴 구조·첫 화면·밀도가 묶음에 들어간다) screen-writer를 병렬로(sonnet). 프롬프트에는 `PACK=` · DOMAIN · 화면별 메모 · "시안 메모"(그 시안의 home·밀도·borrow + 3의 힌트)만.

```
Agent(subagent_type: "screen-writer", model: "sonnet", prompt: "
PACK=runs/<project>/packs/<이름>.md
RUN=runs/<project>
SCREENS=<slug1>,<slug2>,<slug3>
DOMAIN=<도메인 한 줄 + 고정 더미 데이터: 인물(역할 포함)·장소·날짜 범위·금액 단위·상태 어휘. 오늘 날짜>
THEME_HINT=<상태 배지 규칙(예: 확정=badge-success+circle-check, 후보=badge-neutral+circle-dashed)>
화면별 메모:
- <slug>: <이 화면에 무엇이 보여야 하는지, 채울 값, 빈 상태면 .empty로 비워 둘 것, primary 버튼 문구>
트리거: runs/<project>/flow.json에서 from이 이 화면인 step의 trigger를 실제 버튼에 data-trigger로 (00-rules 3-1).
이 PACK 파일 하나만 읽고, 화면마다 Write 한 번으로 쓴 뒤 끝낸다(다시 열어 점검하지 않는다).
")
```

6. `node scripts/expand.js runs/<project>` → `lint.js`(FAIL 화면만 재호출 최대 2회) → `build.js --mode board` → 헤드리스 검수: (사용 흐름) 구역 띠 수 = sections 수 / 화면 아래 정책 상자 / 오류·완료 화면이 원래 화면 옆 / `when` 수만큼 초록 조건 이름표 · 시작 버튼에 초록 테두리 / 구역 바로가기 / 화면 클릭 → 화면 디자인(오른쪽 '이 화면의 규칙'). (화면 디자인) 화면 속 버튼이 제 모양 / 요소 하나 눌러 바꿔주세요 → 핀·'의견 보내기 (1)' / 콘솔 에러 0 → **헤드리스 종료** → `--open`.
7. `elapsed.txt`에 `초안: HH:MM`. 사용자에게:

```
시안 X로 만든 초안을 띄웠어요. (runs/<project>/out/board.html)
'사용 흐름'에서 구역마다 화면이 쓰는 순서대로 놓여 있고, 화면 아래 검은 상자에 그 화면의 규칙을 적었어요. 초록 화살표는 조건에 따라 길이 갈리는 곳이에요.
고치고 싶은 화면을 누르면 '화면 디자인'에서 의견을 남길 수 있어요(규칙이 틀렸으면 화면 메모에). 화면 느낌은 위쪽에서 바꿔 볼 수 있어요. 다 되면 "의견 보내기"로 복사해 붙여넣어 주세요.
(화면 N개 · 구역 S개 · 조건 화살표 K개 · 웹|모바일)
```

## 3턴 — 의견 → 최종

`references/answer-parsing.md`대로.
1. `prompt-log.md` 3회 + 답변 로그.
2. 반영: `화면 S 메모: …`가 규칙(정책)에 대한 말이면 그 화면의 `policy`를 고친다(화면 조각은 그대로). `화면 S · … [경로]` 줄은 그 화면의 경로 요소를 고칠 대상으로(answer-parsing §1-1) / 첫 줄의 분위기·글자 크기·버튼 색 확정(`theme`, `toggles.type`, `toggles.swatch`) / `확인:` → 구조 반영 / `화면 S … 빼기` → 요소·조각 블록 제거 / `화면 N 빼기` → 화면 제거 + 흐름을 **끊김 없게** 다시 잇기(끊기면 흐름을 쪼갬) / `추가:` → 새 화면(+ 필요하면 새 흐름·갈래) / `메모:` → 전역 힌트.
3. 의견 때문에 화면에 **새 묶음이 생기거나 버튼이 다른 묶음으로 옮겨지면** screens.json에 항목을 추가하고, 그 버튼을 쓰는 흐름 step·갈래의 `region`도 옮긴다. `ids.js`.
4. 재작성: 문구·아이콘·요소 교체처럼 단순한 수정은 haiku, 배치를 다시 짜는 수정은 sonnet(`MODE=revise`, 1~2개씩 병렬), 새 화면도 sonnet.
5. `lint.js && build.js --mode final` → `out/index.html`과 `out/screens/NN-slug.html`(화면마다 하나).
6. 검수는 **실제 클릭**(chrome-devtools `click`, 스크립트 `.click()`으로 대신하지 않는다)으로: 사용 흐름(처음 열림) 구역 보드의 화면 수 = 화면 수 · 정책 상자 · 조건 화살표 / 화면을 누르면 크게 다가감 / 화면 전체 탭의 대지 수 = 화면 수(주소가 index.html에 머무는지) / 완성본 페이지에서 흐름 버튼·왼쪽 메뉴를 누르면 해당 페이지 / 콘솔 에러 0. **index.html에 다른 파일로 가는 링크를 넣지 않는다**(macOS Chrome 폴더 권한 문제로 '파일 액세스 거부됨'). → 헤드리스 종료 → `build.js --mode final --open`.
7. 제출: `out/` 전체(`index.html` + `screens/`)를 `submissions/srlee0408/`로 복사, `prompt-log.md`(총 개입 횟수), `elapsed.txt`(종료·소요).
8. 사용자에게: 경로 + "사용 흐름에서 구역별 화면과 화면마다의 규칙을 한 캔버스로 볼 수 있고, 화면을 누르면 그 화면으로 다가가요" 한 줄. 이어서 `AskUserQuestion` 하나로 "이대로 제출할까요?" [이대로 제출 (추천) / 고칠 게 있어요 — 의견 보내기 글이나 고칠 점을 '기타' 칸에 붙여넣기]. **고치기를 고르는 것과 의견을 한 답으로** 받아 턴을 아낀다.

## 4턴 — 제출 확인
- "이대로 제출" → 끝. `prompt-log.md`에 총 개입 4회.
