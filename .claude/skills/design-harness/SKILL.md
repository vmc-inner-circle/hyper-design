# design-harness

비디자이너가 PRD만 주면 **질문 없이 먼저 만들어 보여주고, 바꿀 것만 받아** 3라운드 안에 끝내는 하네스.

- 계약(무엇을 만드는가): `docs/harness-design.md`
- 사용자에게 보이는 말: `references/ux-writing.md` — **데이터를 쓰기 전에 반드시 읽는다**
- PRD → 데이터 규칙: `references/prd-to-screens.md`
- 의견 해석: `references/answer-parsing.md`
- 이 문서: 실행 절차

## 절대 규칙

1. **사용자 개입은 PRD 포함 5회 이하.** 목표는 3회(PRD → 의견1 → 의견2 → 완성).
2. **기본은 질문 없이 바로 초안.** PRD에 없는 것은 추천값으로 정하고 `brief.md` 가정 로그에 남긴다. 질문은 보드 안(`board.ask`, 최대 3개)에서 한다. **예외는 하나** — 잘못 짐작하면 화면 대부분을 다시 그려야 하는 모호함이 PRD에 있을 때만 초안 전에 한 번 묻는다(1.1-0).
3. **취향을 말로 묻지 않는다.** 분위기·글자 크기·버튼 색은 보드 상단에서 눌러 보고 고르게 한다.
4. **확정된 것은 다시 묻지 않는다.** 2라운드부터 `board.locked`.
5. **"끝났다"는 스크립트가 판정한다.** `lint.js` exit 0 + `build.js` 성공 + 메인의 브라우저 검수 전에는 사용자에게 보여주지 않는다.
6. **결과는 사용자 브라우저에 자동으로 띄운다.** 마지막 빌드는 항상 `--open`. 띄우기 전에 검수용 헤드리스 Chrome을 종료한다.
7. **번호가 나온 화면만 다시 쓴다.**
8. **사용자에게 보이는 말은 ux-writing 규칙대로.** 컴포넌트·디자인 용어 금지, 흐름 제목은 '~하기'.
9. 채팅 메시지는 짧게: 무엇을 띄웠는지 + 할 일 한 줄.
11. **예전 실행물을 보지 않는다.** 실행 중에는 다른 `runs/*` 폴더와 `submissions/`를 읽지 않는다. 형식은 계약 문서(`docs/harness-design.md` §6)와 `packages/core/schema/README.md`로 충분하다. 다른 PRD의 화면·문구·구조를 가져오면 "PRD만으로 시작"이라는 조건이 깨진다.
10. **사용자에게 묻는 것은 전부 객관식이다.** 초안 전 확인, 보드의 질문, 마지막 확인(더 고칠지·제출할지)까지 모두 `AskUserQuestion`(또는 보드의 라디오)으로 선택지를 주고, 첫 번째가 추천이며 "(추천)"을 붙인다. "어떻게 할까요?" 같은 열린 질문을 채팅으로 던지지 않는다. 자유 입력은 선택지에 없는 답을 위한 "기타"로만 둔다.

## 사용자가 보게 되는 것 (계약 §3 요약 — 검수 기준)

두 탭으로 **이해**와 **의견**을 나눈다.
1. **사용 흐름** 탭(처음 열림): 전체 흐름 카드(번호 · '~하기' 제목 · 누구의 흐름 · 상태 태그 · 첫 화면 · 화면 순서, 맨 앞은 처음 시작 흐름) → 카드를 누르면 **따라가 보기**(지금 화면 + 다음 화면, 누르는 버튼의 파란 박스 → "1단계 · '…'를 누르면" 화살표, ←/→, Esc). 빨간 번호 없음. 화면을 누르면 화면 디자인으로.
2. **화면 디자인** 탭: 왼쪽 화면 목록(역할별, 맨 위 "전체" = 질문·남긴 의견) · 가운데 화면 한 장 · 오른쪽 의견. 화면에서 **아무 요소나 눌러 고르고**(마우스를 올리면 "버튼 '…'" 이름표) 바꿔주세요/빼주세요 + 예시 칩 → 화면 위에 핀 번호. **아이콘**을 고르면 허용 Lucide 목록에서 바로 바꿔 볼 수 있다.
3. 상단 **화면 느낌**: 분위기 3개(이름·이유) · 글자 크기 · 버튼 색 5개를 한 창에서 — 고르면 모든 화면에 바로 적용.
4. 상단 **의견 보내기 · n개**(n = 추천과 다르게 고른 것 + 남긴 의견) → "이렇게 전달돼요" 확인 창 → 복사. "전체"에서 항목별 지우기·모두 지우기.

## 1턴 — PRD → 초안 1

### 1.0 기록 시작
- `runs/<project>/` 생성(영문 케밥케이스). `templates/prompt-log.md`·`templates/brief.md` 복사. `harness-notes.md` 빈 파일.
- `elapsed.txt`에 `시작: YYYY-MM-DD HH:MM`(`date`로 확인). `prompt-log.md` 1회에 PRD 원문.

### 1.1-0 초안 전에 물을지 판단 (메인, 1분)

PRD를 읽고 아래 표로 판단한다. **대부분의 PRD는 묻지 않는다**(묻지 않는 것이 기본값).

| 먼저 묻는다 — 틀리면 화면 대부분이 바뀜 | 묻지 않는다 — 초안으로 보여주면 됨 |
|---|---|
| 누가 주로 쓰는지가 두 가지로 읽힌다 (예: 예비부부 둘만 / 초대받은 지인도 가입) | 화면 한두 개만 달라지는 선택 (할 일을 사람별 / 날짜별) → `board.ask` |
| 어디서 쓰는지가 모호하다 (휴대폰 앱 / PC 웹) | 첫 화면에 무엇을 보여줄지 → `board.ask` |
| 핵심 기능이 둘 중 하나일 수 있다 (일정 조율 도구 / 기록·공유 도구) | 색·분위기·글자 크기 → 보드의 화면 느낌 |

판단 기준: **"이걸 반대로 짐작했을 때 화면의 절반 이상을 다시 만들어야 하는가?"** 아니면 묻지 않는다.

물을 때:
- 초안 전에 **딱 한 번**, `AskUserQuestion`으로 **질문 3개 이하**, 전부 객관식. 각 질문의 첫 번째 선택지가 추천이며 라벨 끝에 "(추천)", 선택지에 **"알아서 해주세요"** 를 둔다(고르면 추천값).
- 질문 앞에 한 줄: "초안을 만들기 전에 방향이 크게 갈리는 것만 확인할게요."
- 쉬운 말로 묻는다(ux-writing). "플랫폼", "타깃 페르소나" 같은 말 대신 "주로 휴대폰으로 쓰나요, 컴퓨터로 쓰나요?".
- 이 답도 개입 1회다: PRD(1) + 확인(1) + 의견(2) = 4회, 버퍼 1회. `prompt-log.md`에 "초안 전 확인"으로 원문을 남기고, `brief.md` 가정 로그에 `[확인]`으로 적는다.
- 묻지 않기로 했으면 그 판단을 `brief.md` 가정 로그 첫 줄에 한 줄로 남긴다(예: "[판단] 초안 전 확인 없음 — 누가·어디서·핵심이 PRD에 분명함").

### 1.1 PRD 분석 → brief.md (메인, 5분)
`references/prd-to-screens.md`대로:
- 플랫폼: 현재 web만 구현 → `platform: "web"`(모바일 신호가 강하면 가정 로그).
- 역할 2~3개 + 역할마다 `nav`.
- 화면: **핵심 8~14개 + 처음 시작용 3~5개**(빈 홈·등록·빈 목록·초대 받았을 때·빈 부모 홈 등, `state`·`variantOf`).
- 흐름: **처음 시작 흐름을 역할마다 맨 앞에** + 핵심 흐름. 전부 끊김 없는 한 줄, 흐름 6~9개.
- 항목: 화면당 3~6개, `label`·`why`는 ux-writing §2.
- **화면 느낌**: PRD에 맞춘 분위기 3개(이름·이유·배경·글자·모양) + 분위기마다 버튼 색 5개(색 이름, 첫 번째 추천) + 글자 크기 추천(prd-to-screens §6). 구조 질문 최대 3개.
- 가정 로그: PRD에 없어서 정한 것 전부.

### 1.2 데이터 파일
- `screens.json`(계약 §6.1), `flow.json`(§6.2, 모든 step에 `trigger`, 제목 '~하기'), `icons.json`.
- 달력 화면이 있으면 `node scripts/calendar.js YYYY-MM --event …  --out runs/<p>/snippets/calendar-YYYY-MM.html`로 격자를 미리 만든다.
- `node scripts/ids.js runs/<project>`.
- `node scripts/lint.js runs/<project>` — 이때 FAIL은 "조각 파일 없음"만 남아야 한다. 말·흐름 WARN은 여기서 고친다.

### 1.3 화면 조각 — screen-writer 병렬 (sonnet, 3개씩)

```
Agent(subagent_type: "screen-writer", model: "sonnet", prompt: "
RUN=runs/<project>
SCREENS=<slug1>,<slug2>,<slug3>
DOMAIN=<도메인 한 줄 + 고정 더미 데이터: 인물(역할 포함)·장소·날짜 범위·금액 단위·상태 어휘. 오늘 날짜>
THEME_HINT=<상태 배지 규칙(예: 확정=badge-success+circle-check, 후보=badge-neutral+circle-dashed)>
화면별 메모:
- <slug>: <이 화면에 무엇이 보여야 하는지, 채울 값, 빈 상태면 .empty로 비워 둘 것, primary 버튼 문구>
트리거: runs/<project>/flow.json에서 from이 이 화면인 step의 trigger를 실제 버튼에 data-trigger로 (00-rules 3-1).
각 화면은 screens.json의 해당 항목(name·purpose·pattern·regions)을 읽고, packages/web/patterns/<pattern>.html에서 시작해 packages/web/snippets/*.md의 조각만으로 조립한다. 출력은 runs/<project>/screens/<slug>.html 뿐.
")
```

- 끝나면 `lint.js`. FAIL 화면만 FAIL 원문과 함께 재호출(최대 2회), 그래도 실패면 메인이 고친다. "components에 없는 클래스" WARN은 반드시 잡는다.

### 1.4 검수 → 띄우기
1. `node scripts/build.js runs/<project> --mode board`
2. 헤드리스 Chrome(계약 §11)으로 `out/board.html`을 1440×900에서 연다. 확인: (사용 흐름) 카드 수 = 흐름 수 / 첫 카드 → 따라가 보기 두 장·파란 박스·단계 문장 / → 한 번·Esc / 화면 클릭 → 화면 디자인. (화면 디자인) 화면 속 버튼이 제 모양 / 요소 하나 눌러 바꿔주세요 → 핀·'의견 보내기 (1)' / 콘솔 에러 0. 깨진 화면만 고친다. 검수로 남긴 의견은 헤드리스 프로필에만 남으므로 사용자 보드에는 영향 없다.
3. **헤드리스 Chrome 종료** → `node scripts/build.js runs/<project> --mode board --open`
4. `elapsed.txt`에 `초안1: HH:MM`. 사용자에게 (이 형식 그대로):

```
초안 1을 브라우저에 띄웠어요. (runs/<project>/out/board.html)
'사용 흐름'에서 흐름 카드를 눌러 화면이 어떻게 이어지는지 보시고, '화면 디자인'에서 고치고 싶은 곳을 눌러 의견을 남겨 주세요.
다 되면 오른쪽 위 "의견 보내기"에서 내용을 확인하고 복사해 여기에 붙여넣어 주세요.
(화면 N개 · 흐름 M개 · 웹)
```

## 2턴 — 의견 1 → 초안 2

`references/answer-parsing.md`대로.
1. `prompt-log.md` 2회에 (AI 질문 요약 = "초안 1 보드") + 붙여넣은 원문.
2. 줄 단위로 해석해 `brief.md` 답변 로그에 **원문 | 해석 | 반영**.
3. 반영: `화면 S · … [경로]` 줄은 그 화면의 경로 요소를 고칠 대상으로(answer-parsing §1-1) / 첫 줄의 분위기·글자 크기·버튼 색 확정(`theme`, `toggles.type`, `toggles.swatch`, `board.locked = ["theme","type","swatch","ask"]`) / `확인:` → 구조 반영 / `N 빼기` → 항목·조각 블록 제거 / `N 바꿔` → 재작성 대상 / `화면 N 빼기` → 화면 제거 + 흐름을 **끊김 없게** 다시 잇기(끊기면 흐름을 쪼갬) / `추가:` → 새 화면(+ 필요하면 새 흐름) / `메모:` → 전역 힌트.
4. 의견 때문에 화면에 **새 묶음이 생기거나 버튼이 다른 묶음으로 옮겨지면**(예: 열 머리에 끼어 있던 '회원 추가' 버튼을 위쪽 도구줄로) screens.json에 항목을 추가하고, 그 버튼을 쓰는 흐름 step의 `region`도 새 항목으로 옮긴다. `round: 2`, `board.focus = [고친 화면 slug]`, `ids.js`.
5. 재작성: 문구·아이콘·요소 교체처럼 단순한 수정은 haiku, 배치를 다시 짜는 수정(열 정렬·새 묶음)은 sonnet(`MODE=revise`, 1~2개씩 병렬), 새 화면도 sonnet → lint → 검수 → 헤드리스 종료 → `--open` → "초안 2를 띄웠어요. 고친 화면에는 '고친 화면' 표시가 있어요."

## 3턴 — 의견 2 → 최종

1. 같은 방식으로 국소 반영(분위기 변경은 한 번만 허용).
2. `lint.js && build.js --mode final` → `out/index.html`과 `out/screens/NN-slug.html`(화면마다 하나)이 만들어진다. 검수는 **실제 클릭**(chrome-devtools `click`, 스크립트 `.click()`으로 대신하지 않는다)으로: 화면 전체 캔버스의 대지 수 = 화면 수 / 대지를 누르면 크게 다가감 / 사용 흐름 카드 → 두 장씩, 화면을 누르면 화면 전체의 그 화면으로(주소가 index.html에 머무는지) / 완성본 페이지에서 흐름 버튼·왼쪽 메뉴를 누르면 해당 페이지 / 콘솔 에러 0. **index.html에 다른 파일로 가는 링크를 넣지 않는다**(macOS Chrome 폴더 권한 문제로 '파일 액세스 거부됨'). → 헤드리스 종료 → `build.js --mode final --open`.
3. 제출: `out/` 전체(`index.html` + `screens/`)를 `submissions/srlee0408/`로 복사, `prompt-log.md`(총 개입 횟수), `elapsed.txt`(종료·소요).
4. 사용자에게: 경로 + "화면 전체에서 확대·축소하며 모든 화면을 볼 수 있고, 대지를 누르면 그 화면으로 다가가요" 한 줄. 이어서 `AskUserQuestion`으로 "이대로 제출할까요?" [이대로 제출 (추천) / 한 번 더 고치기(의견 보내기로)]를 묻는다.

## 실행 중에 사용자가 하네스 자체를 지적하면

리허설처럼 사용자가 보드의 구조·말·레이아웃을 지적하면(개입 횟수와 별개로 하네스 개선 대화일 때):
1. 이번 실행물만 고치지 말고 **원인이 있는 층을 고친다**: 말 → `ux-writing.md`·lint / 구조·레이아웃 → `packages/core/canvas` / 데이터 규칙 → `prd-to-screens.md`·lint / 조립 → `snippets/00-rules.md`·screen-writer.
2. `runs/<project>/harness-notes.md`에 한 줄: 무엇을 왜 바꿨는지 + 사용자 원문.
3. 반복될 결정이면 계약 §13 표에 옮긴다. 이전 결정을 되돌리는 지적이면 표의 그 줄을 고친다.
4. 도메인 값은 하네스에 넣지 않는다.
