# PRD → brief · screens.json · flow.json 규칙

1턴에서 메인이 **5분 안에** 끝내야 하는 분석. 표를 먼저 만들고 빈 칸은 추천값으로 채운다. 사용자에게 묻지 않는다.
**이름·제목·항목 글을 쓰기 전에 `ux-writing.md`를 읽는다.**

## 1. 플랫폼

| 신호 | 결정 |
|---|---|
| PRD가 "앱"·"스마트폰"·"휴대폰"·"이동 중"·"푸시 알림"을 말하고 주 사용자가 폰을 든다 | `mobile` (390×844, `packages/mobile`) |
| PRD가 "웹"·"PC"·"관리자 페이지"·"대시보드"를 말하거나 표·다인 관리·긴 입력이 중심 | `web` (1280×800) |
| 두 역할이 다른 기기를 쓸 것 같다 | 주 사용자(가장 자주 쓰는 역할) 기준으로 하나만. 두 벌 만들지 않는다 |
| **PRD만으로 정할 수 없다** | 초안 전에 **객관식 하나로 묻는다**(SKILL 1.1-0): "주로 휴대폰으로 쓰나요, 컴퓨터로 쓰나요?" [첫째 = 신호가 조금이라도 더 강한 쪽 (추천) / 다른 쪽 / 알아서 해주세요] |

- PRD에 분명하면 묻지 않는다 — 필수 개입 3회(PRD · 시안 · 의견)를 지킨다(사용자 결정 2026-10-07). 판단을 `brief.md` 가정 로그 첫 줄에 남긴다("[판단] 모바일 — PRD에 '앱 푸시'·'이동 중 확인'").
- `mobile`이면 화면 조각·패턴·메뉴 구조가 `packages/mobile`(web 위에 겹침)을 따른다: 아래 탭 메뉴 · 위 제목 줄(← + 가운데 제목) · 맨 아래 꽉 찬 주 버튼 · 아래에서 올라오는 창. 시안의 메뉴 구조는 §6-1의 모바일 값.

## 2. 역할(roles)

PRD 유저스토리의 "~로서"를 그대로 역할로. 2~3개. 역할이 하나면 `roles: []`로 둔다. 각 역할에 **한 문장 목표**를 brief에 적는다 (예: 부모 = "묻지 않고도 큰 흐름을 안다").

역할마다 **내비 목록 `nav`** 를 screens.json에 적는다 — 모든 화면의 사이드바가 이걸 그대로 복사하므로 화면 간 일관성이 여기서 결정된다. 항목 = 그 역할이 진입하는 화면 slug(3~6개), 라벨은 화면 이름보다 짧게, 아이콘은 allowlist 이름.

```json
"roles": [
  { "key": "host", "label": "모임장", "nav": [
    { "slug": "host-home", "label": "모임", "icon": "calendar-days" },
    { "slug": "tasks", "label": "할 일", "icon": "list-checks" },
    { "slug": "members", "label": "회원", "icon": "users" }
  ] }
]
```

읽기 전용 역할(보기만 하는 회원 등)은 nav를 2~3개로 줄이고 그 역할에 `"type": "large"`(그 역할 화면만 글자 크게 — build가 .app에 data-type). 앱 전체 `toggles.type`은 보통으로 두고, screen-writer에게 "글자 크게"라고 시키지 않는다(조각에서 키우면 두 번 커진다).

역할마다 **`user`**(`{ "name": "김지영", "initials": "김지" }`)를 적으면 셸의 오른쪽 위·사이드바 아래에 그 사람이 보인다(expand.js). 서비스 이름은 `screens.json`의 `brand`(없으면 `title`), 상단 아이콘은 `brandIcon`(allowlist 이름).

## 3. 화면 인벤토리 (8~14개)

유저스토리 → 핵심 작업 1개씩 → 작업당 화면 2~4개. 아래를 기계적으로 훑는다.

| 종류 | 언제 넣나 | pattern |
|---|---|---|
| 진입/홈 | 항상 1개. 역할별로 다르면 역할당 1개 | dashboard 또는 timeline |
| 목록 | 반복 개체가 있으면 | list-detail |
| 상세 | 목록 항목을 열어보면 | list-detail (우측 패널) |
| 작성/수정 | 사용자가 무언가를 만들면 | form |
| 확인/공유 화면 | 다른 역할이 "보기만" 하면 | timeline 또는 dashboard (읽기 전용, 큰 글자) |
| 할 일/체크 | PRD에 체크리스트·할 일이 있으면 | board 또는 list-detail |
| 알림/변경 이력 | PRD에 변경 전달이 있으면 | list-detail |
| 설정/구성원 | 다인 사용이면 | settings |
| 온보딩/초대 | 첫 사용·초대 흐름이 있으면 | onboarding |

- **처음 시작 흐름은 반드시 만든다.** 비디자이너가 서비스를 이해하는 가장 쉬운 순서는 "처음 켰을 때 → 데이터를 넣을 때 → 채워진 뒤"다. 주된 역할마다 흐름을 하나씩 **맨 앞에** 둔다(예: "첫 모임 만들기", "초대 수락하기").
  - 계획하는(쓰는) 역할: **빈 홈**(`state: "first-run"`) → **등록 화면**(`state: "input"`) → **빈 목록**(`state: "empty"`) → 첫 항목 편집.
  - 보기만 하는 역할: **초대·첫 진입**(`first-run`) → **빈 홈**(`empty`, "정해지면 알려 드릴게요").
  - 빈 상태 화면은 `.empty` 조각으로 비워 둔다(숫자·목록을 채우지 않는다). 등록 화면은 입력칸에 예시 값을 채운다.
  - 빈 상태 화면은 원래 화면의 변형이다: slug에 `-empty`를 붙이고 `variantOf: "<원래 slug>"`, 이름 끝에 "(처음)". 캔버스가 "처음 켰을 때 / 데이터 없을 때" 태그를 붙여 채워진 화면과 구분한다.
  - **오류·완료 상태는 반드시 그린다**(디자이너 보드처럼 — 사용자가 실제로 밟게 될 상태). 원래 화면의 변형으로 `state: "error"`·`"success"` + `variantOf`, 이름 끝에 "(입력 오류)"·"(예약 완료)"처럼 무슨 상태인지. 구역 보드에서 원래 화면 바로 옆에 놓인다.
    - 오류: 입력하는 화면(form) 중 틀리기 쉬운 곳 1~3개 — 잘못된 칸에 빨간 테두리 + 고치는 방법 한 문장. lint: 입력 화면이 있으면 오류 상태 1개 이상(FAIL), 오류 상태 없는 입력 화면은 WARN.
    - 완료: 핵심 작업이 끝났을 때(저장·예약·보내기) 1~2개 — 맨 위 완료 안내 한 줄 + 끝난 항목 표시. lint: 1개 이상(FAIL).
    - 오류·완료 화면마다 `when`(언제 나오는지 한 마디, 예: "마이크를 허용하지 않았을 때") — 보드 ⓘ 카드 맨 위 '언제 나오나요'와 흐름 재생에 보인다.
    - 로딩·서버 오류처럼 사용자가 고칠 수 없는 상태는 만들지 않는다(정책 메모에 글로 적는다).
  - 채워진 화면은 목록을 3~5행으로 채운다. 긴 대기가 필수인 작업(결제 등)만 별도 화면.
- **밤에 쓰는 화면**(`"dark": true`, 선택): 어두운 방에서 보는 화면(자기 전·측정 중)은 고른 분위기와 상관없이 looks 중 어두운 분위기(mode dark 첫째)로 칠한다(build.js). 그래서 분위기 5개 중 하나는 어둡게 만든다.
- 화면 수: 핵심 화면 8~14개 + 처음 시작용 화면 3~5개 + 오류·완료 상태 2~4개.
- **뜨는 창 화면**(대화상자·오른쪽 패널): 핵심 작업의 버튼이 새 입력·선택 UI를 열면(추가·수정·고르기·초대) 그 창을 화면으로 만든다. `overlayOf: "<뒷 화면 slug>"`, 이름은 '~ 창'(예: "회원 추가 창"), 조각에는 창만 쓴다(뒷 화면은 build가 깐다). screens.json에서 뒷 화면 **바로 다음**에 둔다. 한 실행에 3~6개. 화면 수(8~14)에 세지 않는다.
- **screens.json 순서 = 사용자가 만나는 순서**(역할별 처음 시작 → 핵심 작업 순). `ids.js`가 이 순서로 화면 번호 1, 2, 3…을 준다.
- 14개를 넘으면 합친다. 8개 미만이면 역할별 뷰나 알림 화면을 되짚는다.

## 4. 영역(regions) — 화면당 3~6개

사용자는 화면 디자인 탭에서 **아무 요소나 직접 골라** 의견을 단다. 영역은 사용자에게 번호로 보이지 않고, ① 흐름의 `region`(누르는 버튼이 속한 곳) ② 사용자가 고른 요소의 **위치 경로 기준점**(`@key`) ③ "'<label>' 안에 있어요" 설명으로 쓰인다. 그래서 여전히 **의미 덩어리**로, `label`은 일상어로:
- 좋은 예: 상단 요약 띠, 날짜별 목록 전체, 우측 상세 패널, 하단 고정 액션, 필터 툴바, 초대 카드.
- 나쁜 예: 버튼 하나, 아이콘 하나, 제목 텍스트.
- 플로우 step에서 "누르는 곳"은 반드시 영역이어야 한다(lint). 그래서 primary 액션이 든 덩어리는 항상 영역으로.
- **사용자는 컴포넌트를 모른다.** 번호를 누르면 이 글이 그대로 보이므로 일상어로 쓴다.
  - `label` = **무엇이 보이는 곳 / 무엇을 하는 곳** (예: "날짜 고르기", "회원에게 아직 안 알린 변경", "어디서 몇 시에 모이는지"). 컴포넌트 이름 금지: 카드·띠·배너·스트립·패널·서랍·드로어·모달·탭·칩·배지·세그먼트·토글·스위치·리스트·타임라인·섹션·영역·위젯 (lint WARN).
  - `why` = **"이게 뭐냐면"** 한 문장, 사용자 눈높이 (예: "끄면 회원에게는 '정하는 중'으로만 보여요").
  - `prd` = PRD 근거(내부용, 사용자에게 안 보임) (예: "§2-2 부모가 큰 흐름만").

## 5. 흐름 (flow.json의 flows, 6~9개, step 1~5)

흐름은 **버튼이 어디로 이어지는지의 정본**이다(최종본 완성본 페이지의 버튼 이동 · lint의 버튼 검사 · 단계 문장). 사용자에게 보이는 사용 흐름은 §5-2의 구역 보드다 — 화면을 순서대로 나란히 놓고 **조건이 갈리는 곳에만** 화살표를 그린다. **흐름 하나 = 끊기지 않는 한 줄**이다: "홈에서 '예약하기'를 누르면 → 예약하기 화면에서 '날짜 선택'을 누르면 → 날짜 화면". 
- **step[i].from == step[i-1].to** 를 반드시 지킨다(lint WARN). 중간에 홈으로 돌아가 다른 걸 누르는 경우는 **별도 흐름으로 쪼갠다.** 흐름이 늘어나는 건 괜찮다 — 섞이는 게 문제다.
- 같은 화면이 여러 흐름에 나와도 된다(화면은 중복으로 그려진다).
- 순서: 처음 시작 흐름(역할별) → PRD 핵심 스토리 순.
- `name`(흐름 제목)은 **디자인 산출물에서 쓰는 작업 이름**이다: 짧은 '~하기' 형태, 8~16자. 문장·해요체·'~한다'체·주어를 쓰지 않는다 — 누가 하는지는 카드의 역할 태그가 보여준다.
  - 나쁜 예: "처음 모임을 만들어요" · "모임장이 후보 책을 적고 확정한다" · "회원이 모임 장소와 시간을 확인해요"
  - 좋은 예: "첫 모임 만들기" · "책 고르고 투표하기" · "바뀐 일정 알리기" · "모임 장소 확인하기" · "초대 수락하기"
  - 가운뎃점(·)·괄호 대신 "와/과"로 잇는다 ("공유 범위와 알림 주기 정하기").
- 역할을 건너는 전달(모임장이 보냄 → 회원이 받음)은 하나의 흐름으로 잇는다.
- step의 `action`은 **버튼 문구를 그대로 따옴표 안에** 넣은 한 문장("'변경 3건 보내기'를 누르면"). 마지막 step의 `to`가 그 스토리의 "만족 화면".

### 5-1. 갈래 (flow.json의 branches)

흐름이 한 줄이라 **흐름 밖의 버튼은 누르면 어떻게 되는지 안 보인다**(리허설 2 지적: "'후보 더하기'를 누르면 무슨 화면이 나오는지 모르겠다"). 화면마다 글자가 있는 버튼을 모두 적어 보고 셋 중 하나로 정한다:

| 버튼 | 정하는 것 | 예 |
|---|---|---|
| 새 입력·선택 UI를 연다 (핵심 작업) | 뜨는 창 화면(§3) + 갈래 | '회원 추가' → 회원 추가 창 |
| 이미 있는 다른 화면으로 간다 | 갈래 | '회원 보기' → 회원 목록 |
| 이전 화면으로 (취소·닫기·'~로') | 조각에 `data-back` | '모임으로', '취소' |
| 그 자리에서 바뀐다 (삭제·필터·다시 알리기) | 조각에 `data-stay="바뀐 뒤 안내 문구"` | '다시 알리기' → "알림을 다시 보냈어요" |

- 갈래 형식은 step과 같다: `{ from, region, trigger, action, to }`. 흐름 단계에 이미 있는 버튼은 넣지 않는다.
- 갈래는 **화면 조각을 쓰기 전에** flow.json에 적는다 — screen-writer가 갈래의 trigger도 `data-trigger`로 붙인다.
- `data-back`·`data-stay`는 screen-writer가 붙인다(00-rules 3-2). 메인은 '화면별 메모'에 "'다시 알리기'는 data-stay='알림을 다시 보냈어요'"처럼 문구가 필요한 것만 적는다.
- lint가 글자 버튼마다 셋 중 하나가 있는지 본다(FAIL).

### 5-2. 구역 보드 — 구역 · 단계 이름표 · 조건 · 정책 메모 (사용자 결정 2026-10-07: "디자이너식 구역 보드로 교체")

디자이너 보드처럼: **큰 구역 → 단계 이름표 → 화면을 순서대로 나란히**, 화살표는 주요 분기에만, **화면 아래에 정책**. 디자인 보드가 제품의 정본(source of truth)이 된다.

```json
"sections": [ { "key": "start", "name": "처음 시작하기", "desc": "가입하고 첫 모임을 만들어요" }, { "key": "home", "name": "홈", "desc": "다가오는 모임과 할 일을 한눈에 봐요" }, { "key": "club", "name": "모임 꾸리기", "desc": "모임장이 일정·사람·회비를 정해요" } ],
"screens": [
  { "slug": "join-terms", "name": "약관 동의", "section": "start", "step": "약관 동의", "…": "…",
    "policy": [
      { "title": "기본 정의", "items": ["처음엔 모두 선택 안 된 상태", "아래에서 올라온 창은 동의 전에는 닫을 수 없음", "'보기'를 누르면 약관 전문 페이지로 이동"] }
    ] },
  { "slug": "join-terms-error", "name": "약관 동의 (필수 빠짐)", "state": "error", "variantOf": "join-terms", "section": "start", "step": "약관 동의" }
]
```

- **구역(`sections`) 2~6개**: 서비스의 큰 단위 — 처음 시작하기 / 홈 / 핵심 작업(수업 예약하기·모임 꾸리기…) / 내 정보. 역할이 다르면 역할별 구역을 따로 둬도 된다. 이름은 **사용자가 하는 일**을 12자 이내 일상어로(줄임말·줄표·가운뎃점 금지), 그리고 **`desc` 한 줄 필수**(여기서 누가·언제·무엇을 하는지, ux-writing §8). 둘 다 구역 띠에 보인다(lint).
- **단계 이름표(`step`)**: 화면 위 작은 이름표. 한 단계 = 같은 일을 하는 화면 묶음(예: "닉네임 입력" 빈칸·오류·완료). 14자 이내. 상태만 다른 화면은 원래 화면과 **같은 이름표**. screens.json에서 같은 단계 화면은 붙여 둔다.
- **조건 이름표(`when`)** — flow.json step·branch에 선택: 같은 버튼·같은 화면에서 **조건에 따라 다른 화면**으로 갈 때만(예: "처음 가입이면" / "이미 가입했으면", "자리가 있으면" / "꽉 찬 수업이면"). 구역 보드는 `when`이 있는 연결에만 초록 화살표 + 이름표를 그린다. 순서대로 이어지는 단계에는 붙이지 않는다(화면 순서가 곧 흐름). 16자 이내 "~면" 꼴. 한 실행에 3~8개.
- **정책 메모(`policy`)** — 상태 변형(variantOf)을 뺀 모든 화면에 필수(lint FAIL). 화면 아래 검은 상자로 보이고, 화면 디자인 탭 오른쪽 '이 화면의 규칙'에도 나온다. 묶음 1~4개 `{ title, items[] }`, 줄은 한 줄에 규칙 하나·70자 이내:
  | 묶음 제목 예 | 적는 것 |
  |---|---|
  | 기본 정의 | 처음 들어왔을 때 상태(무엇이 선택돼 있나·비어 있나), 무엇을 누르면 어디로 |
  | 제한 · 입력 규칙 | 개수·길이·기간(최대 10장 · 영상 불가 · 2~20자 · 2주 뒤까지) |
  | 표기 | 날짜·숫자·남은 시간을 어떻게 보여주나("1개월" · "'25년 3월'" · 0개월은 '이번 달') |
  | 예외 · 오류 | 틀렸을 때·없을 때·겹칠 때 무엇을 보여주나 |
  | (움직임은 정책에 글로 적지 않는다 — §5-3 `motion`으로 적으면 완성본에서 실제로 움직이고, 보드 정책 상자에 '움직임' 묶음이 자동으로 붙는다) | |
  - PRD에 있는 규칙을 먼저 옮기고, PRD에 없어서 정한 값은 가정 로그에도 남긴다.
  - ux-writing §9대로 개조식 짧은 줄, 컴포넌트 용어 금지(lint WARN).

### 5-4. 안내·예외 — 누르면 뜨는 안내 · 글자 수 · 엣지 케이스 (사용자: "지우기 같은 행동에 안내·오류 문구가 없다", "엣지 케이스나 글자 수 제한도")

- **누르면 뜨는 안내**: 그 자리에서 바뀌는 버튼의 `data-stay="무엇이 됐는지"`(실패·오류면 `data-stay-tone="danger"`). 완성본에서 앱 디자인의 안내 상자로 뜨고, 보드 ⓘ 카드 '누르면 뜨는 안내'에 자동으로 모인다. 지우기·삭제처럼 되돌릴 수 없는 행동은 확인 창(뜨는 창 화면)을 먼저 거친다(lint WARN).
- **앱 밖으로 나가는 버튼**: 휴대폰 설정·전화·지도 앱처럼 앱 밖을 여는 버튼은 `data-out="휴대폰 설정 › 앱 › 마이크 켜기"`(경로를 ›로). 완성본에서 '앱 밖으로 나가요' 카드, 보드 ⓘ와 상태 화면에 보인다.
- **글자 수**: 글자 칸마다 `maxlength`(필요하면 `minlength`)를 화면별 메모로 정해 준다 — 완성본에 '3/20'이 실시간으로, 너무 짧으면 칸 아래 빨간 안내. 보드 ⓘ 카드 '글자 수'에 자동으로.
- **엣지 케이스 `cases`**(화면마다 선택, 입력 화면은 권장): `[{ "when": "이럴 때", "show": "보여 줄 문구", "tone": "danger|warning|info|success" }]` — 빈칸으로 보낼 때 · 너무 길 때 · 이미 있을 때 · 연결이 끊겼을 때 · 권한이 없을 때 · 기록이 없을 때. 화면 하나를 따로 그릴 만큼 큰 경우만 오류 상태 화면(`state: error`)으로, 나머지는 여기에 문구로. 보드 ⓘ 카드 '이럴 땐 이렇게'와 마우스를 올렸을 때 안내 상자로 보인다.
- 문구는 ux-writing: 무엇이 일어났는지 + 어떻게 하면 되는지(오류는 사과 없이 고치는 방법).
- **상태 화면은 따로 그리지 않아도 보드에 한 장씩 생긴다**: 구역 보드가 `cases`·누르면 뜨는 안내·앱 밖 버튼마다 원래 화면에 안내 상자·앱 밖 카드를 얹은 화면을 원래 화면 옆에 놓는다("08-1 [안내] 어젯밤 측정을 안 했으면"). 위쪽 '상태 화면 접기'로 숨긴다.

### 5-3. 움직임 (`screens[].motion`) — 피그마로 못 그리는 것을 HTML로 (사용자 결정 2026-10-07: "정책의 [움직임]까지 재현")

화면마다 선택. `[{ "type", "target", "ms", "note" }]` — 완성본 화면별 페이지(`packages/core/motion`)가 실제로 재현하고(화면에 안내 UI는 두지 않는다), 구역 보드에서는 그 화면에 마우스를 올리면 그 자리에서 재생된다(✦ 움직임 표시). `note`는 보드의 ⓘ 규칙 카드 '움직임' 묶음에 보인다. 화면 들어오기·뜨는 창 올라오기·누름 반응은 모든 화면에 기본으로 들어가니 적지 않는다.

| type | target | 언제 | note 예 |
|---|---|---|---|
| `hold` | 버튼 key(trigger) · `ms` 기본 2000 | 실수로 누르면 안 되는 버튼(측정 끝내기·삭제) | '측정 끝내기'를 2초 길게 누르면 끝나요 |
| `breathe` | 영역·버튼 key | 진행 중임을 조용히 알릴 때(녹음 중·연결 중) | 녹음 중 표시가 숨 쉬듯 천천히 깜빡여요 |
| `dim` | 없음 · `ms` 기본 3000 · `level` | 어두운 곳에서 켜 두는 화면 | 3초 뒤 화면이 가장 어두워져요 · 누르면 잠깐 밝아져요 |
| `countup` | 영역 key(없으면 화면 전체) | 결과 숫자가 핵심인 화면 | 숫자 세 가지가 0부터 올라가요 |
| `stagger` | 영역 key(없으면 본문) | 아침 요약처럼 순서대로 읽히길 바랄 때 | 판정부터 차례로 나타나요 |
| `reorder` | 목록이 든 영역 key | 사용자가 순서를 정하는 목록 | 길게 눌러 끌면 순서를 바꿀 수 있어요 |
| `carousel` | 옆으로 넘치는 띠가 든 영역 key · `ms` 간격 | 자동으로 넘어가는 띠·배너(넘김 속도) | 2.5초마다 다음 칸으로 넘어가요 |
| `play` | 재생 버튼과 진행 막대가 든 영역 key · `ms` 길이 | 소리·영상 다시 듣기 | 재생을 누르면 18초 막대가 차올라요 |

- 한 화면에 0~3개. 꼭 필요한 곳에만(핵심 작업 화면 3~6곳). lint가 type·target·note를 본다.
- **스크롤 움직임은 모든 완성본 화면에 기본**(적지 않는다, 사용자 결정 2026-10-14): 스크롤 따라 나타나기(처음 화면 아래에 있던 판이 들어올 때) · 큰 제목 접힘(내리면 화면 제목이 작아지고 뒤로 화면은 위 제목 줄에 이름) · 위 줄 그림자. 움직임 줄이기 설정이면 끈다.
- `note`는 44자 이내, 사용자가 무엇을 하면 무엇이 되는지(ux-writing §9) — 보드에서 이 글을 보고 완성본에서 직접 해 본다.

**모든 step에 `trigger`를 적는다** — 실제로 누르는 버튼의 key(케밥케이스, 예: `add-item`, `send-digest`). 화살표가 이 버튼의 파란 박스에서 다음 화면으로 나간다. 같은 화면에서 같은 버튼을 두 step이 쓰면 key를 공유한다. `action`의 따옴표 안 말이 그 버튼의 문구가 된다('일정 추가'를 누르면 → 버튼 "일정 추가").
- 역할 간 전달이 핵심인 PRD면 **역할을 건너는 플로우**를 하나 넣는다 (모임장이 확정 → 회원 화면에 반영).

## 6. 색 — PRD 맞춤 분위기 1개 + 고정 스타일 7개 + 직접 고르기 · 글자 크기 (이유 한 줄 필수)

사용자 결정(2026-10-14): "당근 스타일이나 토스 스타일, 아니면 색 팔레트처럼 빨강·파랑부터 잘 안 쓰는 색까지 직접 골라서 실시간으로 화면에 반영", "애플도 있고 여러 브랜드 더 추가", "색상은 레이아웃 선택 후 최종 다 나온 결과물에서 바로바로". 색은 **1턴에 고르지 않는다** — 1턴 시안 보드는 PRD 맞춤 색 하나로 보여주고, **2턴 초안 보드와 최종본(입구·화면별 페이지)의 '색 바꾸기'**(`packages/core/color/picker.js`)에서 자유롭게 바꾼다. 초안에서 고른 색은 의견 보내기 첫 줄로 와서 최종본의 처음 색이 되고, 최종본에서 고른 색은 그 브라우저에 기억된다.

보드에 뜨는 선택지 — 메인이 만드는 것은 **PRD 맞춤 1개뿐**:
| 종류 | 어디서 | 내용 |
|---|---|---|
| PRD 맞춤 | `screens.json` `looks` 1개 | 이 PRD의 도메인 감정을 살린 분위기 + 버튼 색 5개 (아래 규칙) |
| 고정 스타일 21개 | `packages/core/tokens/presets.json` `presets`(`group` 국내·해외) | 국내 13: 토스(회색 바탕·흰 카드·`shape: flat`) · 당근 · 카카오 · 카카오뱅크 · 배민 · 네이버 · 라인 · 쿠팡 · 컬리 · 오늘의집 · 무신사 · 29CM · 뱅크샐러드 / 해외 8: 애플 · 구글 · 에어비앤비 · 노션 · 슬랙 · 리니어(어두운) · 스포티파이(어두운) · 넷플릭스(어두운). 앱 이름은 **고르는 칸의 이름표로만** — 화면 안에 로고·앱 이름을 넣지 않는다. `exact: true`라 버튼 색 채도를 낮추지 않는다 |
| 직접 고르기 | presets.json `palette`(기본 색 12 · 색다른 색 12) + 그 밖의 색 + `bases`(흰·따뜻한·어두운 바탕) | 누르면 보드가 looks.js `customLook`으로 바로 칠한다. 고르면 답에 `색 직접 #hex(이름) · 바탕 <base>` → `screens.json` `custom` (answer-parsing §1) |

추천 색(`board.recommend.theme`)은 PRD 맞춤 또는 PRD에 가장 잘 맞는 고정 스타일 하나(예: 돈·숫자 → toss, 동네·생활 → daangn, 밤에 보는 화면 → netflix). `themeWhy`에 이유 한 줄.

PRD 맞춤 분위기 규칙 — 메인은 **배경·글자·모양·버튼 색만** 정하고, 나머지 토큰(표면·테두리·흐린 글자·눌림색·연한 강조)은 `scripts/looks.js`가 계산한다.

```json
"looks": [
  { "id": "cream", "name": "따뜻한 크림", "why": "여럿이 함께 보는 포근한 느낌이에요",
    "mode": "light", "bg": "#FBF8F3", "ink": "#1F1B16", "shape": "round",
    "swatches": [ { "id": "terracotta", "name": "테라코타", "hex": "#D9562B" }, … 5개 ] },
  ← PRD 맞춤 1개. 고정 스타일(toss·daangn…)은 넣지 않는다 — looks.js가 붙인다
],
"theme": "cream", "toggles": { "type": "large", "swatch": "terracotta" },
"board": { "recommend": { "theme": "cream", "themeWhy": "…", "type": "large", "typeWhy": "…", "swatch": "terracotta", "swatchWhy": "…" } }
```

- **PRD 맞춤은 고정 스타일과 겹치지 않게**: 고정 스타일이 밝고 중립·브랜드 색을 이미 덮으므로, PRD 맞춤은 도메인의 감정을 살린 쪽(따뜻한 크림·새벽 안개 같은)으로. `shape`는 soft 기본 / round 부드럽고 둥글게 / sharp 각지게 / flat 회색 바탕 위 흰 카드. id는 고정 스타일 id와 다르게.
- **이름은 한국어 일상어**: "깔끔한 흰색", "따뜻한 크림", "밤 바다", "숲 속 아침". "모던", "미니멀", 영어, "테마 A" 금지. `why`는 "~에 어울려요 / ~한 느낌이에요" 한 문장.
- **버튼 색 5개**: 그 분위기에 어울리는 색, **첫 번째가 추천**. 이름은 색 이름(바다 파랑 · 청록 · 테라코타 · 숲 초록 · 먹색 · 모래 노랑 …). 상태색(확정 초록·변경 주황·삭제 빨강)이 중요한 서비스면 추천 버튼 색을 그 색들과 겹치지 않게(파랑·청록·먹색 쪽).
- **대비**: 글자(ink)와 배경(bg) 7 이상(4.5 미만 FAIL), 버튼 색 위 글자 3 이상(lint가 계산).
- **글꼴 세트 `font`** — 분위기마다 하나(사용자 결정: 분위기를 고르면 글꼴도 따라간다 · 선택지는 늘리지 않는다). 글꼴마다 어울리는 굵기·자간·줄간격·글자 진하기가 묶여 있다(`scripts/looks.js` FONTS):
  | id | 이름 | 어울리는 곳 |
  |---|---|---|
  | `pretendard` | 프리텐다드 | 중립 — 어떤 서비스에도 (기본) |
  | `suit` | 수트 | 숫자·정보가 많은 화면, 또렷하게 |
  | `nanum-square-round` | 나눔스퀘어라운드 | 둥글고 친근 — 생활·가족·아이 |
  | `ibm-plex` | IBM 플렉스 | 곧고 단정 — 업무 도구·관리 |
  | `serif-title` | 명조 제목 | 제목만 명조 — 기록·읽을거리·감성 |
  PRD 맞춤은 도메인에 맞는 글꼴 하나(고정 스타일은 저마다 글꼴이 정해져 있다).
- **자동 보정(디자이너 기준)** — 메인이 정한 값을 looks.js가 고쳐 쓴다: 본문 글자가 순수 검정·순수 흰색에 가까우면 바탕 쪽으로 눌러 준다(#000 → #2C2C2C 수준), 버튼 색이 형광처럼 쨍하면 채도만 낮춘다, 상태색(완료·주의·오류·안내)은 원색 대신 차분한 색(흙빛 빨강 등). 그래서 `ink`는 "검정 계열"·"흰색 계열"처럼 방향만 맞으면 되고, 버튼 색은 이름에 맞는 색을 고르면 된다.
- 추천 신호:

| 신호 | 추천 |
|---|---|
| 가족·생활·기록·감성 | 따뜻한 밝은 분위기(round) |
| 업무·관리·데이터·도구 | 밝고 중립(soft) |

## 7. board.ask — 구조 질문 최대 3개
